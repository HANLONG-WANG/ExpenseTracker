# 一、架构总决策

最终采用：

> **粗粒度多模块的模块化单体架构，内部使用领域驱动的分层设计、端口与适配器、轻量 CQRS、不可变账务日志和可重建投影。**

完整表述为：

|维度|决策|
|---|---|
|部署形态|单个 Android App Bundle|
|进程模型|单应用进程，不拆分业务进程|
|代码组织|多 Gradle 模块、模块化单体|
|分层|UI → Application → Domain ← Infrastructure|
|写入模型|Command/use case 驱动，所有财务写入经过统一协调器|
|读取模型|独立查询模型和投影，轻量 CQRS|
|财务审计|不可变 journal/posting，修改通过冲销和替换实现|
|业务历史|当前实体＋不可变 revision 链|
|数据权威源|本机 SQLCipher 主数据库|
|文件权威源|加密内容对象库＋数据库元数据|
|网络角色|汇率、地图、Drive、遥测的外部适配器，不是账本权威源|
|一致性|单 SQLite 事务覆盖所有财务状态和同步投影|
|后台执行|数据库操作记录＋WorkManager/UIDT/前台服务触发|
|大型导入恢复|加密暂存库或影子数据库，验证后原子替换|
|备份|逻辑全量、物理增量的快照仓库；另提供单文件便携备份|
|安全|设备账本密钥、保险库认证密钥、恢复密码密钥三层分离|

Android 官方架构指南建议明确区分 UI、数据和可选领域层，通过 repository 暴露数据、使用单向数据流，并在大型复杂应用中使用领域层封装可复用业务逻辑。这个项目的复杂度远高于普通 CRUD 应用，因此领域层不是可选项。([Android Developers](https://developer.android.com/topic/architecture/recommendations "Recommendations for Android architecture  |  App architecture  |  Android Developers"))

# 二、为什么不是其他架构

## 1. 不使用单模块 MVVM

单模块 MVVM 很快会出现：

- ViewModel 直接组合多个 DAO；
    
- 预算、贷款、退款和账户余额逻辑散落在页面中；
    
- 修改一笔交易时，不同模块各自更新；
    
- 无法证明账务不变量；
    
- 导入和周期交易绕过正常写入规则；
    
- 数据库迁移和测试范围失控。
    

MVVM只作为 UI 层的状态组织模式，不作为整个系统架构。

## 2. 不使用微服务或本地“多服务”架构

本产品没有服务端账户和在线同步，所有复杂业务都需要在同一个本地数据库事务中完成。拆分服务只会破坏原子一致性。

## 3. 不采用完整事件溯源

不会要求通过重放全部事件来还原所有当前业务对象。那会使查询、数据库迁移、合并恢复和调试成本过高。

本项目采用的是：

> **当前状态表＋不可变业务修订＋不可变财务日志。**

财务日志不可修改，但账户、分类、商户等仍有高效的当前状态表。

## 4. 不采用全局 Redux/MVI Store

使用单向数据流，但不引入一个保存整个应用状态的全局 Store。50 万笔交易和复杂页面不适合被映射为一个内存状态树。

每个页面或流程拥有自己的 ViewModel 和 `UiState`，数据库仍是应用级状态权威源。

Android 官方模块化指南强调高内聚、低耦合，feature 模块不应了解其他 feature 内部实现，data source 也应隐藏在 repository 之后；同时也警告过细模块化会带来过多构建和配置开销。([Android Developers](https://developer.android.com/topic/modularization/patterns?utm_source=chatgpt.com "Common modularization patterns | App architecture"))

# 五、运行时架构

## 1. 单进程、单 Activity

应用采用：

- 一个 Android 应用进程；
    
- 一个 `MainActivity`；
    
- 一套 Compose 根树；
    
- 一个 SQLCipher 主数据库实例；
    
- 所有 Worker、Service、小组件更新和 ContentProvider 默认运行在同一进程。
    

不为数据库、附件、地图或备份创建独立进程。多进程会使数据库连接、应用锁、Keystore会话和内存缓存管理显著复杂化。

## 2. 应用运行状态机

```text
Uninitialized
     │
     ▼
FirstRun ───────────────┐
     │                  │
     ▼                  │
Locked                  │
     │ authenticate     │
     ▼                  │
OpeningBook             │
     ├── migration ───> Maintenance
     ├── failure ─────> RecoveryRequired
     ▼
Ready
     │ background/timeout
     ▼
Locked
```

`BookSessionManager`负责：

- SQLCipher数据库生命周期；
    
- UI会话锁定；
    
- 内存密钥引用；
    
- 敏感图片缓存清理；
    
- 后台任务的数据库 lease；
    
- 迁移和恢复期间的只读或维护状态。
    

应用锁定后，UI不再访问账本。后台任务只能通过受限的 `HeadlessBookLease` 打开数据库。

# 六、账务内核架构

这是整个系统最重要的边界。

## 1. 三种不同概念

必须明确区分：

### 用户业务交易 `BusinessTransaction`

用户在界面上看到的一笔业务：

- 支出；
    
- 收入；
    
- 转账；
    
- 退款；
    
- 信用卡还款；
    
- 贷款还款；
    
- 外币兑换；
    
- 互请结算。
    

### 业务修订 `TransactionRevision`

交易每次创建、编辑、删除、恢复产生一个不可变修订。

### 会计日志 `JournalEntry / Posting`

业务修订对财务账户产生的底层会计影响。

```text
BusinessTransaction
        │ currentRevisionId
        ▼
TransactionRevision
        │ produces
        ▼
JournalEntry 1..N
        │
        ▼
Posting 2..N
```

## 2. 不可变会计日志

`JournalEntry` 和 `Posting` 一经提交后永不修改、永不删除。

编辑交易时：

```text
旧交易：1000 JPY 餐饮
          │
          ├── 追加旧分录的反向冲销
          └── 追加新交易 1200 JPY 的替换分录
```

删除交易时追加冲销，不删除旧 posting。

恢复交易时追加新的恢复分录。

这使数据库能够回答：

- 当前余额是多少；
    
- 某一历史时点发生了什么；
    
- 某次修改前后差异是什么；
    
- 为什么余额发生变化；
    
- 旧分录是否曾经存在。
    

这不是完整事件溯源，因为当前交易仍由当前 revision 直接读取；只有财务效果采用不可变追加模型。

## 3. 隐藏式复式记账

内部使用真正的借贷方向：

|内部账户类型|正常余额方向|
|---|---|
|现金和银行资产|借方|
|信用卡、贷款负债|贷方|
|费用|借方|
|收入|贷方|
|期初权益|贷方|
|互请结算头寸|可正可负，内部按借方余额表示应收|

用户永远不直接看到“借方”和“贷方”。

内部系统账户包括：

- `SYSTEM_INCOME`
    
- `SYSTEM_EXPENSE`
    
- `SYSTEM_OPENING_EQUITY`
    
- `SYSTEM_BALANCE_ADJUSTMENT`
    
- `SYSTEM_FX_CLEARING`
    
- `SYSTEM_FX_ROUNDING`
    
- 每个互请活动和参与人的结算头寸账户
    

分类不是会计账户，而是统计维度。这样分类重命名、归档或删除不会改变会计结构。

## 4. 多币种 posting

每个 posting 至少保存：

```text
ledgerAccountId
side                    DEBIT / CREDIT
accountAmountMinor      账户币种金额
accountCurrency
baseAmountMinor         本位币历史估值
baseCurrency
valuationRate
valuationSource
```

不变量：

```text
Σ 借方 baseAmountMinor = Σ 贷方 baseAmountMinor
```

账户余额使用 `accountAmountMinor`。

收入、费用和历史报表使用交易时的 `baseAmountMinor`。

当前净金融资产使用账户当前余额和最新汇率重新估值。

舍入差额只能进入 `SYSTEM_FX_ROUNDING`，不能静默丢失。

## 5. 财务语义不能只存一个枚举

贷款还款可能同时包含：

- 本金：资产负债转换；
    
- 利息：非消费费用；
    
- 手续费：非消费费用。
    

因此一笔业务交易可以有多条经济影响：

```text
EconomicEffectLine
 ├── nature: INCOME / EXPENSE / CONTRA_EXPENSE / EQUITY
 ├── consumption: true / false
 ├── amountInBaseCurrency
 ├── categoryId
 ├── projectId
 └── accrualDate
```

预算影响单独保存：

```text
BudgetEffectLine
 ├── kind: USE / RESTORE / ADJUST
 ├── targetMonth
 ├── categoryId
 ├── projectId
 └── amount
```

这样不会试图从银行账户流动反推“消费”或“预算”。

# 七、统一财务写入入口

所有可能改变财务结果的操作都必须经过：

> `FinancialMutationCoordinator`

禁止：

- DAO直接插入交易；
    
- 导入程序直接写表；
    
- Worker直接修改余额；
    
- ViewModel调用多个 repository 手工拼接；
    
- 数据库 trigger 承担业务规则。
    

## 1. 命令模型

示例命令：

```kotlin
sealed interface FinancialCommand {
    val commandId: CommandId
    val expectedRevisionId: RevisionId?
}

data class RecordExpenseCommand(...)
data class EditTransactionCommand(...)
data class DeleteTransactionCommand(...)
data class RestoreTransactionCommand(...)
data class RecordRefundCommand(...)
data class RecordTransferCommand(...)
data class RecordCreditPaymentCommand(...)
data class RecordLoanPaymentCommand(...)
data class RecordSettlementCommand(...)
```

每个命令具有全局唯一 `commandId`，用于幂等处理。

编辑命令包含 `expectedRevisionId`，实现乐观并发控制。即使是单用户，后台周期任务、导入和恢复也可能与编辑页面同时发生。

## 2. 纯领域规划

命令不会直接写数据库。领域层先生成不可变计划：

```kotlin
data class FinancialMutationPlan(
    val revision: TransactionRevisionDraft,
    val journalEntries: List<JournalEntryDraft>,
    val economicEffects: List<EconomicEffectDraft>,
    val budgetEffects: List<BudgetEffectDraft>,
    val projectEffects: List<ProjectEffectDraft>,
    val goalEffects: List<GoalEffectDraft>,
    val statementEffects: List<StatementEffectDraft>,
    val loanEffects: List<LoanEffectDraft>,
    val settlementEffects: List<SettlementEffectDraft>,
    val projectionChanges: ProjectionChangeSet
)
```

Planner 是纯 Kotlin：

- 不访问 Room；
    
- 不访问网络；
    
- 不读取系统时间；
    
- 不生成随机数；
    
- 所有 Clock、ID、汇率、现有状态由调用方显式传入。
    

因此相同输入必然生成相同结果。

## 3. 提交流程

```text
UI Action
   │
   ▼
ViewModel
   │
   ▼
Command Handler
   │
   ├── 加载当前业务快照
   ├── 检查 expectedRevision
   ├── 领域校验
   └── 生成 MutationPlan
           │
           ▼
FinancialMutationCoordinator
           │
           ▼
Room withTransaction
   ├── 检查 commandId 未处理
   ├── 创建 BookCommit
   ├── 插入 TransactionRevision
   ├── 追加冲销分录
   ├── 追加替换分录
   ├── 写入所有 effect
   ├── 更新同步投影
   ├── 验证借贷平衡
   ├── 验证 projection revision
   ├── 更新当前 revision 指针
   ├── 增加 bookRevision
   └── 记录 CommandReceipt
```

其中任何一步失败，整个事务回滚。

## 4. 单写入门

进程内使用 `LedgerWriteGate`：

```kotlin
class LedgerWriteGate {
    private val mutex = Mutex()

    suspend fun <T> execute(block: suspend () -> T): T =
        mutex.withLock { block() }
}
```

它减少多个长写事务之间的争用，并提供确定性提交顺序。

真正的原子性仍由 SQLite 事务保证，Mutex不是数据库事务的替代品。

# 八、Commit、版本和合并恢复

## 1. 双版本标识

每次数据提交产生：

- `BookCommitId`：全局稳定 UUID，用于备份和跨设备合并；
    
- `localRevision: Long`：本机单调递增，用于投影版本和缓存失效。
    

```text
Book
 ├── headCommitId
 └── localRevision
```

所有被修改的实体记录：

- `lastCommitId`
    
- `rowVersion`
    
- `contentHash`
    

## 2. Commit 图

普通操作只有一个父 commit：

```text
A ──> B ──> C
```

同一账本在两台设备发生分叉：

```text
          ┌──> C1
A ──> B ──┤
          └──> C2
```

合并后创建双父 commit：

```text
C1 ──┐
     ├──> M
C2 ──┘
```

因此“合并恢复”不是根据最后修改时间粗暴覆盖，而是：

1. 找到共同祖先；
    
2. 对实体稳定 ID 做三方比较；
    
3. 无冲突数据自动合并；
    
4. 同一实体的分叉修改要求用户选择；
    
5. 账务交易的不同新增可以直接并入；
    
6. 同一交易的两条不同 revision 构成冲突。
    

这仍然不是实时同步，只是可靠的备份合并能力。

# 九、主数据库架构

## 1. 一个主业务数据库

- 账务日志；
    
- 交易修订；
    
- 预算；
    
- 项目；
    
- 目标；
    
- 信用卡；
    
- 贷款；
    
- 互请；
    
- 周期模板；
    
- 附件元数据；
    
- 搜索索引；
    
- 地理索引；
    
- 投影；
    
- 后台操作状态。

# 十、投影与轻量 CQRS

## 1. 写模型和读模型分离

写模型追求：

- 完整不变量；
    
- 修订和审计；
    
- 原子提交；
    
- 清晰领域含义。
    

读模型追求：

- 快速列表；
    
- 快速报表；
    
- Paging；
    
- 地图聚类；
    
- 小组件读取。
    

UI不会直接把 `PostingEntity` 或 `TransactionRevisionEntity` 拼成页面。

## 2. 同步投影

下列结果必须与财务命令在同一数据库事务中更新：

- 当前账户余额；
    
- 账户每日汇总；
    
- 当前交易视图；
    
- 退款剩余额度；
    
- 当月预算使用；
    
- 项目预算使用；
    
- 目标余额；
    
- 信用卡账单金额；
    
- 贷款实际进度；
    
- 互请净额；
    
- FTS记录；
    
- R*Tree坐标；
    
- 小组件关键指标。
    

每个投影保存：

```text
asOfLocalRevision
```

提交前检查：

```text
projection.asOfLocalRevision == newBookRevision
```

不允许出现“余额已更新但预算还未更新”的时间窗口。

## 3. 重型分析缓存

自定义报表缓存可以异步生成，但只能在以下条件使用：

```text
cache.bookRevision == book.localRevision
```

不匹配时：

- 从当前投影和事实表即时查询；或者
    
- 先重建后再展示。
    

绝不展示旧版本缓存后再悄悄刷新。

## 4. 账户运行余额

不为每笔交易永久保存一个容易失效的运行余额。

使用：

- 每账户每日 opening/inflow/outflow/closing 投影；
    
- 查询某日时从该日 opening 开始；
    
- 用窗口函数计算当日每笔交易后的余额。
    

修改多年以前的交易时，只需从受影响日期向后重算每日余额，而不是重写所有历史交易行。

# 十一、搜索和自定义分析架构

## 1. 搜索

使用两级查询：

```text
FTS5：文本候选
R*Tree：地理候选
普通索引：日期、账户、分类、金额等
最终精确过滤：SQL/Kotlin
```

FTS只存储可搜索文本，不存保险库字段。

地图半径查询：

1. R*Tree获得矩形范围候选；
    
2. Kotlin计算精确球面距离；
    
3. 再应用账户、分类、金额等筛选。
    

## 2. 类型安全的报表定义

自定义报表不会接受 SQL字符串，而是保存类型化 AST：

```kotlin
data class ReportSpec(
    val measures: List<Measure>,
    val dimensions: List<Dimension>,
    val filters: FilterExpression,
    val granularity: TimeGranularity,
    val sorting: List<ReportSort>,
    val comparison: ComparisonMode?
)
```

指标和维度使用封闭枚举或 sealed interface，例如：

```text
Measure:
  Expense
  Consumption
  Income
  NetCashFlow
  BudgetUsage
  AccountBalance
  NetFinancialAssets

Dimension:
  Date
  Category
  Merchant
  Account
  Project
  Currency
  Place
```

`ReportSqlCompiler`只允许预定义列、JOIN和聚合，所有用户值使用绑定参数。用户无法构造任意 SQL。

## 3. 查询计划

查询服务根据 ReportSpec 自动选择：

1. 月度汇总；
    
2. 每日汇总；
    
3. 当前经济影响事实表；
    
4. 原始 journal/posting。
    

固定常用报表优先使用投影。

特殊自定义组合才回退到事实表。

## 4. 预测与异常

预测和异常算法位于纯 Kotlin `analytics:domain`：

- 输入是不可变时间序列；
    
- Clock和当前日期显式传入；
    
- 输出包含算法版本和解释信息；
    
- 不直接读数据库；
    
- 不写回账务数据。
    

这样可以对算法做 golden test 和 property test。

# 十二、附件对象库

附件不能作为普通路径保存在数据库中。

## 1. 内容对象模型

```text
Attachment
  ├── attachmentId
  ├── displayName
  └── blobId

EncryptedBlob
  ├── blobId
  ├── randomStorageName
  ├── plaintextSha256
  ├── size
  ├── mime
  ├── wrappedDataKey
  ├── encryptionVersion
  └── referenceCount
```

磁盘文件名使用随机 ID，不直接使用明文 SHA-256，避免通过文件名暴露文件相同性。

## 2. 导入流程

```text
ContentResolver InputStream
       │
       ▼
流式计算 SHA-256＋加密到 staging
       │
       ├── 已存在同 hash/size：删除 staging，复用现有 blob
       │
       └── 新文件：原子 rename 到对象库
                         │
                         ▼
                 数据库事务创建关联
```

数据库提交之前，最终 blob 必须已经存在。

如果数据库事务失败，最多产生一个无引用的孤立 blob，由清理任务删除；不会产生“数据库引用成功但物理文件不存在”的状态。

## 3. 删除

删除交易只删除或软删除关联，不立即删除物理对象。

只有同时满足：

- 回收站已过期；
    
- 没有任何当前或历史引用；
    
- 不再被受保留备份依赖；
    

才允许垃圾回收物理 blob。

## 4. 外部打开

实现 `SecureAttachmentProvider`：

- 使用 `ParcelFileDescriptor` pipe；
    
- 后台协程边解密边写入 pipe；
    
- 外部应用获得一次性 URI授权；
    
- 不生成永久明文副本；
    
- Provider不支持目录浏览；
    
- URI带随机短期 token；
    
- 应用锁定后停止新授权。

# 十三、后台任务架构

WorkManager用于可靠但不要求精确时刻的任务，并支持唯一工作、约束、重试和设备重启后的重新调度。周期交易的正确性不能依赖WorkManager准点执行，而应依赖本地 occurrence engine 的补齐算法。([Android Developers](https://developer.android.com/develop/background-work/background-tasks/persistent "Task scheduling  |  Background work  |  Android Developers"))

## 1. Worker只携带不透明ID

WorkManager自身有独立数据库，因此其 InputData 中禁止放入：

- 金额；  
    -账户名称；
    
- 备注；
    
- 文件名；
    
- 位置；
    
- 备份密码；
    
- Drive路径。
    

只传：

```text
operationId
```

完整操作参数位于主加密数据库。

## 2. 长操作状态机

```text
QUEUED
  │
  ▼
PREPARING
  │
  ▼
RUNNING
  ├──> PAUSED
  ├──> CANCEL_REQUESTED
  ├──> FAILED_RETRYABLE
  ├──> FAILED_FINAL
  ▼
COMMITTING
  ├──> ROLLING_BACK
  ▼
SUCCEEDED
```

适用于：

- 导入；
    
- 导出；
    
- 完整备份；
    
- Drive上传；
    
- 恢复；
    
- 合并；
    
- 附件迁移；
    
- 大型数据库维护。
    

每个阶段都有持久化 checkpoint。进程被终止后从最后一个安全检查点继续。

## 3. 周期交易

`RecurrenceEngine`根据：

- series revision；
    
- 起止日期；
    
- 时区；
    
- 周末规则；
    
- 最后成功 occurrence；
    

确定应产生的发生项。

唯一约束：

```text
UNIQUE(seriesId, seriesRevisionId, occurrenceInstant)
```

因此以下情况都不会重复记账：

- Worker重复运行；
    
- 应用启动补齐；
    
- 系统重启；
    
- Worker执行中进程被杀；
    
- 用户手动重试。

# 十四、大型导入与批量操作

## 1. 独立加密暂存数据库

十万行导入不直接写入主数据库，而是创建一次性 SQLCipher staging database：

```text
import_<operationId>.db
```

暂存库保存：

- 原始行；
    
- 解析结果；
    
- 字段映射；
    
- 校验错误；
    
- 重复候选；
    
- 实体映射；
    
- 生成的准备命令；
    
- 临时附件引用。
    

优点：

- 不污染主数据库；
    
- 取消时直接删除暂存库；
    
- 解析和预览不持有主库长事务；
    
- 导入失败不会扩大主库 WAL；
    
- 容易实现崩溃恢复。
    

## 2. 提交

小批量可以在主库单事务提交。

超大批量采用影子数据库：

1. 创建主数据库一致性快照；
    
2. 在影子数据库应用全部 prepared commands；
    
3. 使用相同领域规划器和不变量检查；
    
4. 执行完整 integrity check；
    
5. 暂停主库写入；
    
6. 检查 live head commit 未变化；
    
7. 原子替换数据库；
    
8. 重新打开并验证；
    
9. 保留旧库作为安全快照。
    

这样实现真正的全有或全无，同时避免主数据库被锁定很长时间。

批量导入不得绕过 `FinancialMutationPlanner`。

# 十五、备份架构

每日保留30个“完整备份”，若每份都物理复制数十 GB，存储不可接受。因此备份必须区分逻辑快照和物理对象。

## 1. 管理型备份仓库

目录模型：

```text
backup-repository/
 ├── repository-header
 ├── snapshots/
 │    ├── snapshot-A.manifest
 │    ├── snapshot-B.manifest
 │    └── ...
 └── objects/
      ├── DB chunk objects
      ├── attachment objects
      ├── settings package
      └── vault package
```

每个 snapshot 在逻辑上完整，但物理上只引用加密对象。

数据库一致性快照被切分成固定块并去重；未改变的附件直接复用原有对象。

删除旧快照时：

1. 删除 manifest；
    
2. 计算仍被其他 snapshot 引用的对象；
    
3. 仅回收无引用对象。
    

## 2. 单文件便携备份

用户手动导出时生成：

```text
*.ledger-backup
```

其内容为：

- 版本头；
    
- 加密 manifest；
    
- 数据库快照；
    
- 附件对象；
    
- 设置；
    
- 可选保险库；
    
- 完整性校验。
    

采用 ZIP64＋Streaming AEAD流式输出，不把完整备份放入内存。

## 3. 备份过程

```text
短暂数据库检查点
        │
        ▼
创建一致性 SQLCipher 快照
        │
        ▼
释放主数据库写入
        │
        ▼
分块、去重、生成加密 manifest
        │
        ▼
写本地仓库或 Drive
        │
        ▼
校验远端对象
        │
        ▼
发布 snapshot manifest
```

只有最后的 manifest 发布成功，快照才视为有效。未完成对象由垃圾回收任务处理。

## 4. 恢复

恢复不直接覆盖当前数据：

1. 下载或读取全部对象；
    
2. 验证密码；
    
3. 验证 AEAD；
    
4. 验证每个对象哈希；
    
5. 在影子目录重建；
    
6. 执行数据库迁移；
    
7. 执行 `integrity_check`；
    
8. 验证 journal平衡；
    
9. 重建并验证投影；
    
10. 原子交换 live/restore 目录；
    
11. 保留恢复前安全快照；
    
12. 用户确认后才允许清理旧数据。

# 十六、安全密钥架构

## 1. 三层密钥

```text
Android Keystore
│
├── DeviceLedgerKEK
│     ├── wraps SQLCipher DB DEK
│     ├── wraps Attachment Root KEK
│     └── wraps Secure Settings Key
│
└── VaultAuthenticationKEK
      └── wraps Vault DEK
          需要每次生物识别或设备凭据认证

Recovery Password
│
└── Argon2id
      └── Backup KEK
            ├── wraps Backup Repository Key
            ├── wraps portable DB key material
            ├── wraps attachment key material
            └── optionally wraps Vault DEK
```

## 2. 账本密钥不能要求每次生物识别

SQLCipher和附件基础密钥不能绑定“每次使用都认证”，原因是：

- 周期交易需要后台运行；
    
- 自动备份需要后台读取；
    
- 回收站和维护任务需要数据库；
    
- 小组件需要受控读取。
    

因此：

> **应用锁是 UI访问控制，不是整个数据库密钥的生物识别门。**

数据库仍通过应用沙箱、Keystore和SQLCipher实现静态加密。

卡片保险库则使用独立的认证绑定密钥。

## 3. 保险库双重包装

为了让自动备份能够包含保险库，而不在后台弹出指纹：

- Vault DEK由设备认证密钥包装一份；
    
- 用户启用“备份保险库”时，再由恢复密码体系包装一份；
    
- 自动备份只复制密文和恢复包装密钥；
    
- 不需要在后台解密卡号和安全码。
    

新手机恢复后：

1. 恢复密码解开Vault DEK；
    
2. 新设备创建新的认证绑定Keystore密钥；
    
3. 重新包装Vault DEK；
    
4. 删除临时明文密钥。
    

## 4. 字段级关联数据

保险库字段加密时的 AEAD associated data 包含：

```text
bookId
cardId
fieldType
schemaVersion
```

这样攻击者不能把一张卡的安全码密文移动到另一张卡或另一个字段后仍成功解密。

## 5. 位置保存

保存时：

1. 如果已有位置，立即使用；
    
2. 如果请求尚未完成，最多等待剩余3秒；
    
3. 超时保存无位置交易；
    
4. 不在后台补写。
    

位置请求属于UI流程，领域命令只接收最终的 `LocationSnapshot?`。

# 十九、错误和故障恢复

## 1. 错误分层

```text
DomainError
 ├── ValidationError
 ├── AccountingInvariantViolation
 ├── ConflictError
 ├── CurrencyError
 └── BudgetRuleError

DataError
 ├── DatabaseUnavailable
 ├── StorageFull
 ├── CorruptData
 └── PermissionRevoked
```

## 2. 启动完整性恢复

启动时只做轻量检查：

- 数据库能否解密；
    
- schema是否正确；  
    -最近一次操作是否处于未完成状态；  
    -投影版本是否等于book revision；  
    -是否存在待完成的文件操作。
    

若检测到不一致：

- 禁止新的财务写入；
    
- 进入 `Maintenance`；
    
- 从journal或影子快照重建；
    
- 重建成功后恢复Ready；
    
- 无法恢复时进入RecoveryRequired。

# 二十、性能架构

## 1. 查询原则

- 列表使用 Paging 3；
    
- 大列表优先使用 keyset pagination，而不是深层 OFFSET；
    
- 常用查询必须有复合索引；
    
- 不在UI查询中使用大型 Room嵌套 `@Relation` 对象图；
    
- 不把全部交易加载到内存后分组；
    
- 不在每次重组时重新执行SQL；
    
- 图表只查询当前显示范围和必要粒度。
    

## 2. 关键索引

示例：

```text
posting(account_id, effective_instant, posting_id)
economic_effect(local_date, nature, category_id)
business_transaction(deleted_at, effective_instant, id)
transaction_revision(transaction_id, revision_number)
budget_effect(target_month, category_id)
journal_entry(business_transaction_id, created_commit_id)
recurrence_occurrence(series_id, occurrence_instant)
credit_statement(credit_account_id, cycle_start, cycle_end)
location_rtree(min_lat, max_lat, min_lon, max_lon)
```

## 3. 数据库维护

从建库开始启用：

- WAL；
    
- foreign keys；
    
- incremental auto-vacuum；  
    -受控WAL checkpoint；
    
- `PRAGMA optimize`；
    
- SQLCipher内部日志关闭；
    
- file-based临时存储安全验证。
    

完整 `VACUUM`不作为常规维护任务，因为它可能需要接近数据库大小的额外空间。

## 4. 数值溢出

每行金额为 `Long`，但所有加减使用受检运算：

```kotlin
Math.addExact()
Math.subtractExact()
```

复杂中间值使用 `BigInteger`。

SQLite `SUM`溢出时不能转为Double继续计算；查询服务应：

- 使用安全的汇总层；
    
- 或分块读取后用BigInteger累加；
    
- 或明确返回数值范围错误。

# 二十一、测试架构

## 1. 领域测试

`finance:domain`不依赖Android，因此可以高密度执行：

- journal平衡性质测试；
    
- 冲销后净效果为零；
    
- 编辑等于旧分录冲销＋新分录；
    
- 贷款本金守恒；
    
- 互请参与人净额总和为零；
    
- 预算结转链；  
    -跨月退款；  
    -多币种舍入；  
    -周期规则幂等；  
    -金额表达式解析。
    

## 2. 数据库契约测试

每个正式schema版本测试：

- 从所有旧版本升级；
    
- 迁移后journal平衡；
    
- 主键和外键完整；
    
- 投影可重建；
    
- FTS和R*Tree可查询；
    
- SQLCipher真机解密；
    
- WAL文件不含明文；
    
- 不允许 destructive migration。
    

## 3. 故障注入

必须覆盖：

- 附件加密完成后数据库提交失败；
    
- 数据库提交后进程立即终止；
    
- Drive上传中断；
    
- SAF权限被撤销；
    
- 备份空间不足；
    
- 恢复交换前崩溃；
    
- 恢复交换后首次打开失败；
    
- Keystore密钥失效；
    
- 生物识别配置变化；
    
- 导入第99,999行失败；
    
- 修改十年前交易后的预算链重算；
    
- 应用更新期间projection版本变化。
    

## 4. 架构约束测试

CI检查：

- feature模块不能依赖data模块；
    
- domain不能依赖Android；
    
- DAO和Room Entity不能出现在feature API；
    
- 禁止通用遥测Map；
    
- 禁止敏感类型调用普通日志；
    
- 禁止直接实例化系统Clock或随机ID生成器；
    
- 禁止财务DAO写方法被写入协调器之外调用。

# 二十二、冻结的架构决策记录

|ADR|决策|
|---|---|
|ADR-001|使用粗粒度多模块的模块化单体|
|ADR-002|SQLCipher主数据库是账本唯一权威源|
|ADR-003|采用当前状态＋不可变修订＋不可变财务日志|
|ADR-004|不采用完整事件溯源|
|ADR-005|采用轻量CQRS，写模型和查询投影分离|
|ADR-006|所有财务写入必须经过FinancialMutationCoordinator|
|ADR-007|Journal和Posting只追加，不更新、不删除|
|ADR-008|修改通过冲销旧效果和追加替换效果完成|
|ADR-009|所有核心财务投影在同一数据库事务更新|
|ADR-010|使用单进程和单写入门|
|ADR-011|网络数据不是账本权威源|
|ADR-012|大型导入使用加密暂存库或影子数据库|
|ADR-013|恢复必须先在影子目录验证，再原子交换|
|ADR-014|管理型备份采用逻辑全量、物理增量|
|ADR-015|同账本合并使用稳定ID和Commit图|
|ADR-016|账本密钥、保险库密钥和恢复密码密钥分离|
|ADR-017|应用锁是UI访问控制，保险库使用密码学认证门|
|ADR-018|WorkManager只传递不透明operation ID|
|ADR-019|报表使用类型安全AST，不接受用户SQL|
|ADR-020|不支持拆分交易的限制由领域模型强制执行|
