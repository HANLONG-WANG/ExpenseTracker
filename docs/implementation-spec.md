## 1. 金融规则配置与验证

### 1.1 可分步使用的三个层次

1. **账户与实际记录**：名称、类型、币种、期初日期及余额/债务、实际流水。没有计息规则仍可使用。
2. **手动已知安排**：已确认账单、下一还款日、本金/费用组成及未来逐期平台计划。即使缺规则，已知金额仍能参与提醒和资金时间线。
3. **规则预测与调整试算**：资料齐全才计算该规则支持的情景。缺项列出具体原因，不把未知费用视为零，不把未知利用可能额显示为零。

“用户填写完整”与“经过实际账单验证”分开；规则在对比后可标记已验证，后续账单不一致仍展示差异。

### 1.2 按支付或借款模式配置

| 模式 | 关键规则与资料 |
| --- | --- |
| 一次付 | 締め日、边界当天的归属、账单月份、还款日、实际扣款账户、本期日期覆盖。 |
| 分期 | 支持期数；每100单位账户币种手续费表、总手续费/费率或该机构实际适用算法；逐期本金/费用分配、首末期处理、取整时点。 |
| リボ | 年率；按日/月计费；计费余额依据；计息起止与端点是否计入；365/366或机构实际约定；本金定额/含费总额/余额阶梯；首次收费、自动リボ、最低额与费用分配。 |
| 固定借款 | 按合同维护本金、实际到账、预扣/另付费用、期数和起止；等额本金、等额本息、按期付息到期还本或手动计划；提前还款/退款的实际费用与未来计划变化。 |
| 循环借款 | 授信总额、已用本金、逐笔新增借入、日/月利息、付款分配顺序、计费区间和额度恢复条件。 |

- 模式有独立配置，不能用リボ年率推定分期手续费。机构名称不填入任何规则。
- 不要求用户写公式。复杂或未支持的计费方案使用手动确认逐期计划，明确“暂不能自动试算”，不套用近似公式冒充精确结果。
- 分期允许逐期覆盖本金/费用；通用等额方案仅在明确选择并填齐适用规则后使用。月本金不足以覆盖债务、含费总额不足费用等情况明确显示无法按该方案结清，不生成假结清计划。
- 信用卡消费保存当前付款方式（一次付/分期/リボ/明确采用本卡自动リボ设置）、分期次数和采用的自动规则版本。自动设置按消费日期选取，未配置不推定一次付；之后修改设置不改旧消费，手动明确方式优先。已保存消费的普通补充不重新套用新自动规则；用户可明确重新核对本消费日期的自动方式，并保留前后规则版本与修订。
- 一次付/分期资料齐全时，从同一消费生成本地预测账单，不增加消费、资金或本金；资料不足或期数不受支持时保留消费并列入未安排部分。没有确认、付款关联或逾期义务的本地预测可随原记录纠正而更新或留痕替换；已确认/有付款关联/逾期的原义务保持，需明确核对和调整。
- 信用卡リボ及循环贷款可按账户建立一个循环余额池，明确其中的期初本金、来源日期口径及未分配还款的归属；新增消费/循环借入进入同一逐期计划，固定贷款不并入。期初债务、来源本金与合同不能再次相加。归并前预览原计划的去向，确认/付款关联/逾期账单保留原ID和金额，仅撤回可替换的未来预测；同日原账单在总计划中只占一次月付款。新增本金、实际清偿及退款按实际日期改变计息余额，不提前使用尚未发生的借入。保存来源、规则及清偿快照，资料变化需重算或核对，未知金额不生成确定的备款结果。
- “仍需处理的未分配清偿”扣除显式义务分配及当前有效账户余额池登记的份额；余额池过期或还款事实变化时旧份额不再视为已归属，编辑器与计息仍使用原始未分配本金。账户期初日期或金额变化不会阻断实际记账：保留余额池原预测、提示核对/重算，用户重新接受期初定义后恢复自动更新。
- 信用卡待处理周期付款复用实际消费的规则版本选择与账期/金额计算：一次付、奖金付、分期按实际资金扣款账户和扣款日进入预计现金时间线，超出范围的扣款不列出。リボ及自动リボ不产生独立扣款；非自动 ACCOUNT_RULE 按一次付。缺付款方式、规则或有效扣款账户时列出可操作原因。实际记账后由 CARD_ENTRY 账单接替，不重复备款；参考换算仍为估算，不代表真实结算。
- 信用卡总览与月账单按有效扣款日期汇总，修正平台日期后随之改变月份；原消费日期独立保留，同一消费可关联多期但不重复计消费。分别列待清偿本金、费用、已付待确认与仍需备款；未知拆分不填0，未安排消费与未分配期初本金不被已知账单合计隐藏。
- 备款先检查实际扣款账户当前资金，再列按该账户全部已知安排得到的基础/含预计收入情景；已扣款但清偿待确认的明确分配不再要求同一笔资金。其他账户资金不视为已转入，未分配的付款可从原实际记录继续核对。
- 总额度、分期子额度、リボ子额度及共享关系分开。平台已确认利用可能额可作为当前观测值；推算利用可能额标为预计，并按额度恢复规则计算。它不计入资金合计。
- 本地预计以用户核对的占用基准为起点，不能把欠款本金直接当作额度占用。明确选择交易日或账户入账日开始占用，以及付款日预计恢复、平台确认日预计恢复或逐笔实际恢复；只按本金的模型不覆盖费用占用等特殊条件，此类条件可仅记录平台值。
- 占用基准包含保存时已记录、截至基准日的相关事实，之后新增同日记录视为基准后变动；新增更早记录、基准事实金额/日期改变或删除时提示重新核对。未知本金或子额度归属保持未知，不用0替代。平台可用值保留观测时间，相关资料变化后仍保留当时值并提示核对。
- 总池、独立子上限、分期与リボ共用子池分别配置；跨账户共享池另有同币种上限与占用基准，成员额度不相加。预计可用同时受本账户总额、相应子池和跨账户共享池约束；成员配置改变后重新核对共享基准。
- 逐笔实际恢复只确认对应归还本金，可部分确认并作废留痕；实际确认替代该付款的规则推算，不能再按规则重复恢复全额。确认依据中的本金、日期或相关分配改变时标为待核对。循环贷款仅计算明确归属循环合同的本金，固定贷款不占用循环额度。
- 还款日或締め日填写31而月份不足31时，默认当月最后一天，并在规则预览说明；日期归属与利息端点不得因此自动推定。
- 休息日顺延只有配置相应营业日历才自动计算；第一版支持用户输入本期实际扣款日。日本/中国节假日不硬编码成全平台规则。
- 支払い変更按具体账期、变更类型保存日期/时间，可另设重复规则生成候选；本期确认值优先，不能只保存每月一个固定日期。
- 机构规则、金融到期时间保留明确时区，默认日本账户使用 Asia/Tokyo、中国借款账户使用 Asia/Shanghai，均可修改。交易预算按保存的当地发生日期归属；手机旅行换时区不自动移动历史消费月份。

### 1.3 信息优先级与变更

- 金额优先级：用户确认的实际付款/结算事实 → 用户确认的平台账单/计划 → 当前生效规则预测 → 未确认的情景估算。实际到账用于资金变化，账单仍表示剩余义务，二者不能把同一笔付款再计一次。
- 同时保留预计与实际值、来源、确认状态和时间，不用实际值直接抹掉原预测。
- 已确认账单与预测不同：展示本金、费用、合计、账期、日期差异；用户可采用实际值，但不自动改原消费、规则或所有未来月份。
- 规则改动采用带生效日的版本，保留旧版本；预览受影响的未来计划后保存。默认不改已确认历史，本期已确认账单若要改需用户明确进入该期调整。
- 分期/リボ变更试算比较原方案和新方案：本期减少、后续逐期压力、总费用增量、截止、付款账户缺口是否解决。实际办理后另记“已办理”，不会提交金融操作或仅因试算就覆盖正式计划。
- 追溯记录办理时，生效日当天的已确认清偿按变更前处理，之后已关联原义务的清偿须明确保留原账单或转入新期次；允许本金、利息、费用分别拆分，各项合计必须与原值一致。先按生效日重建待转本金，再按真实后续清偿日期计算，不能把已经实付的本金或资金再扣一次。原确认账单保留金额，义务转移、清偿分配修订与新计划同事务保存；仍保留的旧义务即使当前已付清，也不能因入口失活而在删除付款后消失。
- 借入增加负债和资金，不算收入；还本金不算消费；利息及明确费用在实际扣收/支付时计支出。预扣费用和同一次还款内费用不能重复扣余额。
- 直接跨币种还款保留源币实付、目标币平台实收、目标本金/费用和确认状态。清偿未确认时源账户实际付款仍可记录，目标债务的已确认减少额单列，不提前假定结清。
- 金融 UI 全屏流程：规则（含试算）、借入/期初合同、还款、预测/手填计划、余额池、额度/共享额度配置及已办理安排重核为填写 → 预览，保存是预览固定操作；方案调整、共同月付款、批量转换为填写 → 比较 → 记录已办理结果。返回先退一步，填写页关闭保留草稿，确认勾选和预览不持久恢复；事实刷新重新审阅。键盘避让固定操作，短选择器仍为原主题菜单/弹层。全屏流程只显示返回、任务标题、关闭和步骤，不重复应用账本/设置页头。切换账本或进入设置前先关闭流程，草稿自动保留，返回原账本后续办或明确放弃；页面上的原切账本草稿保护保持原样。第三步指示使用“记录结果 / 結果を記録”，按钮保留完整办理语义。
- 规则差异与日期对齐比较由 `FinancialDisplayFacts` 无写入投影生成：规则完整字段递归比较含删除/空值/嵌套条件；金额按付款日期并集聚合同日已列行，账户或组成变化也显示。日期比较为同一紧凑表中的“日期｜原｜新｜差额”，差额符号在币种前（如 −¥6,600 / +¥3,400）；“—”表示该日无已列付款并配图例。两侧都有付款时，仅不同的付款账户、分配或本金/费用组成在该行下合为小注，相同信息不重复，新增/移除日期的逐笔信息留在完整依据。金额未变的账户/组成变化仍保留。规则值改空为“未填写 / 未入力”，键或嵌套段删除为“已移除 / 削除済み”；扣款账户、締め日和还款日沿用编辑器及缺项列表的同名字段。完整性和未知不折叠误导，原计算与历史归档不变；云端只用步骤快照，保留逐项完整前后值。计划摘要按同一展示投影列变化、已列范围与保留账期，再展开逐期依据；循环计划包含保留原账单且按身份去重。核对返回上一步或补齐账单后保留输入，不沿用旧预览与勾选；新建预测的当前安排确认也不随草稿恢复。
- 金融 UI 阶段 3：账单/期次将“金额已确认”与“已付款/部分清偿/待平台确认/已结清”分开，未清账单提供就地还款；全额已付待确认转向已有付款核对。沿用 `financialAccountSummary`/`billOutstanding` 的已清偿、待确认分配和剩余备款事实，不从实扣总额猜测目标币分配。
- `FinancialRepaymentEditor` 使用上述全屏流程，基本区为目标、付款账户、实扣、付款日期、清偿确认和分配摘要。展开区为费用/组成与跨币种、已有付款及先前转账、多目标、类型/备注；编辑既有记录自动显示完整原输入。新旧草稿兼容，展开状态持久保存，预览和平台确认不持久恢复。
- 从账单预选目标与扣款账户，同币种且已知待付时建议扣除明确待确认分配后的金额并标注来源；未知/失效预测不预填。合并费用中计算依据单列的追加费用计为平台费用、其余计为利息（无依据时平台费用为 0）；单目标未手填利息时按「实收（未填则同币种实扣减付款端费用）− 本金 − 平台费用」自动更新，手填后不覆盖；实收和付款端费用不因同币种相等而假定。单目标从唯一组成生成分配；原记录存在独立分配或多目标时完整保留。同币种实扣偏离已知建议时清空单目标本金并展开核对，回到建议值恢复本金和建议利息/费用；无建议时输入实扣不自动展开或推算本金，不按比例计算。
- 本机预览先显示付款账户、实扣、清偿状态、余额变化及账单/合同待付变化，再保留计划影响和完整资料。保存继续使用 `previewRepayment` / `commitFinancialLedger`。云端 `financialRepayment.save` / `.confirm` 从各步骤前后快照按相同顺序展示，schema、事实确认和原子事务不变，不新增金融对象跳转。

### 1.4 金额与验算

- 实际货币金额按最小单位存储：JPY整数，CNY/USD到分；汇率、利率、数量与中间计算使用十进制定点/任意精度类型，避免二进制浮点累计误差。
- 费用的取整方向、取整时点、逐日或账期合计后取整、尾差分配均属于用户规则。比例互请的金额尾差默认归最后一位参与者，界面可改，合计必须与整单一致。
- 每期可展开计算依据：计费区间、适用本金/余额、费率、天数/年天数、取整、当期本金/费用/总额、期后债务与利用可能额状态。
- 用用户自愿提供的脱敏账单逐期验证；无需为设计提供卡号或登录信息。不为“对得上”自动添加容差或反推隐藏费率。
- 精确匹配要求按账户币种取整后的实际金额一致；取整/日期/汇率差異逐项提示并由用户确认。

### 1.5 参考汇率

- 首版采用 Frankfurter v2 的 ECB 固定来源（`/v2/providers/ecb/rate/...`），不混用默认合成汇率；保留 API 与具体来源、汇率所属日期和获取时间。接口依据见 [Frankfurter v2 官方文档](https://frankfurter.dev/)。覆盖 JPY/CNY/USD，人民币使用 CNY，不默认为 CNH。
- 开启自动参考汇率后，当天首次需要时查询并缓存；常规使用不持续请求，支持手动刷新。只发送币种、日期等查询参数，不发送账户名称、余额、流水或购买内容。
- 非更新日、服务失败、无网络时显示最后可用汇率及日期；可手填汇率或实际金额。不把过期缓存标成当日新汇率。
- 参考汇率只估算未确认金额及当前资产价值；历史交易保存自己的换算值，真实手续费和实扣实收优先。服务不是实时成交价或发卡行结算规则。
- 已有记录后的账本本位币迁移第一版不自动提供：本位币设置保留只读说明，用户可创建另一独立账本。后续若实现迁移需专门方案与预览，不静默重算旧账。

### 1.6 记账默认值、转账及保存确认（2026-10-31）

- `BookGraph.savedRevisions` 只投影 revision 的 eventId/timestamp，在同一 Room 快照构造 `BookSnapshot.eventSaveTimes`；按 max(timestamp)、createdAt 排序，删除记录不参与记忆，不新增数据库字段。新建收支按 kind 记忆账户，转账记忆两端，显式账户参数优先；不可用账户回退且两端不同。
- 信用卡可作为转出账户，贷款不可；转入仍须资金账户。`prepareTransfer` 的 CREDIT source posting 为正数，含 INCLUDED_FROM 手续费的 source 总额作为账单本金；本金不计消费。复用 `cardPayment`、`cardRuleChecked`、提交时规则校验和 `refreshCardEntryPrediction`，金融预测/手动来源、未安排欠款及池刷新纳入信用卡转账。额度和对账已有 posting 方向口径，现金时间线只计资金端及实际扣款账户的账单，不再次扣除信用卡本金。
- 新建信用卡支出/转账按卡记住最近保存 choice，INSTALLMENT 带期数，DEFERRED 不带月份/费用；编辑不重套记忆。信用卡对账漏记的转出行也可选择转账。
- `saveEntry` 统一构建 `previewEntry`，复用其 AccountBalanceChange：非 debt 且 after < 0 且 after < before 时弹出确认；确认后普通记录提交同一份预览，需要影响审核的仍进入审核。提交时快照或规则变化则重新预览并重新检查负余额，不重复生成交易。
- 新建/编辑/周期/退款及 tab 切换在附件初始化之后记录内存基线。未选分类的非转账，或仅改分类/自动商户的草稿，离开时直接放弃；恢复草稿不建立基线。切换 tab 保留 date/note/mediaSession/附件和返回目标。基线不持久化，`merchantLocated` 仅为兼容默认 false 的草稿 JSON 字段，无 schema 迁移。
- 定位以 repository clock 的今天为界，非今天不请求/展示当前候选，也不接受自动商户回填；改日期清除自动定位内容，手动内容保留。商户联想和搜索使用 NFKC + 不区分大小写，精确匹配自动关联启用商户。

## 2. 正式文件协议


### 1.7 周期规则固定内容与记账模板（2026-11-01）

- `RecurrenceEntity` 新增 merchant/merchantId/note/cardPaymentChoice/cardPaymentPeriods；`fixedCardPayment` 统一校验：非信用卡清空，不接受 DEFERRED，INSTALLMENT 须期数>0。`occurrenceDraft` 生成 date=scheduledDate、`merchantManuallyEdited=true` 的草稿；规则没设付款方式时用 `withRememberedCardPayment`。
- 一键确认用 `AppViewModel.occurrenceConfirmation`：`previewEntry` → `commitEntryReview(clearDraft=false)`，不动用户草稿；提交时快照变化返回 null，则重新预览并标记 refreshed；负余额沿用 `negativeBalanceChanges`。「修改后再记」用同一草稿进入原表单（`startOccurrence`）。
- `entry_templates`（book/account/category/activity 外键）。`validateTemplate` 和记账一样检查分类启用与类型、`entryAccounts(kind)`、币种、商户和活动；`templateIssue` 返回失效原因，`templateDraft` 拒绝失效模板。`startTemplate` 打开预填表单并建立基线，`amountFocusSession` 只聚焦一次金额框。分类合并在 `previewCategoryOperation` 中迁移模板，活动删除清空 activityId，账户/分类删除时模板算作引用。
### 1.8 新商户记账位置与地图选点（2026-11-01）

- `EntryDraft.capturedPlace`（纬度/经度/精度）：`EntryLocation` 定位成功且为今天的新建支出时写入；`changeEntry` 在日期非今天或非支出时清空；`hasManualInput` 忽略它。
- `placeForNewEntry`：新建、支出、`merchantId==null`、商户非空、日期为今天且有暂存定位时，`PreparedLedgerChange.eventPlace` 在同一事务写入 `event_places`。保存时关联了已保存商户则删除该记录的位置；永久清理沿用级联表清理。
- `recordedPlaces(name)`：未关联商户且商户文字（trim）相同的支出，按日期从新到旧，以簇首点100米内贪心合并；坐标取精度最好的点。`saveMerchantWithLocations` 在一个事务里保存商户和地点；新建商户时删除所有同名未关联支出的位置。距离统一用 `distanceMeters`（haversine）。
- `PlacePicker`：`AndroidView(MapView)`，转发生命周期；中心图钉、半径圈为 Compose 叠加层（像素半径 = 米 / `getMetersPerPixelAtLatitude`），相机停下回调中心坐标；MapView 在按下时请求父级不拦截，防止外层滚动抢走拖动。`applyPlaceTheme` 在 Liberty 样式加载后按图层 id 重设颜色、隐藏 3D 建筑和道路编号、文字只用 `name`。`YohakuApplication` 初始化 MapLibre，用 OkHttp 拦截器设置专用 User-Agent。


- 统一 UTF-8 JSON，首版版本号1；不同用途使用不同 `kind`。正式协议与 HTML 示例区分，不把示例账本/账户ID当真实ID。
- 货币采用 `{ "currency": "JPY", "amount": "15230" }` 这样的明确结构，金额为十进制字符串；CNY/USD规范为两位小数。交易资金方向单列，实际金额通常为正数。
- 数量、单价、汇率也使用十进制字符串。无法确定的字段为 `null` 或缺省，不能把未知变成0；非法金额、币种、日期等在预览前给出具体行/字段错误。
- 使用稳定 UUID 关联账本、账户、记账、小票、文件批次和图片。名字仅供显示，不能用“日常生活”“PayPay”猜关联。
- **导入标识说明**（当前账本ID、账户ID/币种/名称、协议版本）由应用在创建云端流水任务时自动附带，不单独导出；它是格式辅助文件，不是账本备份或同步。
- 记录消费日期/当地日期；有明确时刻时另保存带偏移的ISO时间与时区。日期与金额不从摘要臆测。
- 首版按文件整体校验与预览、整体确认保存；拒绝文件时不写入半份数据。兼容的可选未知字段可以忽略，有冲突的版本明确拒绝。

### 2.2 银行/信用卡核对文件

类型：`kind: yohaku.statement`。

文件字段：`version`、`file_id`、`book_id`、`account_id`、`account_currency`、区间 `from/to`、`complete`、来源说明与转换待确认项 `issues`、`rows`。

每行字段：

- `row_id`：转换文件内唯一；有银行原始流水号/来源行号则保留。
- `date`、`direction: in/out`、`settlement`：账户实际入账金额/币种。
- `summary`：原始摘要，允许保留日文原名；转换后的辅助说明另存。
- 可选 `original`：原消费金额/币种；`occurred_date`：明确提供的原购买日期；`posted_date`：明确提供的入账日期。基准匹配日期字段语义在文件中明确，不用两者自动替换。
- 可选 `fees`、`exchange_rate`、来源页/行引用 `source_ref`、转账/还款事件辅助标记。辅助标记只提供候选，不直接绑定或新增正式记账。
- 本期账单本金/费用/合计、还款日期可作为独立 `statement_info` 补充资料；用户确认后进入账单组成，不因导入覆盖计划。

处理流程：标识与币种检查 → 预览区间/完整程度/笔数/汇总/疑点 → 保存独立资料 → 逐笔核对 → 人工处理差异。

- 严格以同账本、同账户、同方向的账户实际入账金额和匹配日期核对，笔数逐一占用；不因原币相同或参考汇率接近而自动完全匹配。
- 只导入转账/还款一端，另一端未核对不算漏记。两端可有不同币种、金额和真实日期，关联同一事件。
- 重复文件由文件标识与内容指纹识别，不重复创建核对任务。区间重叠单列提示，可更新对应核对批次或独立保存资料；不按“同日同额”去重真实多笔交易。
- 完整原文件保留在该账本的核对资料中。删除该资料仅移除资料/核对关联，不删手动账目。
- 补记先选消费、收入、转账、还款或原消费退款，再填写并保存。预计结算确认必须单独预览原记录变化；仅确认差异显示差异状态。

### 2.3 小票上传包与商品回填

上传ZIP（仅作为云端任务的输入，应用不提供本地导出）：`manifest.json` 和按小票ID组织的多张图片。清单类型 `yohaku.receipt-bundle`，含 `bundle_id`、版本、账本/记账/小票/图片ID、图片顺序/路径/校验值、原记录日期/商户/原币金额及账户实际金额、打包时的记录与小票修订号。

- 只打包选中且未整理的小票，不默认携带普通附件或整本账。提交云端后标为「已交云端 · 待回填」，不意味着已识别。
- 输出已保存的小票图片字节，打包时不再压缩或改写。批量体积过大时分包并保持同一批次关联，避免读取全部图片到内存。

回填JSON：`kind: yohaku.receipt-items`、`version`、`bundle_id`、`book_id`、`records`。每项有 `record_id`、`receipt_id`、打包修订号、币种、来源图片ID和 `items`。

商品保留稳定 `item_id`、名称、数量、单位、单价、行金额、来源图片引用与不确定字段/说明。数量允许0.5等小数；无法辨认的信息待补，不强行猜测。

- 可单列小票税费、折扣、运费和小票合计，说明已包含于商品行还是另列；不得同时加两次。商品金额与原消费币种比较，和信用卡换算后的金额分开。
- 显示商品已知小计、税费/折扣/其他调整和小票合计；缺明细时标为不完整。合计不同可以保存并提示待检查，但不修改交易金额。
- 导入只更新原小票商品。目标不存在、账本不一致或关联图片不符时提示，不自动建立记账。
- 原记录或小票在打包后发生变化时预览指出变化；旧结果不默默覆盖新增图片或手工编辑。已回填再次导入必须预览并确认替换，不重复追加。
- 回填保存后，只要当前图片都已被结果覆盖即转为已整理；明细不完整、行金额未知或有疑点不影响整理状态，只在已整理卡片标“明细待确认”并在详情中提示。图片有新增尚未整理部分时仍保留待整理状态，原已保存商品不删除。正式应用不做OCR，也不自动上传；只有用户在小票工作台明确选择“交给云端整理”时才上传所选小票图片ZIP（见3.2）。商品明细可领取云端回填、通过办理命令 receipt.items.save 回填/编辑，也可在本机首次手工录入；不提供手动选结果文件导入。

## 3. 数据管理与本地存储

### 3.1 编辑、删除、恢复

- 已保存记录直接编辑原ID，保存修订号与必要修改前后值。首版提供简洁“修改记录”查看，不建设复杂审计后台。
- 普通删除进入回收站，保留30天，删除后立即退出正常统计并取消对应未来提醒。30天内恢复原ID、附件与关联，不变成第二笔。
- 删除前展示余额、预算、活动/互请、关联退款/费用/核对/计划的影响。有必要关联的原消费及退款、转账两端等按一组处理；不能只删转账的一端。确认回收后替换详情路由为流水，返回栈保留详情之前的页面，不再回到已回收记录。
- 独立实际还款、已确认账单和历史付款不会因删除一笔消费被连带抹掉；依赖该消费的预测与核对标为待重新确认。
- 恢复后重新计算余额和统计、重新检查核对与计划有效性；旧手工差异关联不盲目恢复为完全匹配。
- 回收站显示到期时间，手动永久删除/清空需确认；到期清理移除最后引用的附件。明确这是应用内恢复，不是外部备份。

#### 3.1.1 账户、分类、商户、活动、账本

- **账户**：优先停用，历史保留，日常选择隐藏。停用不代表债务结清、不取消尚未完成的重要安排；仍有欠款或付款时显示说明。只有无记录/计划/核对引用的空账户可以直接删除，不制造余额调整来消除数据。
- **分类**：优先归档（一级、二级均可），归档后从日常选择隐藏、在分类管理的「已归档」区可取消归档，已有记录仍可查看；删除被使用的分类需明确转移记录到另一节点。改父级先预览历史分类汇总/预算影响，仍最多两级。不能悄悄把已用分类改成未分类。
- **分类图标**：`categories.icon` 可空，存 Tabler id。Room v32 / `MIGRATION_31_32` 按名称一次性回填，二级只在推荐与父级不同时写入。显示解析：自身有效图标 → 父级 → `category`，目录里不存在的 id 视为空。目录由 `android/tools/build-category-icons.py` 从固定版本 Tabler Icons 3.49.0 生成 `domain/category/CategoryIconCatalog.kt`（每组一个字符串常量、懒解析）和设计稿 JS。`saveCategory(icon=Auto)` 新建时按名称推荐、编辑时保留；`Set(id|null)` 显式写入。CSV 新建分类走 Auto。
- **商户/朋友**：可改资料或停用；原交易商户原文、地点和活动参与者历史保留。管理名称与原始购买摘要分开。
- **活动**：结束/取消保留历史消费和互请，释放明确未用预留。删除活动需明确消费改为日常后的预算归属影响，不能删除活动时暗删消费或把互请累计到其他活动。
- **账本**：支持重命名/归档；归档移出普通切换列表，数据和未完付款提醒保留账本标识。整本删除进入回收站30天并取消该账本提醒；确认显示账户/记录/附件范围，不联动其他账本。恢复后重建安排。自动删除到期数据的行为在回收站说明。
- 使用全局唯一ID和账本ID约束防止跨账本关联，但储存不必按账本拆成多个物理数据库；每个查询、写入和外键关系遵循逻辑隔离。

#### 3.1.2 存储、附件和草稿

- 数据存在应用私有的本地Room/SQLite库；一次保存的账目、资金变动、费用和关联在同一事务内完成，失败不留下半筆。
- 核对外部流水、小票商品与正式账目是不同数据表/对象；核对资料永远不能因导入变成正式记录。
- 表单附件与小票选择入口使用 `ACTION_GET_CONTENT` + `CATEGORY_OPENABLE` + `EXTRA_ALLOW_MULTIPLE=true`，分别为 `*/*` / `image/*`，每次经 `Intent.createChooser` 打开应用选择窗口；解析 clipData 或单个 data，立即复制临时授权 URI。小票拍照由 Activity 级 `LocalReceiptCamera` 打开 `ScanFlow` 应用内相机，权限与不可用状态由相机页处理。待处理账本、`ReceiptTarget.Draft(session, replaceFileId?)` / `Record(eventId)`、来源路径、主题语言和表单保存选项保存在 saved state；扫描页同时恢复临时照片和确认/调整状态，重建后结果仍交给原媒体会话或记录。结果经 FileProvider 的 `receipt-capture/` 路径交给 `importFiles` / `importRecordReceipts`，导入后清理输出目录；FileProvider 继续服务附件、导出和扫描输出。云端分析台选择器保持不变。
- `scanAutoCapture` 默认 false、`scanAutoProcess` 默认 true，持久化并进入完整备份。自动处理关闭时相机原图直出（`processed=false`），处理结果（`processed=true`）与原图都照常按「原样保存」开关入库；「处理这张」以 `EXISTING_IMAGE` 借用图片，始终进入确认/调整页。结果在同一导入事务内暂存为新文件，并在草稿 `receiptFileIds` 原位置替换旧 ID；入库失败保留旧图，旧文件沿用现有暂存/引用清理规则，编辑已存记录保存时生成新小票修订。扫描状态并入 busy，期间不可变更其他媒体或提交表单。
- 导入时可按全局“照片保存方式”设置优化（默认节省空间），也可在本次表单切换原样保存；在记录详情页为没有小票的记录补加小票时直接使用全局设置。节省空间模式下，所有 MIME 为 `image/*` 的图片都重新编码，不按截图、PNG、GIF 等格式豁免：小票短边 ≤ 2000px、JPEG 质量90；图片附件长边 ≤ 2560px、JPEG 质量85；等比缩小且不放大，EXIF 方向烘焙到像素，输出 sRGB SDR，去掉 gainmap，透明区域合成白底，不保留 EXIF/XMP、GPS、机型或动态视频。优化后 MIME 为 `image/jpeg`、扩展名 `.jpg`；原样保存及非图片保持字节不变。源文件完整读入后若格式不支持或损坏而无法解码，原样保存并提示数量；读取、写入或数据库失败不走回退。
- 在 `mediaWrites` 锁内流式写临时文件并计算源字节大小/SHA，保持严格小于100,000,000字节；ImageDecoder 在头部回调使用 `setTargetSize` 直接解到目标尺寸、软件分配器和 sRGB。编码输出重新计算实际 size/checksum，再由每文件独立事务写 blob/草稿引用；失败清理临时和未提交文件，取消正常传播。无去重、历史重写或数据库迁移。
- 记录详情页补小票：仅在记录未删除且当前没有小票图片时显示选图（`image/*` 多选）和拍照入口，不显示保存方式开关而直接读全局设置。`importRecordReceipts` 在 `mediaWrites` 锁内逐张写文件（每张独立失败），再在一个事务内写入成功文件的 blob 和小票新修订，事务前后都确认仍无小票图片；事务失败时删除已写文件。不新增事件修订。
- 全局 DataStore `photo_save_original` 默认 false，备份偏好 `photoSaveOriginal` 缺省 false；表单按 mediaSession 保留本次选项，批次开始固定选项，切换仅影响后续导入。串行处理，每文件独立失败，进度为当前序号/总数，结束 notice 汇总成功数、优化失败原样保存数、失败数及首个原因。
- 上传打包与备份使用已保存的图片字节，打包时不再转码；ZIP 中 `sha256` / `size_bytes` 是实际入包字节的校验值与大小，MIME 也对应保存后的文件。
- 图片缩略图长边 ≤ 512px，大图预览长边 ≤ 4096px，ImageDecoder 精确等比缩小、不放大，按 EXIF 方向显示；预览不改写已保存字节。音频仅本地播放，其他格式临时授予外部应用只读访问。
- 编辑时移除附件先进入待删除状态，取消恢复；同一文件仍有引用时不删物理文件。缺文件/打不开时显示真实状态，不伪装为空或静默忽略。
- 草稿本地自动保存，按账本归属；返回、进程回收或重新打开应用后可继续。有手动输入的草稿切换账本时可保留/放弃/继续编辑；清草稿不删除已保存记录。
- 账本切换只保留顶部当前账本按钮、设置→独立账本管理及其下级管理页。收支、转账、退款表单不再显示账本/主题工具行；顶部账本按钮在记账中打开切换弹层，其余正常页面进入账本页，金融草稿保护继续沿用。主题只在设置→外观主题切换；离开有手动输入的记账时可保留或放弃草稿；未选分类的非转账草稿，或相对打开基线仅改分类/自动定位商户的草稿，直接放弃并离开。恢复的草稿没有基线，已选分类或转账时仍提示。顶部不再提供语言按钮。首次设置的顶部设置按钮打开同时含主题和语言的设置弹层，切换保留未保存设置输入。
- 设置页依次为「外观与语言」「账本与分类」「提醒与汇率」「小票、流水与云端」「数据」「其他」。外观主题行显示当前主题名，进入 `appearance` 二级页选择主题（缩略预览与选中标记保留）；语言切换位于同组。「小票、流水与云端」依次进入 `receipts`、`statements`、`cloud`；「数据」含「照片保存方式」、「备份与恢复」（`backup`）与「从 CSV 导入」（`csv-import`）；「其他」只含回收站。「账本与分类」还提供「商户与地点」（`merchants`）入口，分析页原入口保留。
- 并列短操作使用 `YActionRow` 自适应排布：杂志/手账/小物分别沿用 8/10/12dp 间距，按钮保持各主题原有字形、边框和阴影；按自然宽度排列，空间不足时整项换行，主按钮占满所在行剩余宽度；确认弹层中并列的二选一（放弃 / 继续编辑等）都用本主题的次要按钮，不与无框链接混排。长文案或不同层级操作仍纵排。
- 金融草稿按账本、账户、表单种类和原编辑对象分别保存未完成文本、日期、选项和逐期输入；预计收入及到账草稿归属账本，目标资金账户仍可编辑。金融账户总览与预计收入区提供继续入口，支持明确放弃；资料已改变或原目标不可用时保留草稿并提示核对。恢复输入不恢复过期计算预览、办理确认或期限外接受勾选，正式提交前重新预览。正式保存与对应草稿清除同一事务完成，过期拒绝或失败保留草稿，不能产生两笔实际账目。
- 正式应用升级采用数据库迁移，保留ID/关联/附件；迁移失败提示真实错误，不重建空数据库掩盖失败。
- 账本与首次设置资料的读取采用统一加载/成功/失败状态。失败页按当前可知主题和语言提供重新读取与可展开错误详情；保留最后成功读取的外观信息，不静默清空库或用默认设置覆盖损坏资料。重试只重新查询，问题仍存在时继续显示真实失败。
- 提供用户手动的本地完整备份/恢复（整份替换，不加密，不同步，不自动备份），不提供应用锁；云端分析交接（3.2）由用户主动提交；云端办理（3.3）自动附带账本结构，具体记录按用户选定范围附带，不做后台账本同步。明确关闭并排除Android应用数据云备份与可配置的数据迁移路径，不依赖一个manifest开关就声称控制了所有厂商迁移行为。正式验收检查实际配置。

### 3.2 云端分析交接

- 契约见`docs/android-cloud-handoff-package/`（API v1）。设置→云端分析交接台导入网页生成的连接配置JSON（粘贴或选文件），显示站点与设备ID后确认；两项令牌整体以Android Keystore AES-GCM加密存于`noBackupFilesDir`，不进Room、日志或URL。每次请求带`OAI-Sites-Authorization`与`Authorization`两个头，不跟随重定向；401暂停队列并提示重新连接。正式包只接受HTTPS源，可调试包另允许`10.0.2.2/127.0.0.1/localhost`明文供本地模拟服务。
- 小票：工作台所选未整理小票按已保存字节打包（目标95 MB分包，最终每包须<100 MB，单张超限拒绝提交）。流水：导入流水页唯一入口为选定目标账户与原始资料，并附当前账本`import-identifiers`；一个任务只对应一个账户，不提供手动选JSON导入。普通通用分析：任意文件，结果文本另存到用户所选目录，不套用导入器。`general` 类型另承载 `purpose=command|monthly-review` 的云端办理/评语。每个办理任务自动附带协议、能力清单和账本结构，并非只上传所选资料；普通办理可再附所选记录及源文件，月评初次另附月汇总而不附逐笔/源文件。此类结果进入方案校验、回答/评语或预览，不走普通通用分析文本另存。receipt/statement及purpose=analysis的原上传规则保持各自含义，不能把所有general都当成办理。
- 资料先复制到内部目录、记录大小/SHA-256与任务、Idempotency-Key及原始创建体，再由WorkManager串行上传；重试复用同一份字节和同一键，上传回包丢失先查任务文件。提交确认后才登记小票导出批次（`recordSavedReceiptExport`）。待补资料任务可补充文件后再次提交。
- 领取只选`ready`、非过期且`inputRevision`一致的结果，下载到临时文件核对大小与SHA-256后严格UTF-8解码，小票/流水再走原有`previewStatement`/`previewReceiptItems`预览，办理任务进入`CommandRepository.receive → preview`；保存时按任务锁定的账本/账户/批次校验。本地事务内同时写入业务资料、导入记录（站点+taskId+resultId+sha256）与imported回执；回执由WorkManager重试，绝不重新导入。实际保存失败才发failed，取消预览不发送。
- 前台打开交接台时按需轮询（30秒），无推送、无后台同步。网页工作台由系统浏览器打开。
- 云端工作台另提供 MCP Events：用户在 Work 建立持续订阅后，首次上传提交或补充资料提交可触发助手处理；此为服务端到 Work 的事件通知，不是手机推送。协议、投递重试边界与接入步骤见 `docs/mcp-implementation-handoff-package/reference/README.md`。手机仍需领取、预览并确认结果。

#### 预览、确认与一致性

适配器执行normalize→前提校验→共用Repository操作→StepEffect；false/null提交结果转为整批失败。UI和命令共享记账默认值、金融输入/候选日期、实例支付草稿、预计收入到账、流水补记及商品校验；UI无直接DAO写入。适配器新增/扩展须遵守[检查表](plans/cloud-command-adapter-checklist.md)。

执行器统一mediaWrites→主库外层withTransaction。试运行在事务里顺序写入、计算派生影响，抛内部信号后在最外层事务外捕获回滚；不复制数据库，不写偏好/文件或启动选择器。ExecutionContext固定日期、时区、366天预测区间与事务外参考报价。正式确认在新事务重跑同一归一化方案并比较结构化模型，相关事实改变则回滚并要求重新预览；不冻结UUID，不以整本最新digest粗粒度失效，不重新扩大选择器集合。

比较包含每步固定对象及识别事实、完整业务前后绝对值、余额/额度/预算风险、逐期日期/本金/费用/付款账户/规则及确认状态、资金预测、关系和默认值保存顺序。新ID按步骤/输出角色/业务键规范化，嵌套JSON按结构映射完整标识，不替换用户文字。纯审计时刻忽略，退款/还款revision与额度组等业务依据保留；日期/时区/恢复或办理期限越界另使预览失效。净变化为零也保留中间步骤。未知/估算和统计口径可见，不能变成零或已确认。

INFORMATION不勾选；RISK仅沿用已有独立风险策略（如实际资金账户负余额加重），普通金额变化不新增勾选；USER_FACT由手机生成具体账户/金额/日期声明，只能用户亲自勾选，绑定步骤及条件digest，变化后失效。助手不能传平台确认/期限外受理布尔值、不能代勾或声称已办理银行业务。

确认提交时同一事务保存业务资料、执行日志、来源(站点/taskId/resultId/sha256)与plan_id去重、回执和后续效果队列。更换结果版本不能让同plan_id重复执行；取消/失败无部分业务写入。回答/月评在领取时保存并回执，月评imported仅表示评语已保存，不表示建议执行。回执重试不重执行业务。

#### 后续效果、交互与整批撤销

transactional一起提交或回滚；post-commit写DataStore/附件；interactive由手机用户继续补草稿、授权或选择导出目录。后两者不属于跨系统原子事务。command_effects持久状态PENDING/RUNNING/DONE/RETRY/WAITING支持离线启动恢复、重试和详情；失败不谎称已回滚正式账本。

偏好值及effectId凭据同次DataStore.edit，崩溃后不覆盖用户后来修改；附件核对本任务source-N的名称/路径归属/大小/SHA，固定文件身份及关联/所有权日志/DONE同事务；草稿写入和WAITING同事务且不能覆盖已有草稿。系统权限不由助手授予或自动撤回。导出先持久目录授权和固定目标身份，重启核验同一文件，目标被修改时要求用户检查后重试；备份副本把本次导出效果标DONE，防恢复后重做导出。内容是用户开始导出时的全库，不冒称预览冻结快照。

整批撤销仅从本机历史生成逆方案，继续preview→confirm流程；云端不能使用local.*。已有对象与关系恢复精确原值，本次新建且未变/无外部引用的行受限移除；v3包含原行、被替换关系、生成ID、完整冲突守卫，恢复记录revision与保存次序。旧v1/v2按其证据兼容，缺完整证据的旧执行不可撤销。撤销检查完整原始行及外键、逻辑ID、嵌套JSON/草稿引用；恢复已有行后按依赖移除新行，再检查外键和残留。任一冲突阻止整批，不部分恢复。UNDONE及撤销时间与独立逆方案同事务，原去重/审计永远保留。

全部后续步骤完成才可撤销；偏好恢复仍是排队的post-commit，附件只移除本方案新增关联而不物理删源文件。补完草稿、需要系统授权或已导出文件无自动逆操作，一步不可撤销即整份不可撤销，预览说明原因。

#### 月计划、月评与问答

预算页附近编辑每账本一份通用自然语言计划，book.monthlyPlan.save完整替换text（最多20000字符，保留空白/换行，空字符串清内容但不删行），共用保存函数，支持快照撤销。每次月评保留当时原计划；后续修改不改历史。月计划无生效月或定时更新，未来预算可设month，计划文字立即更新来表达未来意图；message须说明时间差。明确要求届时才改文字时，不冒称可安排延时执行。

提醒设置monthlyReview默认true，独立于重要事项enabled；关闭全部提醒须同时关闭两者。沿用ReminderCoordinator权限、提醒时刻、午夜重建、持久去重；每月1日提醒上月，未完成/归档/回收账本或已提交月份不提醒，不补发过期日。点击提醒预填月评提交页，历史可手动选已结束月份。用户核对才上传，无后台自动上传。

月汇总含收入/净消费、直接分类、继承预算执行、账户月初/月末变化、月计划与口径。退款回原消费月、已确认费用按自身日期，预算排除独立活动；账户按已确认入账日和自身币种，不跨币相加。历史月汇总是提交时已知事实，配套结构是提交时当前结构，不能混为月末审计或把计划当交易。月评message非空，steps可选；领取后保留首次成功评语和提交快照，不执行/拒绝/建议失败均不丢评语，不用新plan_id覆盖已保存月份。普通command的无步骤message/questions作为ANSWER保存并可回看，无执行按钮。

Room v38保留command_plans/command_effects/cloud_tasks.purpose，37→38增加monthly_plans/monthly_reviews；正式迁移保留旧数据。月评历史快照压缩并随完整备份保存；历史JSON不充当实时金融引用，真实账本外键仍约束删除。

### 3.4 手动完整备份 / 恢复（formatVersion=1）

- 设置「数据 / データ」→ `backup`；使用 `SettingsGroup/SettingsRow`、`YLead/Panel/YButton/YSheet` 和既有三主题字体/纸面/边框，中日文完整。首次设置提供恢复入口。SAF `ACTION_CREATE_DOCUMENT` 创建 `yohaku-backup-YYYYMMDD-HHmm.yohaku`（ZIP、MIME `application/octet-stream`），`ACTION_OPEN_DOCUMENT` 选择恢复文件。
- 目录：`manifest.json`、`database/yohaku.db`、`preferences.json`、`attachments/<原相对路径>`。清单字段：`format="yohaku.backup"`、`formatVersion=1`、`versionName`、`versionCode`、`schemaVersion`、`createdAt`（ISO UTC）、`books[{id,name,recordCount}]`（记录数含回收站，不含已物理清理的墓碑）、`attachmentCount`、`attachmentBytes`、`entries[{path,size,sha256}]`。`entries` 覆盖全部载荷文件，不含清单自身。
- 后台导出持有已有附件写入锁并进入 Room 事务，在同一一致视图中复制表结构、原 rowid、全部值与索引/触发器到独立 SQLite 文件，同时复制全部附件和偏好。选择事务逻辑快照是为了兼容 Android 10 的 SQLite，避免直接复制活跃 WAL 库，也不要求 `VACUUM INTO`。失败删除未完成的 SAF 目标，页面展示文件名/字节数或失败原因。
- 全库保存账本、账户、记录、分类、预算、金融资料、原 ID/关联、草稿、回收站、云端任务历史等。偏好保存自动汇率、汇率缓存、提醒设置/投递去重状态、定位开关、照片保存方式、当前账本和首次设置草稿；不保存设备派生的提醒调度计划。`filesDir/cloud`、Keystore 凭证、系统权限、WorkManager 数据库均不打包；本机云端凭证保持不变，缺失上传暂存沿既有「重新准备任务」失败路径处理。
- 在私有临时目录解压，拒绝绝对路径、`..`、重复/未知条目、清单缺失/不支持版本、逐文件大小或 SHA-256 不符。高于当前 schema 拒绝并提示先更新；低于或等于则在暂存副本上运行生产 Room 迁移/结构校验及 SQLite 完整性/外键检查。所有验证通过后显示创建时间、应用版本、账本和附件摘要。
- 用户明确确认整份替换（可先取消并导出，不自动备份）后，取消提醒、全部 WorkManager 工作并关闭 Room。启动非导出的 `:restore` 前台 Activity，终止原主进程并等待其退出，确保 DataStore、附件与数据库无旧句柄。替换前再次核验暂存及迁移副本；以同文件系统移动替换数据库（清除旧 WAL/SHM/journal）、附件及准备好的 DataStore 文件。
- `noBackupFilesDir/restore-journal` 保留旧文件及阶段标志，提交前失败回滚；回滚使用原始文件清单与原子移动，以便中断后继续恢复且不额外复制整套旧附件。主进程初始化前通过文件锁检查/恢复未提交替换，已提交仅清理旧件。WorkManager 改为此检查完成后手动初始化，防止默认 ContentProvider 提前启动旧任务。此内部事务回滚目录不是用户备份。完成后启动新的 MainActivity，再退出临时进程；应用按新数据重建提醒/后台任务并显示结果。
- Android `allowBackup=false` 与数据提取规则不变；不加密、不加密码、不同步、不定期提醒、不自动备份、不合并恢复、备份页面不承担 CSV 迁入（后者使用独立入口）。

### 3.5 CSV 迁入正式账目

- 与 `statement` / 银行流水核对独立：`domain/csv/CsvImport.kt` 负责通用解码、RFC 4180 解析、列/日期/金额与收支判断，`CsvImportRepository` 负责预览、重复索引和正式写入。不得把核对导入改为自动记账。
- BOM 决定编码；无 BOM 严格 UTF-8→Shift_JIS→GBK，也可手动选择。自动判断逗号/Tab/分号与表头，预览原文件前五行。日期支持年月日与 `- / .`，忽略时间；金额去 ¥/￥/逗号/空格，精度按目标币种检查，零值及解析错误须修正或跳过，不推测备注中的金额。类型取值逐项映射，收入退款保持普通收入。
- 仅本位币账户；账户列未对应使用必选目标账户。分类按（收支,原值）对应现有启用的两级分类或新建一级；空分类须指定默认分类。重复候选使用当前账本已有非回收记录的（日期,收支,币种金额,备注,商户）索引，文件内不更新此索引，因而相同行仍分别保存。
- 预览将每行解析结果、账户/分类、`historicalIncluded`、问题与跳过选择固定；提交事务内重新计算一次并比较，资料变化要求重新预览。按 `date <= account.openingDate` 自动标记历史已含，之后明确影响余额。
- 正式写入复用 `prepareEntry` / `writeChange`，生成完整 event、settlement、必要 posting、revision/createdAt；不清空用户草稿、不创建活动或周期关联。无预留/周期的普通收支不读取整账本快照；批次只在末尾按涉及账户刷新金融池派生，避免逐行重载快照。每50行更新进度，全批次、新分类与批次关联在同一 Room 事务中提交/回滚。
- Room v30 / `MIGRATION_29_30`：`csv_batches` 保存批次统计及撤销组 ID；`csv_batch_events` 关联原 event ID，随记录永久清理级联删除但保留批次历史；`csv_profiles` 以（bookId,表头签名）保存 JSON 对应设置。设置含列、日期格式、类型规则/取值映射、分类/默认分类、账户对应与备注商户开关；成功创建分类后记住实际新分类 ID，避免下一批重复建类。三表随完整数据库备份迁移。
- 撤销选中该批仍存活的记录，按既有删除语义带上关联退款，复用 `trashEntrySet` 一次写同一 deletionGroupId、撤销周期完成状态并使旧人工核对失效；既有回收站按组显示、校验并恢复原 ID（30 天）。批次/问题/恢复确认中的记录列表分页，防止长列表一次组成数千 UI 节点。

## 4. 开发与验收

### 4.1 技术选择

- 原生Android：Kotlin + Jetpack Compose；目标Android手机，建议minSdk29（Android10），构建时采用当前稳定工具与目标SDK，固定依赖版本。不是先把HTML包成正式WebView应用。
- 使用Compose基础布局/输入/手势和自定义绘制实现三套独立组件；保持可访问性语义、焦点和足够触控区域，不把整个界面画成不可读不可点击的一张图。
- 本地业务数据Room/SQLite；必要非金融偏好使用DataStore；金额/汇率/费用算法使用BigDecimal等十进制类型。
- 单安卓工程，内部按数据、计算、导入、主题、功能页面划分清晰边界；先不建立大量Gradle子模块、后台服务或服务器。
- 核心记账、账本、预算、分析、金融计划、核对、小票附件全部离线可用；只有参考汇率、用户主动发起的云端分析交接和地点编辑的地图底图（OpenFreeMap）需要网络，定位/通知/系统文件/外部打开按安卓能力启用。
- 本地重要提醒按既定提前天数，默认当地上午9点，可修改；日期安排按账户/规则时区换算。采用AlarmManager的适当时间窗口，后台整理用WorkManager，不依赖常驻进程，不把后台任务当精确秒级计时器。首版不新增临截止精确闹钟需求。
- 请求通知/位置权限只在用户启用相应功能时；记账位置使用前台权限，不追踪后台出行；拒绝后手动记账和应用内待办可用。重启、时区变化、记录修改后重建尚未完成的提醒；不会一次补发多条过期提醒。
- 以安装APK在用户手机测试，先直接交付签名一致的测试包；正式包与测试资料区分。无需先上应用商店；正式数据不得混入演示初始化。

### 4.3 有必要的验证

- 金融与统计使用少量有代表性的固定案例：一次付；分期首末尾差；本金定额/含费总额リボ；日计/月计与明确端点；费率生效/提前还款；借入净到账与预扣费；确认账单覆盖预测；跨月退款/外币退款200差异；换汇两端及已含费用；活动月预算排除；多人实际份额；同日同额多笔与转账两端核对。
- 数据验证：原ID编辑、软删/恢复、跨账本约束、进程重启、附件来源文件删除后的保留、数据库升级迁移。只做必要成功/失败场景，不穷举极少出现的边界。
- 视觉：三主题×中日文，固定可信示例与设计稿对照字体/位置/间距/图标/图表/弹窗；标准手机与320dp窄屏，较大系统字体、长商户/金额、软键盘和滚动；共享全宽日历同时只有一个。
- 通知和定位在真实安卓手机验证；权限拒绝、离线、正常重启和修改到期事项是必要场景。系统节电可能影响时间窗口，应用显示可检查的安排与权限状态，不宣称任何手机上绝无延迟。
- 第一版支持的金融算法必须按验证样例精确核对；不支持的机构特有算法明确用手动计划，不能把简化估算标成准确。
- 交付标准同时覆盖UI复刻、功能、金额、文件协议与本地数据。一个页面能打开或构建成功不足以代表功能完成。

### 金融 UI15/UI19 展示契约增量：办理历史、额度关系与时间

批量转换从「管理 → 办理与版本历史 → 指定批次」查看；循环还款计划的版本历史也能进入同一批次。总览/账单只保留发起转换，不再提供页底整组撤销。确认首段来自 `BatchArrangementArchive` 的办理前/后归档：办理时间、批次身份、原消费/计划名称、逐笔转入金额与合计、原一次付安排、目标循环计划、恢复安排及范围、实际资金/原消费/平台办理边界。取消不写入；确认继续调用 `undoBatchRevolving`，成功后历史保留。后续付款、安排或引用变化由原事务阻断，界面显示具体原因并提供「查看当前还款安排」。

总览、额度页、配置历史和预览依据配置显示关系：`TOTAL_ONLY` 显示分期与循环还款共用总额度；`SEPARATE_CAPS` 分列总/分期/循环上限并说明子额度仍受总额度约束；`SHARED_SUBPOOL` 分层显示总额度与其中共用子额度。未知/未配置不从计算容量推定独立额度。跨账户共享组限制及限制后本账户预计可用值另列，上限与预计可用值分开。计算、恢复规则和余额不变。

金融办理时间按操作规则及历史归档中的规则时区显示，中文为 `2026年11月4日 10:59 · Asia/Tokyo`，日文为 `2026年11月4日 10:59・Asia/Tokyo`。普通版本保存、草稿更新及核对保存标注「记录时间」。日期字段保持日期。显示与输入原值分离，未实际编辑时间时保留原 Instant 的秒/小数精度。新平台观测使用操作时的 UTC 偏移保存同一 Instant，预览与历史用该偏移；既有仅含 `Z` 的观测以 UTC 展示，不能恢复未保存的原地区时区。

中文主入口统一为「循环还款计划」「批量转为循环还款（リボ）」「本期付款方式变更截止」「核对当前还款安排」「已替换计划」「撤销这次批量转换记录」；结账日、奖金月付款、自动循环还款一并收口。同一计划字段 `paymentAccountId` 称「付款账户」，实际还款的 `sourceAccountId` 称「实际付款账户」，两者分别表示计划资金来源和已发生付款来源。`POOL`、协议字段、枚举和命令名不变。

批次历史与摘要复用金融主题组件：杂志编辑短注、手账边线账目、小物标签收纳格；短确认使用各主题弹层，管理目录保留四区选中态。手账数学负号统一为 U+2212；原手账字体把该字形画成连字符，独立的同字体负号子集修正其宽度与数学运算符对齐，不替换其他主题或数字字体。

云端 `financialBatchRevolving.undo` 从该批次历史归档生成同一只读恢复摘要，放入步骤自己的 `revolvingBatchArchive` 展示事实；不查询当前计划冒充办理前版本，不作为撤销事务输入。一次批量转换记录的撤销与「撤销整份云端方案」分别命名。额度和时间在 `CommandFinanceViews` / `CommandEffectViews` 同步，完整前后值、事实勾选、原子性与冲突检测保留；不新增金融对象跳转。

稳定标签：`finance-batch-history-{group}`、`finance-batch-open-{group}`、`finance-batch-undo-summary`、`batch-revolving-undo-confirm`、`finance-batch-undo-cancel`、`finance-batch-undo-blocked`、`finance-batch-current`、`finance-limit-relationship`、`finance-time-{semanticId}`。测试为 `FinancialBatchRevolvingFlowTest`、`CreditLimitFlowTest`、`FinancialDisplayFactsTest` 和 `CommandFlowTest` 的金融方法；数据事务回归继续使用 `CreditCardOptionsStorageTest` 与 `CommandFinanceExecutionTest`。

批次历史项只保留一个入口：未撤销时为“查看并撤销”，已撤销时为“查看”；确认撤销在详情内完成。摘要以办理时间和原消费名称标识批次，不展示内部 ID。原消费按原付款日、名称排序，恢复列表的目标循环计划固定置后。

额度关系中的各项上限只显示一次；预览中变化的上限只在差异区展示，未变化的上限仍在关系区显示，关系说明保留一句。不适用的额度字段不显示；关系切换导致旧上限被删除时，差异明确列出旧金额与“已移除”。

云端确认事实会规范化带 ID 的数组；批次摘要在最终展示边界应用同一业务排序，不能依赖序列化顺序。额度追加版本的差异基线取本步骤捕获的 `creditLimit.before.config`（或同一步的旧配置快照），不能把新增存储行的空 before 当成首次配置，也不能查询当前数据库补基线。
