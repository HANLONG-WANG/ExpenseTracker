# 一、产品边界

- 原需求：产品不管理数字资产，主要资产范围仅为现金和银行存款。
  实际行为：银行账户创建页接受 `BTC` 作为账户币种并成功生成 `0 BTC` 账户；该账户随后又无法用于合理金额的转账。应用既突破了“不管理数字资产”的产品边界，也产生了不可正常使用的账户。
- 原需求：Android 系统集成应支持可实际使用的桌面小组件。
  实际行为：系统小组件选择器虽列出需求中的 9 种小组件，但配置“Quick entry”并保存后，桌面只出现英文错误占位 `Configure this widget again`，无法显示或执行快速记账。

# 三、账户、银行卡和多币种

- 原需求：账户页应能展示和管理现金、银行、信用及贷款账户，并支持后续交易与余额功能。
  实际行为：打开应用后进入“账户”页，页面无法读取任何账户数据，显示 `REFERENCE_INVALID_FIELD` 和“重试”按钮。账户列表及其依赖功能当前不可用。
- 原需求：账户币种只支持有效法定货币，不支持加密货币。
  实际行为：创建银行账户时可输入并成功创建币种为 `BTC` 的银行账户，账户列表显示 `0 BTC`，与“不支持加密货币”直接冲突。
- 原需求：账户币种和交易金额规则应保持一致，系统不应产生不可用账户。
  实际行为：已创建的 BTC 账户可被选为转账目标，但目标金额输入 `0.0001` 或 `1` 均提示“请检查此字段”，无法保存转账；系统接受了禁止的币种账户，却不能处理该账户的任何合理金额。
- 原需求：允许创建任意多个银行账户，银行账户可以没有实体卡或关联多张实体卡。
  实际行为：保存银行账户后账户实际已创建，但页面仍停留在可再次保存的账户设置表单，按钮仅从“正在保存”恢复为“保存”，没有成功提示或返回账户列表。该反馈使用户误以为保存失败并可造成重复账户；测试中因此连续创建了 BTC、USD、JPY 三个银行账户。
- 原需求：银行账户可关联多张实体卡，卡片可独立管理。
  实际行为：实体卡可以成功创建并关联，但保存成功后同样不退出表单、无成功提示，用户必须连续返回才看到新卡，存在重复提交和重复卡片风险。
- 原需求：有历史或引用的账户只能归档，归档操作应给用户明确结果。
  实际行为：账户归档实际成功，但点击“归档账户”后页面无任何变化或成功提示；只有返回账户列表后才能发现状态已改变。
- 原需求：从未使用的空账户可以永久删除，删除后界面状态应保持一致。
  实际行为：空银行账户可被永久删除，但删除后仍停留在已不存在账户的页面；首次返回出现仅有“重试”的错误态，再次返回才回到账户列表。删除后的路由/状态未正确清理。

# 二十四、无障碍和质量要求

- 原需求：正式支持系统字体缩放和大字体布局。
  实际行为：账户流水表头“日期（YYYY-MM-DD）”在当前 Android 模拟器显示配置下被不自然地拆成多行，右括号 `)` 单独占一行，表格可读性和版面适配不符合大字体布局要求。
- 原需求：大字体布局下所有表单内容和主要操作仍应可达。
  实际行为：分类设置页内容超过一屏，但页面无法滚动；“分类颜色”和“保存”位于屏幕下方不可达，导致分类无法创建。首次安装又没有默认分类，因此该布局问题会阻断所有普通收入/支出记账。
- 原需求：图表必须同时提供可读数据表，数据表在支持的显示尺寸下应完整可读。
  实际行为：即使 Android 字体与显示缩放已调到最小，展开“项目现金流数据表”后最右侧列仍被屏幕右边缘裁切，只能看到表头末尾的单个字符和行值开头的 `-`，且未出现明确的横向滚动提示，无法完整读取该列。

# 四、交易系统

- 原需求：首次安装没有默认分类，但用户可以创建、定制并保存收入/支出分类。
  实际行为：分类设置表单在当前显示/字体配置下不可滚动，底部“保存”按钮不可达，用户无法创建首个分类；这直接阻断普通交易录入。
- 原需求：在可达的分类表单中，合法的名称、统计性质、预设、图标和颜色应能保存为分类。
  实际行为：将 Android 字体与显示缩放调到最小后“保存”可达；填写“餐饮”、日常消费、默认账户和颜色后点击保存，页面无加载、成功或错误反馈，返回并切换收入/支出后分类仍暂时不可见；重新启动应用后该分类才出现，说明数据实际写入但页面反馈和刷新失效，用户容易重复创建。
- 原需求：普通交易录入应以用户可理解的字段组织账户、商户、发生时间、项目、位置、备注、附件和统计设置。
  实际行为：支出录入页在“项目（可选）”与位置获取卡片之间出现孤立的一级文案“互请”，与当前位置/备注区域没有可理解的关系，疑似错误分组标题。位置持续显示“正在获取位置…”时保存仍能在约 1 秒内完成，未阻塞记账。

# 二、核心账务模型

- 原需求：用户界面不出现“借方、贷方、会计科目”等专业术语，底层平衡记账应被隐藏。
  实际行为：转账详情的“账户影响”直接显示 `银行二:debit:2000 JPY` 和 `dddd:credit:2000 JPY`，把内部 debit/credit 会计方向原样暴露给用户。

# 十一、项目

- 原需求：项目支持开始和结束日期，项目表单应对日期关系进行合理校验。
  实际行为：可输入早于开始日期的结束日期；保存按钮仍显示为可用，但点击后既不保存，也不显示结束日期必须晚于开始日期等校验信息，用户无法判断失败原因。
- 原需求：项目列表、详情概览、交易和现金流页面之间应具有符合 Android 习惯的返回导航。
  实际行为：从项目现金流页连续使用系统返回键时依次退到交易、概览后，没有返回项目列表，而是进入字段已清空的“项目设置”表单，返回层级异常并存在误建项目风险。

# 十三、目标资金

- 原需求：目标资金支持截止日期和每月建议存入金额，这两个字段应独立录入和保存。
  实际行为：在“截止日期”字段填入 `2026-12-31` 后，同一日期字符串同时自动出现在下一项“建议月存”输入框，并使建议月存显示“字段值无效”。输入发生跨字段污染，可能造成错误计划数据。
- 原需求：目标资金支持进度和历史曲线，分配、释放和调整应形成可重建的历史。
  实际行为：目标先分配至 ¥12,000，再释放 ¥2,000 后当前预留正确为 ¥10,000，但曲线摘要显示“从 ¥10,000 变化至 ¥10,000”，未反映实际的 ¥12,000→¥10,000 变化，历史摘要与操作记录不一致。
- 原需求：目标资金支持手动分配及调整，操作含义应明确且可预测。
  实际行为：“调整”表单只标注“金额”，没有说明该值是增减量还是调整后的余额；在已有 ¥10,000 时输入 ¥15,000，结果变为 ¥25,000。当前文案极易让用户误以为是在把余额调整到 ¥15,000。
- 原需求：目标完成后由用户选择释放、保留或继续使用，并能正常返回目标详情/列表。
  实际行为：选择“完成并释放剩余预留”后，后台实际成功把目标标记完成并将 ¥25,000 预留释放为 ¥0，但界面仍停留在完成策略页、没有成功提示，Android 系统返回键和左上返回均失效；重新进入目标详情后才看到正确结果。完成策略的数据结果正确，但完成后的反馈和导航严重异常。
- 原需求：目标完成后全部资金历史仍应保留并可通过历史曲线查看。
  实际行为：完成并释放后详情页明确提示历史保留，但目标资金曲线变成空白图，只显示 0～1 的默认坐标轴，既有分配、释放和调整历史不可见。

# 二十三、首次启动和国际化

- 原需求：首批完整支持简体中文、日语和英语，当前选择简体中文时界面文案应保持一致。
  实际行为：简体中文账户列表中，已归档账户的状态显示为英文 `archived`，存在未本地化文案。
- 原需求：简体中文界面的业务状态应完整本地化。
  实际行为：目标资金列表中的目标状态显示为英文 `ACTIVE`，与其余中文界面混用。
- 原需求：简体中文界面的日期和交易类型文案应按应用语言/地区正确本地化。
  实际行为：流水日期分组显示英文 `Aug 20, 2026`，交易类型显示原始英文内部枚举 `TRANSFER`、`OPENING_BALANCE`，与中文界面混用。

# 十七、流水、搜索和交易详情

- 原需求：流水行应以图标和用户可理解的文字区分收入、消费、退款和转账，并展示清晰摘要。
  实际行为：转账行显示 `TRANSFER · TRANSFER`，下一行又重复 `TRANSFER`；期初记录同样三次重复 `OPENING_BALANCE`。流水直接暴露并重复内部枚举，缺少用户可理解的本地化交易摘要。
- 原需求：交易详情应展示用户内容、账户影响、预算/统计、来源、完整修改历史，并允许任何交易编辑。
  实际行为：转账详情保留了原始算式，但账户影响使用内部 `debit`/`credit` 字符串，来源显示原始枚举 `MANUAL`，创建/修改时间显示未格式化 UTC 字符串；页面只有“修改历史”“影响范围”“移入回收站”，没有可见的交易编辑入口。
- 原需求：普通支出详情也应以用户可理解的业务语义展示账户影响、预算/统计和退款关系。
  实际行为：一笔 ¥1,500 支出详情直接显示 `SYSTEM_EXPENSE_CONSUMPTION:debit:1500 JPY`、`dddd:credit:1500 JPY`、`included:1`、`CONSUMPTION_EXPENSE` 和 `refund.status:gross=1500;refunded=0;remaining=1500;JPY` 等内部字段；来源与时间继续显示 `MANUAL` 和原始 UTC 字符串。备注与项目名称虽存在，但只是无字段标签地连续显示两行。
- 原需求：流水与详情加载应稳定。
  实际行为：首次点击刚保存的支出流水时，详情先只显示“重试”；随后重新抓取页面才自动恢复为详情，存在瞬时加载错误态。
- 原需求：全文搜索应覆盖备注、商户、别名、分类、项目、参与人、地点和附件显示名，并返回匹配流水。
  实际行为：已有分类为“餐饮”的支出时，在“搜索流水”输入精确关键词“餐饮”，结果区只出现永久“重试”错误态；点击重试仍不恢复。清空关键词后页面没有默认结果，搜索无法用于查找现有交易。
- 原需求：筛选应覆盖期间、时间口径、账户、卡片、分类、商户、地点、项目、参与人、类型、状态、来源、金额、币种、附件和标签等条件，并可保存、固定和排序常用筛选。
  实际行为：“筛选”页只显示 `EXPENSE`、`BALANCE_ADJUSTMENT`、`ACTIVE`、`MANUAL` 等未本地化内部枚举，没有期间、账户、分类、金额等绝大多数需求条件，也没有应用/清除/保存按钮。选择 `BALANCE_ADJUSTMENT` 后返回，流水仍同时显示余额调整和支出，筛选没有生效；“已保存筛选”入口则直接进入仅有“重试”的错误页，保存与管理常用筛选不可用。
- 原需求：流水行应以用户可理解的文字展示所有交易类型。
  实际行为：余额调整流水行连续三次显示内部枚举 `BALANCE_ADJUSTMENT`，与此前转账、期初记录相同，既未本地化也没有可理解摘要。

# 五、交易时间、修改历史和回收站

- 原需求：删除交易后进入回收站，并且回收站交易的账务净效果为零；正式交易、预算和账户余额不能处于部分更新状态。
  实际行为：将一笔从 `dddd` 向 `银行二` 转入 ¥2,000 的转账移入回收站后，正常流水中已不再显示该交易，回收站也提示“其账务净效果为零”，但账户余额仍保持 `dddd` ¥8,000、`银行二` ¥2,000，没有恢复为删除前应有的 ¥10,000 和 ¥0。交易可见状态与账户余额发生部分更新，违反原子性要求。
- 原需求：回收站交易应支持恢复，恢复后交易重新成为正式交易且界面给出明确结果。
  实际行为：在回收站交易详情点击“恢复”后页面无加载、成功或失败反馈，并继续显示原交易与“恢复”按钮；返回正常流水后才发现交易实际已经恢复。随后再次打开回收站，整个页面呈纯白空白，标题、返回按钮、空状态和底部导航均不可见，无法继续使用回收站。
- 原需求：永久删除时应清除当前版本和全部历史版本。
  实际行为：回收站列表和回收站交易详情均未提供可见的“永久删除”入口，无法执行或验证永久删除及历史清理。
- 原需求：回收站保留期可配置，默认 30 天，并支持 1～365 天或永不自动清理。
  实际行为：“回收站设置”页默认选择 30 天，7 天、30 天、90 天和“永不自动清除”四个固定选项均可选择并持久化；但没有自定义天数入口，无法设置需求规定范围内除这三个预设外的 1～365 天数值。

# 二十六、不可破坏的系统不变量

- 原需求：正式交易、预算和账户余额不能处于部分更新状态，删除/修改交易时相关账户结果必须原子级联更新。
  实际行为：转账移入回收站后交易已从正式流水移除，但源账户和目标账户余额均未反冲，形成“交易已删除、余额仍受其影响”的部分更新状态，直接破坏系统不变量。

# 八、信用卡与分期

- 原需求：“信用账户”应进入账单、额度、还款分配和自动记账资格管理页面。
  实际行为：在“更多功能”页点击“信用账户”后，应用直接退到 Android 系统的 Quiet Ledger“应用信息”页，未打开任何信用账户页面；使用可访问元素和屏幕坐标各测试一次均稳定复现，信用账户核心功能完全不可达。
- 原需求：分期计划必须从一笔尚未建立分期计划的已记录信用消费创建。
  实际行为：当前没有任何信用账户或信用消费时，“信用卡分期”仍允许点击“创建分期计划”并直接进入分期设置表单；页面提示应选择信用消费，但没有消费选择控件或明确的“无可用信用消费”空状态，用户进入了无法完成的表单。

# 九、贷款

- 原需求：贷款模块应能创建贷款合同并生成还款计划，进而管理条款版本、实际还款和提前还款模拟。
  实际行为：填写合法的贷款名称、贷款方、放款日、本金 ¥120,000、等额本息 12 期、首次还款日和年利率后，点击“生成计划预览”“复核并保存合同”或右下角“保存”均无加载、校验、成功或错误反馈，页面完全不变。年利率分别按 `5` 和 `0.05` 尝试也无结果；合同无法创建，后续计划、还款、利率变更及提前还款功能全部被阻断。

# 十、互请结算

- 原需求：每个互请活动必须支持明确的活动结算币种，创建后该币种不可静默更改。
  实际行为：“互请活动设置”页提示“结算币种用于全部分摊与结算，产生事实后不可静默更改”，但页面没有任何币种字段或选择控件，用户无法查看或指定结算币种。
- 原需求：用户应能创建含任意参与人并可选关联项目的互请活动，再进行交易级分配和多次部分结算。
  实际行为：填写活动名称、说明、开始日期并添加“朋友甲”“朋友乙”后，点击“保存活动”时该按钮文字消失但页面不返回也无成功/错误提示；继续点击右下角“保存”也无反应。返回列表后仍显示“还没有互请活动”，活动未创建，交易分配和结算流程全部被阻断。

# 十六、快捷模板、周期交易和批量操作

- 原需求：快捷模板保存可复用字段后，应能从模板快速进入完整记账表单，并由用户确认保存，不能绕过确认直接生成交易。
  实际行为：可成功创建“午餐模板”，保存支出、餐饮、`dddd` 账户、`500+500` 金额表达式、JPY 和备注模板；但模板列表没有“使用/记一笔”入口，点击模板卡片只重新打开“快捷模板设置”编辑页，不进入完整记账表单。模板可以创建和编辑，却无法实际用于记账。
- 原需求：周期交易应支持完整周期规则、候选模式和满足资格时的正式记录模式，并可预览未来发生日期。
  实际行为：周期规则编辑器可配置频率、间隔、月内日期、缺失日期、周末、开始/结束日期和最大次数；但点击“应用规则”后一度出现纯白页，返回设置页后规则摘要仍显示内部英文 `monthly day · 1 · 2026-08-20`。即使已选择有效模板，并分别选择候选模式和正式记录模式，保存都只提示“请检查标出的必填项或规则”，页面却没有标出任何具体错误字段；周期交易无法创建，预览页因此只显示“暂无可预览日期”。
- 原需求：批量录入采用摘要表格加完整行编辑器，支持复制、插入、排序、批量粘贴，并在任意行失败时整批不写入。
  实际行为：批量粘贴可生成行，完整行编辑器也暴露分类、三组“最小单位”金额、账户、商户、ISO 时间、项目、附件、互请、位置、分期和备注，并有复制、上移、删除。两条错误行校验时正确报告 3 个错误并提示整批不会写入，原子拒绝有效；但批量粘贴说明和编辑器大量要求用户直接理解内部类型、最小单位和 ISO 时间。删除其中一条错误行后路由没有返回摘要，而是进入整页红色错误“找不到要编辑的批量行”，只剩返回按钮；返回又弹出放弃整个草稿的确认框，且取消按钮显示英文 `Cancel`。删除行后的状态与导航损坏，剩余有效行无法继续提交验证。

# 二十、导入、导出和完整备份

- 原需求：流水导出应支持按当前筛选导出 CSV，并保存到用户选择的位置。
  实际行为：按当前筛选导出 CSV 成功，界面报告导出 2 行并将 `transactions.csv` 写入系统下载目录；但简体中文导出页把筛选摘要显示成原始混合文案“当前筛选：1 states”，本地化不完整。
- 原需求：本地完整备份应在配置备份位置和恢复密码后可立即创建，并支持后续历史与恢复验证。
  实际行为：备份主页已显示“应用私有位置”、恢复密码“已设置”，点击“立即备份”进入创建页后执行仍失败，错误框直接显示内部错误码 `BACKUP_REPOSITORY_UNAVAILABLE`。无法生成首个备份，因此备份历史、恢复预览、演练和真正恢复链路均被阻断。
- 原需求：保险库默认不进入备份，但在用户设置恢复密码并主动选择后可以包含保险库。
  实际行为：恢复密码状态明确显示“已设置”，创建备份页的“包含保险库”开关仍为禁用，并继续提示“必须先设置恢复密码”，状态同步错误导致保险库备份不可用。
- 原需求：通用 CSV 导入应支持表头选择、字段/实体映射、预览、校验、重复处理和手动确认，并能合理导入应用自身导出的当前筛选 CSV。
  实际行为：选择应用自身导出的 `transactions.csv`、UTF-8、表头第 1 行后，字段名可识别为 `account`、`amount_minor`、`category` 等，但自动映射仅识别少数字段，并把未导入的 `attachment_references`、`card_display_name` 等可选列也标成“缺少必填映射”。继续到校验后，导出文件中的 `# export_schema_version`、`# application_version`、`# generated_at`、`# filter_summary` 等元数据行被当成普通交易数据，产生 20 个阻止提交的错误；虚拟化预览把这些注释行标为 `READY`。改变表头行号又会把元数据内容误当列名。应用导出的 CSV 无法通过其自身通用导入器完成往返导入。
- 原需求：所有导入先进入暂存区，只有用户手动确认后才整批提交；离开未提交向导不应改变账本或留下正式长任务。
  实际行为：测试只完成文件选择、映射与错误预览，从未进入最终确认或提交。向导中的页面返回和系统返回均无法退出，只能强制结束应用；重新启动后账本立即永久卡在 `UNFINISHED_OPERATION` 维护态，进度条停住、没有取消/重试/回滚入口。导入在手动确认前就留下了不可恢复的长操作并阻断整个应用。

# 二十一、安全与隐私

- 原需求：完整备份加密及保险库纳入策略应由恢复密码控制，设置成功后相关加密选项立即可用。
  实际行为：恢复密码可输入两次并保存，返回备份页也显示“已设置”，但“包含保险库”仍错误地保持禁用；密码设置状态与敏感数据备份权限不一致。

# 二十二、遥测和崩溃报告

- 原需求：功能统计和崩溃报告开关默认开启，但首次隐私确认前不得发送；首次启动说明应与实际默认状态一致。
  实际行为：接受隐私政策后进入第 5 步，两个开关实际均为开启，符合“默认开启”；但第 4 步隐私政策正文和第 5 步说明都明确写“默认均关闭”。同一首次启动流程中的说明与实际状态及冻结需求互相冲突，用户无法确定默认行为。

# 十二、预算

- 原需求：预算应支持自然月实例、总预算与分类预算约束、真实消费不重复计算、每日可用金额、预算调整、版本历史和预算模板。
  实际行为：本月总预算 ¥10,000、餐饮一级预算 ¥6,000 可保存；既有餐饮支出 ¥1,500 同时正确计入总预算和分类展示而未重复扣减，总剩余 ¥8,500，每日可用按剩余 12 天正确显示约 ¥708。把一级预算改为 ¥12,000 时保存被明确阻止并提示超限 ¥2,000；增加 ¥500 的预算调整后剩余与每日可用也正确重算。版本历史和“常规预算”模板均可创建。
- 原需求：预算版本历史应以面向用户的完整历史展示。
  实际行为：版本历史虽列出两次修订，但时间直接显示 `2026-08-20T02:14:52.741Z` 一类原始 UTC 技术字符串，未按当前简体中文界面和时区格式化。
- 原需求：大型/跨步骤操作必须可崩溃恢复、原子提交并安全回滚，普通预算与模板操作不应使账本长期不可用。
  实际行为：完成预算模板保存后退出并重新打开应用，启动被永久拦截在“正在维护账本”页，暴露内部状态 `UNFINISHED_OPERATION`，进度固定约 50%，且“维护期间禁止新的财务写入。”重复显示两次。持续等待、强制关闭和重新打开均不恢复，页面没有取消、重试或详情入口，整个应用被阻断。

# 二十五、性能和容量基线

- 原需求：大型操作必须支持进度显示、安全取消、崩溃恢复、原子提交、失败回滚和临时文件清理。
  实际行为：应用重启后进入 `UNFINISHED_OPERATION` 维护态，虽有进度条但长期固定约 50%；没有安全取消、重试或失败回滚入口，强制关闭再启动仍停留原状态，崩溃/中断恢复失败并阻断全部功能。
- 原需求：导入在最终确认前应是可安全放弃的暂存流程，中断后必须恢复或回滚。
  实际行为：仅浏览应用自身 CSV 的映射/错误预览、从未确认提交，因向导返回失效而强制结束后，同样触发永久 `UNFINISHED_OPERATION`；进度显示接近完成但长期不动，仍没有安全取消、恢复或回滚。该故障在第二个全新数据集上独立复现，说明不是先前预算模板数据的偶发现象。

# 十八、分析系统

- 原需求：固定报表至少包含需求列出的 20 类分析，并提供图表和可读数据表。
  实际行为：固定报表列表确实列出全部 20 类入口；但运行“数据完整性报告”后，页面把多个不同检查规则全部显示为相同标题“完整性检查项”和“受影响项：0”，没有规则名称或可理解的检查维度。即使结果为“全部通过”，用户也无法知道分别验证了哪些数据库、外键、账务平衡、修订链、投影或索引规则。
- 原需求：支持多个自定义仪表板、丰富图表/表格、筛选、周期比较、预测、下钻、保存复制及多格式导出。
  实际行为：点击固定报表页顶部“自定义报表”后，应用直接跳到 Android 系统的 Quiet Ledger“应用信息”页，未打开任何自定义报表页面；通过可访问元素点击稳定复现。自定义仪表板及其全部配置、保存、复制、下钻和导出功能完全不可达。

# 十五、附件

- 原需求：交易应支持添加任意格式、任意数量附件，并可管理显示名称、图片预览、外部打开、去重、跨交易引用及随交易进入回收站等完整附件生命周期。
  实际行为：新建普通支出的完整录入表单没有任何附件字段或入口；保存后进入该支出详情，页面也只有“修改历史”“影响范围”“移入回收站”，仍无附件入口。附件的导入、预览、重命名、外部打开、去重、跨交易关联、删除引用和备份等全部功能对用户不可达。

# 十四、商户、位置、地点和消费地图

- 原需求：商户应可创建、搜索名称与别名、统计、合并重复商户并在交易中选择，操作结果应立即可见。
  实际行为：商户名称和别名可以保存，别名搜索也能匹配；但保存后表单不退出且无成功反馈，合并后仍停留在合并页且无成功反馈。合并源商户继续以英文状态 `ARCHIVED` 出现在默认列表。更严重的是，新建/合并后的有效商户“便利店B”在普通支出的商户选择器中完全不显示，按精确名称搜索仍只有“未选择”，导致商户无法用于交易。
- 原需求：地点支持手动创建、修改中心点、关联商户、继续创建多个地点，并支持合并和拆分。
  实际行为：地点创建表单要求用户直接填写技术字段“纬度 E7”“经度 E7”，没有可理解的地图选点；保存后不退出且无成功反馈。返回地点页后整个内容只剩在线地图和一个无名称、不可点击的巨大圆形标记，“添加地点”入口消失，也没有地点列表或编辑入口，因此无法继续新增第二个地点、修改中心点、查看关联商户、合并或拆分。
- 原需求：用户手动调整位置时可以移动地图点；交易定位最多等待 3 秒，超时后仍可无位置保存。
  实际行为：交易录入中的位置长期显示“正在获取位置…”，点击“调整”后页面仍只显示同一等待状态和“本次不保存位置”，没有地图或手动移动地图点的能力；无位置保存本身可以正常完成。

# 六、余额、期初记录和对账

- 原需求：余额检查点应让用户输入某日现实余额，显示与账面余额的差异，并允许查找遗漏记录或明确生成余额调整记录；检查点本身不改变账面余额。
  实际行为：账户详情的“余额检查点”只打开一个要求填写“现实余额（最小单位）”的技术化表单。以账面余额 -500 JPY、现实余额 0、日期 2026-08-20 保存后，页面不退出且没有成功或错误反馈；返回账户详情既不显示该检查点，也不显示应有的 500 JPY 差异，更没有“查找遗漏记录”或“生成余额调整记录”的入口。再次点击仍是空白新建表单，检查点结果完全不可查看和使用。
- 原需求：余额调整是独立交易类型，不计入收入、消费或预算。
  实际行为：通过“其他交易—余额调整”增加 500 JPY 成功，账户余额从支出后的 -1,000 JPY 正确变为 -500 JPY，余额趋势与近期流水也显示该独立变动；但表单把账户字段错误标为“转出/目标账户”，沿用了转账术语，不符合余额调整语义。

# 七、退款

- 原需求：应支持关联原交易的全额/多次部分/跨月退款，以及独立退款、退款账户、继承字段、累计与剩余可退金额、超额覆盖和预算恢复策略。
  实际行为：在“记账—其他交易”点击明确标注的“退款”按钮后，应用立即退出到 Android 启动器应用抽屉，没有打开退款页面；重新进入应用后也没有任何退款草稿或提示。普通支出详情中同样没有退款入口，因此关联退款和独立退款的全部流程均不可达。

# 十九、主导航和桌面小组件

- 原需求：桌面小组件应包含快速记账、本月消费、本月预算、今日可用金额、指定账户余额、净金融资产、指定信用卡本期应还、指定目标资金和大型财务概览，并可实际显示或打开相应内容。
  实际行为：Android 小组件配置页确实列出上述 9 种类型；但整个配置流程使用英文，与应用内选择的简体中文不一致。选择“Quick entry”、选择“餐饮”、进入下一步并点击“Save widget”后，桌面新增的小组件只显示英文错误占位文案 `Configure this widget again`，没有快速记账内容，点击也未表现为可用的预填记账入口。小组件创建结果不可用。

# 二十七、需求阶段结论

- 原需求：冻结需求已经足够完整，可作为技术选型和后续实现的约束输入，产品可进入下一阶段。
  实际行为：该标题本身不是独立的用户功能；本轮已将其作为发布前验收基线覆盖全部一级标题。但当前实现存在退款、信用账户、自定义报表和附件等整模块不可达，删除交易不反冲账户余额，导入预览或预算模板可触发永久 `UNFINISHED_OPERATION`，以及备份、搜索、周期交易、贷款和互请等关键链路不可用，因此当前版本尚不满足该冻结基线，不能据此判定达到发布条件。
