# 五、Book、Commit 和版本模型

- 原需求：每个写命令都必须具有 `CommandId`；同一 `commandId` 重复执行时直接返回首次结果，不得重复生成变更。
- 实际实现：自动化领域的 `AutomationMutationIds` 只有 `bookId`、`commitId`、`entityRevisionId`、`deviceInstanceId` 等字段，没有 `commandId`；`SecureRoomAutomationApplicationPort.startCommit` 还明确将 `book_commit.command_uid` 写为 `NULL`。因此保存快捷模板、保存周期规则、修改单次/后续周期等正式领域写入不具备本章要求的命令级幂等身份与重复执行回执语义。

# 八、交易聚合

- 原需求：除普通支出和收入外，其他交易只有在确实包含费用或收入成分时才允许带分类。
- 实际实现：`LoanPaymentPayload` 与 `FxExchangePayload` 均可无条件携带可空 `classification`。`AccountingRuleEngine.loanPayment` 只校验分类引用本身，不拒绝“仅偿还本金却带分类”；`AccountingRuleEngine.fxExchange` 甚至不读取/校验 `classification`，因此无汇兑损益的零差额兑换也可以保存分类。实际约束弱于冻结设计。

# 三十、数据库与领域约束分工

- 原需求：启动维护、备份和恢复后，完整性审计应重复验证 Posting 币种、Active 交易的未冲销 APPLY 链、Trashed 交易净账务效果、各类事实投影可重建，以及投影 Hash 与重建结果一致。
- 实际实现：`DatabaseIntegrityAudit` 只检查 `PRAGMA integrity_check`、`PRAGMA foreign_key_check`、Journal 平衡和当前交易子类型；恢复流程另查投影版本，投影维护流程另做重建与 Hash 对比，但没有一个按要求在上述三个时点执行全部检查的审计，且未发现对 Posting 币种、Active APPLY 链和 Trashed 零净效果的完整审计实现。

# 三十二、永久不变量

- 原需求：35 条永久不变量应同时作为领域测试、数据库审计和恢复验证的共同标准。
- 实际实现：领域模型和写入规则覆盖了这些业务不变量，但数据库审计与恢复验证只覆盖其中少数（主要是 Journal 平衡、当前修订子类型、外键及投影版本）；例如未在两者中验证 Posting 币种、Active/Trashed 净 APPLY 链、退款/预算/贷款/分期/互请守恒、周期唯一性、保险库字段隔离、全金额溢出及缓存版本等，因此没有形成三处共同采用的完整 35 条标准。

# 三十三、Schema v1 迁移规范

- 原需求：每次迁移后都要验证 SQLCipher 解密、完整性与外键、Journal 平衡、交易子类型、投影重建、FTS/R*Tree、目标规模查询基准和旧备份恢复。
- 实际实现：v1→v2、v2→v3、v3→v4 的迁移函数只安装/回填结构并更新 schema registry；打开数据库后的启动检查也只检查 schema contract、操作状态和投影版本。仓库仅提供 `MigrationTestHelper` 基础设施占位，未发现逐次迁移执行上述完整验证、目标规模基准及旧备份恢复的实现。
