下面这份计划以已经确认的行为为准，覆盖业务规则、代码改造、历史数据、云端办理、UI 和验收。本轮只拟定计划，不修改业务代码。

**1．先固定最终行为，后续实现和测试都以这张表为准。**

| 操作或场景 | 最终行为 |
|---|---|
| 修改一笔支出的商户 | 只修改该笔消费的商户归属，其退款跟随；不重命名正式商户 |
| 保存支出时，存在唯一同名正式商户 | 自动关联，并使用正式商户名称 |
| 保存支出时，没有同名正式商户 | 保留原名文字，不自动创建商户 |
| 正式商户已停用 | 仍可自动关联同名记录；停用影响候选和定位推荐 |
| 存在多个历史同名正式商户 | 不自动选择；已有明确关联保留，未关联记录标为归属待确认 |
| 从原名创建正式商户，名称未改 | 自动关联该原名组及对应模板、周期规则 |
| 从原名创建正式商户，同时改名 | 原名组对应记录一起改名并关联；相关模板、周期规则一起更新 |
| 从原名入口输入已有正式商户名称 | 确认后直接归入已有商户，无需先创建中间商户 |
| 正式商户改名 | 保持 ID，统一所属记录和引用；退款跟随原消费 |
| 正式商户改名撞上另一正式商户 | 确认合并，保留目标 ID 和目标名称 |
| 正式商户合并 | 保留目标启停状态，合并备注、迁移地点和引用，删除来源商户 |
| 只改备注或启停 | 只修改相应资料，不顺带批量改名、补关联或删除临时位置 |
| 收入、转账只有同名“名称／说明” | 不因此自动归属商户，也不跟随商户改名 |
| 收入已经明确关联商户 | 跟随对应正式商户更新 |
| 商户操作历史 | 保留改名、归入、合并等追溯信息；不新增本机撤销功能 |
| 云端办理 | 保留现有撤销能力；撤销后原操作历史仍可查看，并标明已撤销 |

所有商户名称匹配统一使用当前规范化规则：去除首尾空白、NFKC 规范化、忽略大小写。保存的正式名称保留用户选择的显示写法。

**2．统一商户归属判断，消除“页面认为有关联，保存时却没关联”的两套规则。**

主要落点：

- [EntryDefaults.kt](/home/hubery-fedora/Projects/ExpenseTracker/android/app/src/main/java/com/yohaku/expensetracker/data/repository/EntryDefaults.kt)
- [AnalysisProjection.kt](/home/hubery-fedora/Projects/ExpenseTracker/android/app/src/main/java/com/yohaku/expensetracker/data/repository/AnalysisProjection.kt)
- [LedgerRepository.kt](/home/hubery-fedora/Projects/ExpenseTracker/android/app/src/main/java/com/yohaku/expensetracker/data/repository/LedgerRepository.kt)
- `TemplateRepository.kt`、`RecurrenceRepository.kt`
- `EntryCommandAdapters.kt`

建立共享的商户解析逻辑，供本机表单、CSV 导入、模板记账、周期记账和云端命令使用。

解析结果明确区分：

- 已确定正式商户；
- 没有对应正式商户；
- 存在历史重名歧义。

具体约束：

- 支出未提供明确商户 ID 时，按最终名称寻找唯一正式商户，包含停用商户。
- 已提供明确商户 ID 时，校验账本归属，并使用该商户的正式名称。
- 普通收入和转账不根据“名称／说明”自动建立商户关联。
- 收入已有明确商户 ID 时保留支持。
- 退款通过原消费确定商户，不独立按退款文字猜测。
- 不允许保存“关联 A、显示 B”这种互相矛盾的结果。

本机输入时，用户改变名称可以清除旧选择，再按新文字重新匹配。云端同时提供明显不一致的商户 ID 和名称时，应返回明确错误，避免静默丢弃其中一个字段。

自动关联必须在**保存事务中再次执行**。输入框的联想和自动选择只是交互辅助，不能作为唯一保证。

**持久化关联是唯一依据。**本轮建立并维护以下不变量：

> 同账本、未永久清理的支出：有效的明确关联优先；没有明确关联、且最终名称唯一匹配某个正式商户（含停用）时，任何写入事务结束后都必须已持久化该关联。

维护者包括：普通保存、CSV 导入、模板／周期记账、模板和周期规则自身的保存（周期规则的 `merchant.ifBlank{rule.name}` 也是最终名称来源）、所有商户操作、历史整理和云端撤销（见第 11 节）。回收站恢复只清删除标记，不重新解析；因此迁移和商户操作必须完整覆盖可恢复记录。

`merchantKey()` 当前在读取时按名称兜底，商户批量操作（`merchantEvents()` 等）也借它计算范围。本轮：

- 批量操作范围改为“明确关联集合 ＋ 显式计算的待认领集合”，不再借助 `merchantKey()`；
- 读取兜底在历史整理和全部写入路径闭环之后删除，只保留重名歧义判断。兜底不能长期保留，否则会掩盖漏关联的写入路径。

输入辅助与保存使用同一套解析，停用商户也包含在内。现有代码中，输入辅助 `merchantInput()` 只自动选中启用中的商户，保存时 `prepareEntry()` 也拒绝新关联停用商户。改为：输入名称唯一匹配停用商户时，同样自动选中，表单标明“将关联到已停用商户 X”；保存时不再拒绝。下拉候选和定位推荐仍排除停用商户。

停用只影响候选和定位推荐：模板、周期规则的校验与可用性不再要求商户启用，仍保留“商户存在且属于本账本”的校验；否则自动关联到停用商户的模板会突然不可用。

商户列表、详情、分析和原名目录共用这些规则。尚无正式商户的支出原名，分析分组也按规范化名称归组，避免目录是一组、分析却拆成多个。

**验收结果：**同一笔记录在输入、保存、商户详情和分析中，对商户归属的判断一致。

**3．重做“从原名保存商户”的数据入口，让它真正处理原名对应的记录组。**

主要落点：

- [MerchantUpdates.kt](/home/hubery-fedora/Projects/ExpenseTracker/android/app/src/main/java/com/yohaku/expensetracker/data/repository/MerchantUpdates.kt)
- [MerchantsScreen.kt](/home/hubery-fedora/Projects/ExpenseTracker/android/app/src/main/java/com/yohaku/expensetracker/ui/features/MerchantsScreen.kt)
- `EventPlaces.kt`

当前 `initialName` 只负责预填输入框，必须改成明确保留两份信息：

- 来源原名组：用户从哪一组记录进入；
- 目标商户：最终创建或归入哪个正式商户。

来源原名不能随着输入框修改而丢失。

以“星巴克咖啡 → 星巴克”为例，保存事务应处理：

1. 原名“星巴克咖啡”对应的未关联支出；
2. 这些支出的关联退款；
3. 对应的无商户 ID 模板和周期规则；
4. 需要同步的草稿；
5. 最终名称“星巴克”下其他可以唯一归属的未关联支出及引用；
6. 本次涉及的临时位置。

已经明确关联其他商户的记录，不得仅因文字相同被抢走。

原名组的范围包含可恢复的回收站支出，预览中分别列出正常记录和回收站记录数量。只存在于回收站的原名仍不必新增到日常目录，但当处理一个已展示的原名组时，要完整处理其可恢复记录。

保存分为两条路径：

| 目标情况 | 处理 |
|---|---|
| 最终名称不存在正式商户 | 创建正式商户，统一来源组名称并建立关联 |
| 最终名称唯一匹配已有正式商户 | 展示归入确认，确认后直接关联到该商户 |

对于第二种情况，沿用目标商户的名称与启停状态；来源原名没有独立的商户启停状态，不应借此改变目标状态。编辑过程中填写的备注和选择保留的地点，在确认中说明如何加入目标资料。

如果最终名称匹配到多个同名正式商户，不在本流程中让用户挑选目标，也不能继续使用 `firstOrNull`；提示“先在商户管理中合并或改名区分”，处理完歧义后再回到本流程。重名歧义统一按第 9 节在管理页处理。

本次不新增独立的“将记录归入商户”入口，行为直接整合到原名保存流程。

**验收结果：**从原名入口改名后，原来那组记录确实一起改名；撞上已有商户时可以在当前流程完成归入。

**4．把商户资料保存、重命名和合并拆成明确的业务操作。**

继续复用现有仓库结构，但不再让一个普通保存函数无差别承担所有副作用。

建议明确区分：

| 操作 | 修改范围 |
|---|---|
| 创建正式商户 | 新资料、同名支出及相关引用 |
| 从原名创建／归入 | 明确的来源组、目标同名组及其引用 |
| 修改商户名称 | 当前所属记录与引用，必要时吸收新名称对应的原名组 |
| 修改备注 | 商户备注 |
| 修改启停 | 商户启停状态 |
| 合并商户 | 来源与目标的相关记录、地点、引用及商户资料 |
| 删除商户 | 地点和正式关联清理，保留记录文字及追溯历史 |

重命名时，先按修改前的身份确定记录范围，避免名称修改后无法找到旧记录。

每个改变名称或商户存在性的操作（创建、改名、归入、合并、删除；只改备注／启停不算），都按最终状态重新计算**受影响的旧名称组和新名称组**。重点是歧义消除：商户 A、B 都叫 X，把 A 改名、合并到别处或删除后，B 成为唯一的 X，未关联的 X 记录应归 B，而不是归合并目标。三个同名商户只合并其中两个时仍有歧义，不能把“执行过合并”当成可以认领的条件。

仅修改大小写或全半角写法，也属于显示名称变化，应统一所属记录的显示文字；但不应因此误触发“合并自己”。

正式商户改成一个已有原名组的名字时，继续展示受影响范围并确认。相关模板和周期规则自动纳入，不增加逐项选择。

正式合并采用已确定规则：

- 保留目标商户 ID、正式名称及启停状态；
- 来源备注加入目标备注，避免明显重复；
- 保存地点全部迁移，不因名称或坐标相近就擅自删除；
- 对完全重复地点给出提示；
- 更新来源和目标所属记录及引用；
- 删除来源商户；
- 保留来源商户的历史信息。

所有批量操作采用“预览影响 → 事务提交”的同一套计算结果。确认前如果相关记录、目标商户或地点发生变化，则刷新预览，不能按旧数量悄悄扩大操作范围。做法可以是：预览返回受影响对象的指纹，提交时重新计算，不一致就拒绝并刷新预览。每个操作首次可执行时（本机或云端）就必须具备准确的影响预览和确认校验，不能先开放执行、后补预览。

预览至少区分：

- 新关联的记录数量；
- 会修改名称的记录数量；
- 回收站记录数量；
- 关联退款数量；
- 模板和周期规则数量；
- 保存地点及待处理临时位置数量。

**验收结果：**操作名称与实际修改范围一致，改备注和启停不再触发隐藏的批量整理。

**5．修复退款归属，以原消费作为唯一业务依据。**

主要落点：

- `CurrencyTransactions.kt`
- `LedgerChangeReview.kt`
- `AnalysisProjection.kt`
- `MerchantsScreen.kt`
- 记录详情与退款相关显示

现状：退款保存时复制原消费当时的商户文字，自身从不写商户关联（历史版本也没有写过）。分析金额从原消费中扣除，所以已经跟随原消费；但商户详情的“归属这个商户的退款”列表、改名／合并的同步范围，都按退款自己的文字判断。修改原消费的商户时，只同步了退款的活动，没有同步商户文字。

具体改动：

- 退款继续不保存自身商户关联，商户文字只作为原消费商户的显示副本，用于显示和搜索。
- `merchantKey()` 判断退款时，先沿 `originalEventId` 找原消费，再取得其商户归属。
- 原消费更换商户、正式商户改名、原名归入、商户合并时，同步相关退款的商户显示文字。
- 同步范围包含可恢复的退款记录。
- 退款不再参与独立的同名原名认领，避免一笔退款被其他同名商户抢走。
- 商户详情和分析使用一致的退款归属规则。

退款的金额、到账确认、日期和与原消费的关联保持原业务规则。待到账退款仍可显示，但必须有状态标识；分析净额继续遵循现有“已确认退款”的计算口径。

关键验收场景：

```text
A 商户消费 100，退款 20
把消费改到 B

B：消费与退款都能找到，分析净额为 80
A：不再把这笔退款当成自己的退款
```

同时覆盖旧数据中“消费与退款文字已经不一致”的情况，不要求用户逐笔重新编辑退款才能修正。

**6．修复草稿同步，区分系统更新和用户正在修改的商户内容。**

主要落点：

- `EntryDraft` 数据结构及序列化
- `EntryDrafts.kt`
- `LedgerRepository.saveDraft()`
- [AppViewModel.kt](/home/hubery-fedora/Projects/ExpenseTracker/android/app/src/main/java/com/yohaku/expensetracker/ui/features/AppViewModel.kt)
- `EntryMerchantInput.kt`
- 模板、周期规则编辑器

不能继续只使用 `merchantId` 判断草稿是否需要同步，也不能把“字段曾经被填过”当成用户正在修改归属。`merchantManuallyEdited` 保持现有用途（`hasManualInput`、定位推荐、日期变化后的清理），不改作冲突标志。

草稿按两类分别处理。

**一、新建草稿，以及引用正式商户的草稿：采用“来源组归属”规则。**草稿当前的商户输入属于本次商户操作处理的来源组，就跟随同步；否则不动。

- 有商户 ID：按 ID 判断。改名时同步名称；合并时把来源 ID 改为目标 ID 并同步名称；删除时清除失效 ID、保留文字。
- 没有商户 ID：按规范化名称判断是否属于本次**明确认领**的原名组。例如刚把原名“星巴克咖啡”整理为“星巴克”，只写着“星巴克咖啡”的新建草稿也跟随，否则保存后会重新生成用户刚整理掉的原名组。
- 只适用于支出。收入、转账不按同名同步；退款沿原消费。
- 存在历史重名时，只认业务操作明确认领的原名组，不能泛化为“和来源商户旧名称相同”。

**二、编辑已有记录的草稿：保存最小商户基线**，即打开时记录的商户文字和商户 ID，不保存整份编辑快照。

- 当前输入等于基线（用户没改商户）：保存时不写入草稿里的商户字段，在提交事务中读取并沿用记录当前的商户。这样外部的改名、合并、归入、云端改商户都能自然生效，不需要逐条同步编辑草稿的文字。预览使用同一规则。
- 用户改过商户：按输入重新解析。只有当记录当前商户相对基线也发生了变化，且与用户输入的最终归属不同时，才算冲突并明确提示；用户正常更换商户不算冲突。
- 旧版本草稿没有基线：保守处理，不猜测用户意图；保存时若与记录当前商户不一致，就提示用户确认。

打开中的表单收到系统同步时，同时更新显示值和基线，避免系统改名被误判为用户修改。已经排队的草稿保存（如 `leaveEntry()` 捕获的旧状态）用会话／状态版本校验，防止旧状态随后覆盖新状态。

模板和周期编辑器的本地副本（以对象 ID 为 `remember` 键，数据库同 ID 更新不会重新初始化）使用相同原则，不能只修记账草稿。

**验收结果：**保留旧编辑草稿、完成原名归入和商户改名、再恢复并保存草稿，不会无意把记录改回旧名称并解除关联。

**7．完整处理临时位置，关联判断必须先于位置保存。**

主要落点：

- `EventPlaces.kt`
- `LedgerRepository.prepareEntry()`
- `MerchantUpdates.kt`
- `MerchantsScreen.kt`
- 定位输入相关代码

保存新支出的顺序固定为：

```text
解析商户 → 确定是否有正式关联 → 决定是否保存临时位置
```

今天新建、有定位、名称非空且最终仍没有正式商户关联的支出，才保存临时位置。唯一同名正式商户即使停用，也应先自动关联，避免误留临时位置。

原名转正式商户、改名吸收原名组、合并时，统一收集相关临时位置：

- 按现有合理的距离聚合方式形成地点候选；
- 用户可保留、调整或明确放弃；
- 默认保留有效地点候选，沿用现有原名创建体验；
- 保存正式地点与完成关联在同一事务内；
- 明确完成保存或放弃后，再清除相应临时位置。

旧数据自动补关联时没有用户确认机会，因此不能直接丢弃已有临时位置。保留为待整理位置，在商户资料中提供现有地点整理流程；不自动把未经确认的旧位置变成定位推荐地点。

“保留”必须同时保证位置仍然可见、不会被意外删除。现有代码两处需要一起修改：

- 位置候选查询（`recordedPlaces()`）目前排除所有已关联事件，应改为纳入“仍有待整理位置的已关联事件”；
- 普通记录保存目前会无条件清除已关联事件的位置（`LedgerChangeReview.kt`），应改为只在明确完成保存或放弃后清除。

这属于历史数据过渡状态。新的正常保存流程不会继续制造同类问题。

云端归入也必须说明临时位置的处理。未明确处理的旧位置保留待整理，不能因调用默认参数而静默删除。

**验收结果：**同一批原名记录从不同入口变成正式关联时，位置资料不会因入口差异而无提示丢失。

**8．增加独立的商户操作历史，不改变记账保存顺序。**

新增商户操作历史存储和查询，覆盖：

- 创建正式商户；
- 原名创建／归入；
- 正式商户改名；
- 商户合并；
- 备注和启停变更；
- 商户删除；
- 历史数据整理；
- 云端操作撤销。

每次实际发生变化的操作记录：

| 内容 | 目的 |
|---|---|
| 操作时间、类型、来源 | 区分本机、云端和升级整理 |
| 来源／目标商户 ID 与名称快照 | 商户合并或删除后仍能辨认 |
| 修改前后的资料 | 查看名称、备注、启停的变化 |
| 受影响对象及数量 | 查清哪些记录、模板、周期等受到影响 |
| 必要的旧／新商户文字和关联 | 支持具体记录的追溯 |
| 云端执行标识、对应撤销关系 | 查看该操作是否已经被撤销 |

采用操作主记录与必要的影响明细，不复制整笔金额、分录、图片等无关数据。影响明细按对象类型和对象 ID 建索引，供记录详情查询。历史按需查询，避免每次读取账本都加载全部历史。

记录详情入口用于补上记录修改历史看不到的部分：商户批量同步不写记录修订，所以单笔记录的修改历史里没有“因原名归入从‘星巴克咖啡’变成‘星巴克’”这类变化。记录详情列出影响过这笔记录商户的改名、归入、合并操作，三套主题各自实现。

历史不能依赖来源商户或事件必须仍存在。删除商户、合并来源被删除、记录到期清理后，相关名称快照仍可阅读；整本账本永久删除时，历史随账本清理。

UI 提供：

- 商户管理中的操作历史入口；
- 商户详情中的相关历史；
- 合并后的目标商户可查看来源商户的历史链路；
- 记录详情可查看影响该记录商户信息的相关操作。

不新增撤销按钮。商户批量同步仍不增加每笔记录的 revision，不改变最近保存排序，也不人为使小票或金融事实过期。

单笔记账主动修改商户，继续使用现有记账修改历史，不重复制造两套相同日志。

**验收结果：**能查到“原来叫什么、何时改了、改到了哪里、影响哪些对象”，来源商户消失后历史仍完整。

**9．处理旧数据和数据库迁移，自动补关联只执行在明确的时机。**

本轮新增历史和导入来源信息需要数据库迁移，必须同步：

- Room 实体、DAO、版本和 schema；
- 完整迁移注册；
- 备份恢复；
- 账本永久清理；
- 云端撤销和引用检查。

本轮所有结构变化（商户操作历史、CSV 来源判重信息等）合并为**一次**数据库版本升级（39→40）。

历史整理**直接写在这次 Room Migration 中**，不放进 `snapshot()`、页面重组或普通读取流程。依据：备份就是数据库文件，`prepareRestore` 在暂存副本上用同一套 `ALL_MIGRATIONS` 升级。因此：

- 升级和恢复旧备份走同一路径；
- 整理和结构变化在同一事务里，失败不留半成品；
- 每条数据库版本链只执行一次，不需要额外的“已整理”标记。重新恢复同一份旧备份时，会在新的暂存副本上再执行一次，这是正确行为。

实现约束：

- 参照 `CategoryIconMigration.kt` 的先例，用游标读取、Kotlin 计算、SQL 写回，不依赖 `BookSnapshot` 和仓库层；
- 名称规范化使用冻结的迁移专用纯函数（NFKC、trim、`Locale.ROOT` 小写），不直接调用以后可能演变的 `normalizedSearchText()`；
- 按账本建立“规范化名称 → 商户列表”索引后扫描记录，退款通过 `settlements.originalEventId` 批量处理；只写实际变化的字段及对应历史；
- 覆盖归档账本、回收站账本和可恢复记录，排除永久清理的占位记录。

整理内容：

- 为唯一同名正式商户补齐历史支出的正式关联；
- 保留已经明确选择的有效商户 ID；
- 同步可以确定的正式名称；
- 修正退款商户归属和显示（按原消费同步退款文字）；
- 处理明确符合规则的模板、周期引用；
- 保留尚未处理的临时位置；
- 对历史重复商户不自动合并；
- 写入“历史数据整理”的商户操作历史。

迁移不修改草稿。旧草稿的兼容由第 6 节的保存规则承担。

**重名歧义统一规则：**没有明确 ID 且有多个匹配时不自动关联；有效的明确 ID 继续尊重。管理页提示重名，引导用户合并或改名区分，并显示地点、备注等辨认信息。每次操作后按最终名称组重新判断是否仍有歧义。由于第 11 节的撤销检查会拒绝新增重名，重名只会来自历史数据。

**旧云端撤销日志兼容：**迁移改写事件和引用、新增列之后，升级前记录的撤销日志可能与现状不再匹配。处理方式：

- 按日志版本为新增列补齐可确定的迁移默认值后再比较，不一律忽略新增列（新列可能承载后续真实写入的业务数据，撤销整行删除时尤其不能漏判）；
- 迁移改写过的行，凡被升级前撤销条目引用的，记录可识别的标记；对应撤销报告“数据已升级整理”冲突，不尝试精确恢复；
- 新增列有后续业务变化或无法安全解释时，拒绝撤销。

对于升级前已经丢失、无法可靠重建的旧名，不伪造历史。追溯从本次实际迁移和后续操作开始，已有修订中能够确认的信息仍保留。

**验收结果：**旧账本能升级、旧备份能恢复、历史重复不会被误合并，迁移不改变余额或制造重复记录。

**10．修复商户改名的其他连带显示和 CSV 判重问题。**

**互请与朋友往来：**

自己付款、明确关联某笔消费的互请，商户显示应跟随原消费。优先使用关联事件的当前商户作为显示依据，并处理仍保存旧名称的派生数据。

朋友独立记录的“别人请我”名称不属于该消费的商户引用，不按同名批量修改。

**信用卡自动计划：**

自动从消费生成的计划，在显示关联消费时使用最新商户名称。独立计划标题及用户自定义标题保持其独立含义，不为改商户名重算账期、费用或已确认账单。

**CSV 导入：**

在导入时保存稳定的来源匹配信息，建立在原始导入值上，而不是事后已经被商户同步改写的名称上。落点是给现有的 `csv_batch_events`（导入批次 ↔ 记录）加一列来源判重键，随 39→40 一起升级。来源判重键在保存解析改写名称之前计算（批次 B）。

重复预览同时使用：

- 现有记录的当前匹配信息；
- 已导入记录的来源匹配信息。

不能简单移除商户字段，以免把同一天、同金额的不同消费误判为重复。继续保留现有“同一文件内相同行不自动互相去重”的规则。

旧导入批次从第 1 版修订（`RevisionEntity.afterJson`）恢复来源信息，这一版就是导入时写下的值。商户同步不写修订，所以这个来源可靠；只在修订缺失时保持明确限制，不根据现名臆造原始值。

来源信息随导入记录生命周期、云端撤销及备份一起处理，不作为商户的别名参与日常自动匹配。

**验收结果：**商户批量改名后，再导入原 CSV，原有导入记录仍能被识别；互请页面不会对同一笔消费显示过时商户名。

**11．同步云端办理接口、预览、撤销和协议。**

主要落点：

- `LedgerCommandAdapters.kt`
- `EntryCommandAdapters.kt`
- `CommandUndoJournal.kt`
- 命令预览／比较和结构导出
- 正式协议、交接包、assets 与能力样例

具体改动：

- 云端普通记账、模板记账和周期记账使用同一商户解析逻辑。
- `merchant.setActive` 只修改启停，不再调用带批量同步副作用的保存路径。
- `merchant.save` 支持明确表达来源原名组与目标商户，复用本机同一业务实现。
- 从原名归入已有商户时，使用明确目标 ID；不把它伪装成两个正式商户的合并。
- 两个正式商户之间的合并继续只在应用内办理，云端禁止。
- 预览显示归入记录、改名记录、退款、模板／周期和位置影响。
- 撤销日志覆盖新增的实际业务数据变化。

商户历史与云端撤销需要单独协调：

- 撤销恢复业务状态；
- 原商户操作历史保留；
- 在同一撤销事务中记录对应撤销关系；
- 历史快照中的旧 ID 不被当作阻止撤销的“活引用”；
- 对真正的活引用和后续修改，继续保留原有冲突检查。

**撤销后的商户一致性：**撤销用原始 SQL 恢复行快照，绕过仓库解析，可能破坏第 2 节的不变量。例如：

- 先把未关联支出 X 改成 Y，再创建商户 X，然后撤销第一步：会恢复一笔未关联、但唯一同名的 X；
- 先把商户 A 从 X 改成 Y，再新建商户 B 叫 X，然后撤销：会造成重名。

处理方式是“冲突拒绝”，不在撤销时静默扩大整理范围：

- 撤销前，对**整个批次**拟恢复的最终状态做商户一致性检查，范围包括：未关联但唯一同名的支出、新增的规范化重名、明确关联的显示名称、退款归属、失效引用；
- 不满足就作为冲突拒绝撤销，与现有“后续修改阻止撤销”一致；
- 区分“新增重名”和“原本存在、本次未改变的历史重名”，避免无关撤销被历史数据阻断。

预览和失败事务不能留下真实操作历史。协议需明确“历史文字快照”和“当前业务关联”的区别。

更新能力定义后，通过现有生成和校验流程同步产物，避免手改 JSON 导致摘要与代码不一致。

**验收结果：**同一业务从本机或云端执行得到一致结果；云端执行再撤销后，业务数据恢复，历史仍能解释发生过什么。

**12．UI 修改覆盖三主题、中日文和所有受影响入口。**

保留当前紧凑双列商户目录，在现有结构内完成：

- 原名保存编辑器明确展示来源组和最终商户名称；
- 撞上已有商户时直接展示归入确认；
- 正式商户撞名时展示正式合并确认；

- 合并确认显示最终启停状态；

“原名”用于尚未保存为正式商户的记录文字；正式商户编辑字段改用“商户名称”，避免继续用“原名”同时表达历史名称和当前正式名称。

**13．按依赖分批实施，每批都有明确完成条件。**

| 批次 | 工作 | 完成条件 |
|---|---|---|
| 批次 | 工作 | 完成条件 |
|---|---|---|
| 0 | 经用户同意，把现有未提交修改提交为“阶段性检查点” | 有可对比、可回退的起点；检查点不作为正确性基准（例如其中合并启停仍取 OR、同步会直接清除临时位置） |
| A | 固定业务类型、商户解析、影响预览结构；一次性设计 39→40 结构（含商户操作历史表、CSV 来源列）；定义历史写入接口 | 各入口有共同规则，新增数据生命周期明确，后续操作可以直接写历史 |
| B | 保存时自动关联、收入／转账边界、退款归属、停用不影响模板可用性；**CSV 来源捕获写入** | 普通记账和分析归属一致；保存开始规范化名称之前，CSV 原始值已被保存 |
| C | 原名组创建／归入、正式改名／合并／删除（含受影响名称组重算）、位置处理；**每个操作同时写历史**；**云端撤销基础适配**（历史排除、恢复后一致性检查、新表覆盖） | 来源组不会丢失，批量操作事务完整；操作首次可执行时就有准确预览和撤销语义 |
| D | 草稿、模板、周期编辑状态同步 | 旧草稿无法无意覆盖新关联 |
| E | Room Migration 历史整理、旧撤销日志兼容、备份恢复及清理；整理与全部写入路径闭环后**删除 `merchantKey()` 读取兜底** | 追溯可读，旧数据可以安全升级，归属只依据持久化关联 |
| F | 互请显示、自动计划来源显示、CSV 旧批次来源回填与判重体验 | 已确认的连带问题闭环 |
| G | 云端协议、预览完善及能力产物 | 本机与云端语义一致，撤销与追溯兼容 |
| H | 三主题 UI、相关流程验证、文档更新 | 行为、界面、测试、文档保持一致 |

批次是实施顺序，不是可省略的范围。实现期间保留现有未提交修改，在其基础上调整，不回退其他功能。

**14．测试集中验证真实风险，不做无收益的全组合。**

优先扩展现有测试类，复用账本和记录准备逻辑。

| 验证组 | 必须覆盖的场景 |
|---|---|
| 名称解析 | 大小写／全半角、唯一正式商户、停用商户、历史重名、ID 与文字一致性 |
| 原名处理 | 原名保持、新名称、已有目标、来源组与目标原名组同时存在、回收站记录 |
| 同步范围 | 支出、退款、明确关联收入、普通收入／转账说明、模板、周期 |
| 退款 | 消费改商户后退款跟随；待到账／已确认展示与统计口径一致 |
| 草稿 | 新建草稿跟随被认领的原名组、合并后 ID 更新；编辑草稿未改商户时沿用记录当前商户（含云端改了该记录商户）；用户改过且记录也变化时提示冲突；无基线旧草稿；排队保存不覆盖 |
| 位置 | 保存时先关联、原名转正式地点保留、已有商户吸收原名、历史补关联不丢位置 |
| 合并 | 保留目标状态、备注、重复地点、来源删除、历史同名歧义消除 |
| 追溯 | 改名／归入／合并／删除后历史可读，记录 revision 和最近保存顺序不变 |
| CSV | 改商户名后重新导入仍判重，不误去重文件内独立相同行 |
| 云端 | 执行与撤销恢复业务数据，历史保留并标明撤销，冲突仍能阻止错误撤销；撤销会造成未关联唯一同名或新增重名时拒绝，历史重名不阻断无关撤销 |
| 迁移与备份 | 旧 schema 升级、旧备份恢复走同一迁移、历史重复不合并、待整理位置可见且不被普通保存清除、升级前撤销日志的兼容与冲突 |
| 名称组重算 | 同名 A、B 之一改名／合并／删除后，未关联记录归剩下的唯一商户 |

金额、分录、预算和金融事实使用少量代表性数据核对前后不变，不为每一种商户名称重复跑整套金融测试。

- 对实际变更的流程使用 `looks=all`、`visual=true`；
- 覆盖三主题与中日文；

重点替换已经过时的说明：

- “每次保存备注／启停都会统一记录”；
- “收入和转账仅凭同名也跟随改名”；
- “合并后的启停取 OR”；
- “旧名不保留”；
- “原名入口改输入框只创建新商户”；
- “商户同步没有独立追溯历史”。

最终必须实际验证这条完整流程：

```text
记录“星巴克咖啡”，保存临时位置
→ 创建模板、周期规则，保留一份记录编辑草稿
→ 从原名入口改为“星巴克”并保存
→ 记录、退款、模板、周期与草稿按规则同步
→ 地点保存或明确处理
→ 再将正式商户改名／并入已有商户
→ 查看相关页面和操作历史
→ 恢复旧草稿保存，不覆盖新关联
→ 再导入原 CSV，仍能识别重复
→ 云端执行同类允许操作并撤销
→ 业务状态恢复，追溯历史仍可解释完整过程
```

只有这条链路及上述必要分支成立，且相关文档、协议、迁移和三主题界面同步完成，才将这轮商户改造标记为完成。
