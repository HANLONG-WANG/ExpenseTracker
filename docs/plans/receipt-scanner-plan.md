## 一、目标与边界

把小票「拍照」从调起系统相机，改为应用内相机：

1. 预览时实时画出小票轮廓；
2. 拍照后自动找到小票、转正、裁剪并展平卷曲（只做几何处理，不做对比度/阴影/二值化增强）；
3. 用户可在确认页调整轮廓后重新处理；
4. 只保存处理后的图片，原始照片不保存；之后照常走现有小票入库流程。
   **实施注：** 此条对应自动处理开启；按追加决策关闭自动处理时，原 JPEG 跳过确认页并按现有保存方式入库。处理时原照片仍在扫描缓存临时保留至确认/放弃。

此外（用户 2026-11-09 追加）：

5. 相机页提供「自动拍摄」开关：画面稳定且轮廓可靠时自动按下快门；
6. 相机页提供「自动处理」开关：关闭后不做任何裁剪/展平，原图直出，之后照常走现有的体积优化流程；
7. 已导入的小票图片（含从相册选择的）提供「处理这张」入口，复用确认/调整页。

**不做：** 长小票多张拼接；OCR 与自动识别；图像增强。

## 二、已验证的依据

离线评估与真机测速的材料在仓库外的 `~/Projects/ReceiptScanEval/`（含用户私人小票照片，**不入库**）。结论：

### 2.1 处理流程（离线评估选定的 D7a）

1. **分割**：EdgeSAM（3× 版，encoder + decoder），以画面中心竖线 3 点为正提示，选取覆盖全部提示点、面积 3%–85% 的候选中分数最高者；保留包含中心的连通域并填洞。
2. **几何**：按 mask 主方向转正；鲁棒拟合左右边缘曲线；判断上下端是否在画面内，在画面内的端点拟合端线。
3. **展平**：转正图按 mask 外接框外扩 10% 裁剪 → SyntheticDoc（31×45，ECCV 2026，MIT）预测 backward map → 网格外延 → 用变换后的 mask 再拉直左右边 → 把旋转、裁剪、网格、拉直合成一张「输出→原图」坐标图，**对原图只做一次 remap**。
4. 用户的 26 张真实照片中约 24 张文字行平直；r21（纸在手指间扭转）底部仍倾斜。

被否决的方案：经典 OpenCV 分割、DocQuad、UVDoc、文字行精修（会扭坏字形）、SyntheticDoc 121×177、各种量化模型。

### 2.2 真机测速（Galaxy S24 Ultra，ReceiptBench 第三轮）

| 用途 | 配置 | 结果 |
|---|---|---|
| **拍照后处理** | encoder **QNN GPU** + decoder CPU + SyntheticDoc **QNN GPU** | 与 Python 参考 26/26 一致；843 ms（含测速工具约 130 ms 自身开销） |
| **实时预览** | encoder **QNN HTP FP16** + decoder CPU | 5.4–5.6 次/秒，60 秒内无一秒低于 5；mask 与精确结果 IoU ≥0.92（中位数 0.998） |
| 回退 | 全 CPU（6 线程） | 26/26 一致；1.12 s；预览 1.9 次/秒 |

- QNN GPU 是 FP32，结果与 CPU 一致；HTP FP16 会让 decoder 偶尔完全失准（r04 转错 90°），SyntheticDoc 平均偏 7.5 px，**因此 HTP 只用于预览的 encoder**。
- HTP 首次编译约 11 s，之后用 EP context 缓存加载约 0.2 s；GPU 首次约 1.4 s，之后约 0.1 s。
- XNNPACK 在该机原生崩溃，不使用。
- 全程热状态为 0，未见降频。
- 预览叠加用 CameraX `CoordinateTransform`，用户确认轮廓与画面对齐。

## 三、总体结构

```
receipt/scan/                    （新包，不依赖 UI）
  ScannerModels      模型文件、会话创建、EP 选择与回退、context 缓存
  Segmenter          EdgeSAM 预处理/推理/候选选择/mask 后处理
  ReceiptGeometry    主方向、边缘拟合、端线、预览宽松闭合
  Dewarper           SyntheticDoc、网格外延、坐标图合成、remap
  ScanContour        用户可编辑的轮廓（左右边控制点 + 上下端线）↔ mask
  ReceiptScanner     对外接口：preview(frame) / process(photo) / reprocess(photo, contour)
ui/features/scan/                （新页面）
  ScanCameraScreen   相机预览 + 轮廓叠加 + 提示 + 快门
  ScanReviewScreen   处理结果确认 + 轮廓调整
```

**实施注：** 上图是计划命名；实际对外为 `preview/detect/render/process`，编辑重处理使用 `render(photo, contour)`，没有单独的 `reprocess` 方法。UI 由 `ScanFlow`、`ScanCameraFlow` 与 `ScanReviewScreen` 串联，详见 [最终模块说明](../../android/tools/receipt-scanner/README.md)。

- 代码从 `ReceiptBench` 的 `pipeline/`（Java）移植为 Kotlin，**数值行为保持不变**；Python 参考仍是正确性基准。
- **EP 分配与回退：**
  - 预览 encoder：HTP → GPU → CPU；
  - 拍照处理：GPU → CPU；
  - 加载失败或执行异常时自动降级并记录日志，不静默改变精度等级。
- **HTP 预热：** 应用启动或更新后，在后台（WorkManager，低优先级）编译 HTP encoder 并写入 context 缓存。缓存键 = 模型哈希 + ORT/QNN 版本 + 设备 `Build.FINGERPRINT`；不匹配或加载失败时删除并重新编译。编译完成前预览用 GPU。
- **预热实施注：** 最终还预热 GPU encoder/SyntheticDoc；唯一 KEEP 任务延迟 15 秒且要求电量不低。前台只加载就绪缓存，不等待编译，GPU 未好时也可回退 CPU。完整缓存键另含 ABI、EP、HTP 配置、固定提示维度及实现版本，context 位于 `noBackupFilesDir/receipt-scanner/contexts/`。HTP 固定沿用 S24 Ultra 的 v75 配置，其他设备靠 EP 回退，不代表已验证所有 HTP 版本。
- **预览调度（2026-11-09 阶段 2 追加决策）：** 依据 ReceiptBench 第三轮 S24 Ultra 真机数据，模型后的 mask 后处理 + 几何约 25 ms / 180 ms（14%），低于 30% 门槛，因此不做流水线化，保持引擎单工作线程并增加轮廓时间平滑。无需启动模拟器测速；完整数据见 `android/tools/receipt-scanner/README.md`。

## 四、阶段划分

每阶段由 Codex 实现、Claude 复核（沿用金融 UI 重构的协作方式：每阶段开新 Codex 会话，复核通过后自动进入下一阶段）。Gradle 任务串行。

### 阶段 1　依赖、模型与处理引擎（无 UI）

- **依赖：**
  - release 用 `onnxruntime-android-qnn:1.29.0`（含 QNN 运行库）；debug 用同版本的 `onnxruntime-android:1.29.0`（含 x86_64，供模拟器测试）；
  - 加入 OpenCV 5.0.0、CameraX 1.6.2；
  - release 打开 `jniLibs.useLegacyPackaging`（实施注：实际为 debug/release 共用 packaging 配置），Manifest 声明 `uses-native-library`（libcdsprpc.so、libOpenCL.so，required=false）。
- **模型：** 三个 ONNX（约 70 MB）放入 assets（存放方式见 7.1），首次使用时复制到私有目录。
- **处理引擎：** 实现第三节的 `receipt/scan/` 包，包括 EP 选择、回退、context 缓存与后台预热。
- **正确性：**
  - JVM 单元测试覆盖纯数值部分（网格外延、坐标合成、PIL 双线性缩放、quickselect 等），用 Python 导出的小样本对照；
  - 仪器测试在模拟器上用 **合成测试小票图**（程序生成文字纸条并施加透视/卷曲，不使用用户照片）跑完整流程，与 Python 对同一输入的结果对比，阈值沿用 `compare_device.py`。
- **验收：**
  - 引擎 API 可用；
  - 单元/仪器测试通过；
  - release 构建成功；
  - 记录 APK 体积变化。

### 阶段 2　相机页

- 新增相机权限（`CAMERA`）及拒绝/永久拒绝的引导（跳转系统设置）。
- CameraX：Preview + ImageAnalysis（RGBA，KEEP_ONLY_LATEST，约 960×720）+ ImageCapture（最高质量，约 12 MP）。
  **实施注：** 实际请求 4:3、MAXIMIZE_QUALITY 与最高可用分辨率，允许高分辨率模式；流尺寸由设备与 CameraX 组合能力协商，不固定 12 MP。
- **轮廓叠加：** 沿用测速 App 已验证的坐标变换。
- **提示文案**（依据 mask 面积、位置、帧间稳定性判断）：把小票放在中间 / 靠近一些 / 拿稳 / 未找到小票。
- **其他控件：** 闪光灯（补光）开关、快门、返回。
- **「自动拍摄」开关：** 连续若干帧（以时间计，约 0.8 s）轮廓稳定（控制点帧间位移小于阈值）、mask 面积与位置合格、手机静止（陀螺仪/加速度计）时自动拍摄；拍摄前在取景框上有可见的倒计时/进度提示，用户可随时手动按快门。
- **「自动处理」开关：** 关闭时仍是应用内相机（可保留轮廓预览，但不做任何几何处理），拍照结果原图直出，跳过确认页的处理与调整，直接交给入库流程；之后按「原样保存」开关照常优化体积。
- 两个开关的状态持久化到 `AppPreferences`（进入完整备份，旧备份缺字段时：自动拍摄=关、自动处理=开）。
- 拍照后进入处理中状态；处理在后台线程，界面不卡顿。
- **验收：**
  - 模拟器上相机页可打开；
  - 无相机/无权限路径正确；
  - 预览帧率与延迟写入调试日志；
  - 三主题截图（预览画面在测试中用静态帧代替）。

### 阶段 3　确认与轮廓调整页

- 默认显示处理结果，操作：**使用 / 重拍 / 调整轮廓**。
- **调整轮廓：**
  - 在原照片上叠加轮廓（照片按小票主方向旋转显示，使边缘接近竖直、便于拖动；编辑坐标逆变换回原图后交给引擎）：左右两边各 5 个控制点（拖动后用平滑曲线连接），上下端各一条可拖动的端线；
  - 拖动时显示放大镜；
  - 「重新处理」用编辑后的轮廓生成 mask，重跑几何与展平（不重跑 EdgeSAM）；
  - 可「恢复自动结果」。
- **分割失败时**（无合格候选）：直接进入调整模式，给出居中的默认轮廓，不报错卡住。
- **原照片只在内存与 `cache/` 临时目录保留到确认或放弃为止。** 进程被回收时可从临时文件恢复确认页；确认、放弃时清理；下次启动清理超过 24 小时的残留，保留近期可恢复的扫描。
- **验收：**
  - JVM 测试覆盖轮廓↔mask 转换与控制点约束（不自交、点在图内）；
  - 仪器测试覆盖使用/重拍/调整/恢复/失败进入调整；
  - 三主题截图。

## 六、风险

| 风险 | 应对 |
|---|---|
| APK 体积大增（模型约 70 MB + QNN 运行库约 180 MB + OpenCV 约 33 MB；当前约 90 MB） | 用户已表示不设上限；可选裁掉用不到的 HTP 版本（V68/V69/DSP），见 7.3 |
| 系统更新后 HTP 缓存失效或驱动不兼容 | 缓存键含 `Build.FINGERPRINT`；失败自动重编译，期间预览用 GPU |
| 预览帧率余量小 | 真机复测各阶段；CPU 后处理达到 30% 门槛后再评估流水线化 |
| 非高通设备 | 自动回退 CPU，功能可用但慢（拍照约 1.1 s，预览约 2 次/秒） |
| 纸张严重扭转（如 r21） | 单张照片的物理局限；靠提示与调整轮廓/重拍 |

## 七、需要用户决定

### 7.1 模型文件如何进仓库

三个 ONNX 合计约 70 MB，每个都小于 GitHub 单文件 100 MB 的限制。

- **A. 直接提交（推荐）：** 最简单，模型很少变；代价是仓库永久增大约 70 MB（当前 `.git` 182 MB）。
- B. Git LFS：仓库不膨胀，但要安装 git-lfs，并受 GitHub 免费额度限制。
