## 2. 工程与依赖决策

### 2.1 工程结构

在仓库新增 `android/` 单一Gradle工程与 `app` 模块，保留原 `design/` 和 `docs/`。

建议初始命名空间 `com.yohaku.expensetracker`；正式稳定安装包使用该 applicationId，开发包增加 `.dev` 后缀，避免开发样例污染正式账本。核心包目录：

```text
android/
  settings.gradle.kts / build.gradle.kts / gradle/libs.versions.toml
  gradlew / gradle/wrapper/
  app/
    src/main/java/com/yohaku/expensetracker/
      app/                 依赖装配、应用生命周期、导航
      domain/model/        Money、账目、规则、状态
      domain/ledger/       资金/债务变动、退款、期初
      domain/budget/       月/分类/活动预算、预留
      domain/finance/      分期、リボ、贷款、账单与额度
      domain/forecast/     确定安排、情景、风险
      domain/reconcile/    1:1匹配与差异
      domain/receipt/      商品与小票状态
      data/db/             Room实体、DAO、迁移、事务
      data/repository/     读写接口、账本约束
      data/files/          附件存储、JSON与ZIP
      data/rates/          Frankfurter、缓存与来源
      platform/            定位、通知、分享、时间
      ui/theme/            magazine / journal / objects
      ui/components/       独立主题控件与无样式行为
      ui/features/         页面、ViewModel、UiState
    src/main/res/          字体、图标、语言、XML配置
    src/test/              必要计算、匹配、协议测试
    src/androidTest/       DB/迁移/核心交互验证
    src/debug/             专用可信样例与视觉入口
```

目录是实现边界，不要求每个目录一个Gradle模块。开始时使用小型应用级依赖容器与构造注入，避免为单机应用建设额外框架。页面通过ViewModel与StateFlow观察数据，不直接改数据库或在Composable内部算利息。

### 2.2 技术与工具落地

- Kotlin、Compose、Room、DataStore、Coroutines/Flow、kotlinx.serialization；金额中间值BigDecimal，持久货币最小单位Long。
- minSdk29，JDK/AGP/Gradle/Kotlin/Compose与compile/target SDK在P01核对当时稳定兼容组合后固定在版本目录；不用动态 `+`、未经核对的旧版本或长期预览版本。
- 时间API使用 `java.time`，注入Clock供预算/到期/30天清理使用；交易当地日期与金融时区分开。
- 网络仅参考汇率，采用简洁HTTP客户端；图像按尺寸解码，不把100MB文件读入Compose状态。音频可选Media3本地播放器，文件播放生命周期与页面一致。
- 前台定位优先Android位置服务，不把Google Play Services作为核心记账前提。仅与该账本用户保存的商户地点比较，不建设全球POI搜索或后台轨迹服务。
- AlarmManager调度适当窗口、WorkManager后台清理/重新检查；不建设服务器或常驻前台服务。
- 字体使用本地许可资源；三主题字体与图形迁移按UI对照第3节。
- 初始源码与工程内不硬编码签名密码、密钥、SDK用户路径或金融平台凭证。

P01之后提供 `android/README.md`，记录JDK/SDK要求、构建/安装命令、设备选择、开发与正式包区别。构建环境问题先解决，不能到交付时才发现无法安装。

### 2.3 计算、写入与页面之间的具体接口边界

以下是后续任务可以直接实现的调用契约。接口名可顺应现有代码，复用已成立的Repository、Money和账本查询，不要求为了这些边界重建工程或添加框架。

| 能力 / 对应任务 | 输入 | 返回结果与写入边界 |
| --- | --- | --- |
| 账目保存 / P06–P09,P17 | 明确bookId、编辑时的原eventId、币种金额、账户资金端、日期、分类及业务关联 | 返回持久化事件ID/修订；在同一事务保存事件、资金端与关联，成功后清除对应草稿；失败保留输入 |
| 操作影响预览 / P07–P11,P14,P17,P23 | 当前持久化快照、拟进行的变更、适用规则版本 | 返回受影响的余额、消费月份、预算、义务与关联对象；预览本身不写账。确认前资料已变化则重新计算并展示当前影响 |
| 预算投影 / P10–P11 | bookId、自然月、有效收支、周期待办、活动排除规则及主动预留 | 返回消费、预算余额、预留、预留后可花金额与来源明细；是可重算结果，不建立另一套手工维护预算余额 |
| 金融计划计算 / P14–P17 | 合同/卡资料、期初、实际事件、版本化规则、计算截止日、手动覆盖 | 返回逐期本金/费用/合计/剩余本金、额度依据与缺项；纯计算不代表已办理，不覆盖确认账单 |
| 未来资金与风险 / P18 | 各账户实际余额、已知待付义务、在途两端、活动资金预留、预计收入与日期范围 | 返回逐日账户余额、基础/含收入情景、风险日期/金额/原因和确定程度；不得把信用额度或预计收入写入实际余额 |
| 文件预览和核对 / P19 | 用户文件、目标bookId/accountId、正式协议版本、当前资金端 | 校验返回具体字段问题；预览返回覆盖范围与匹配候选；确认导入只写独立资料，补记和金额确认调用普通账目事务 |
| 小票导出与回填 / P13,P20 | 选中小票及原图引用，或商品文件与当前小票修订 | 返回真实ZIP/回填预览；保存成功才更新导出或整理状态；商品写入不触及原交易金额 |
| 提醒重建 / P21 | bookId、当前未完成义务/风险、提醒偏好、Clock/时区 | 返回可检查的本地调度清单，更新或取消稳定通知ID；调度失败不撤销已保存账务事实 |

页面只收集输入、呈现这些结果和发出明确动作。同一动作在三个主题调用同一契约；新任务先让输入到结果的真实链路成立，再接入原稿布局。预览和提交共享计算口径，不能各写一套近似公式。

## 3. 数据模型与写入规则

### 3.1 基础数据实体

| 数据组 | 建议实体与关系 | 关键约束 |
| --- | --- | --- |
| 账本与偏好 | Book、BookPreference、Draft | 账本ID、起始日、本位币；主题/语言/分析顺序独立；草稿不属于正式账目 |
| 账户/分类 | Account、OpeningPosition、Category | 账户类型固定；尚无交易引用的账户可调整币种，已有历史/关联事实不得重解释；期初资金/欠款不算收支；分类区分收支最多两级 |
| 正式账目 | LedgerEvent、Posting、ExpenseComponent、FxSnapshot、Revision | 稳定原ID、实际/预计状态、发生/到账日期；一次事件多资金端；一个消费分类 |
| 活动与互请 | Activity、ActivityBudget、Reserve、Friend、Participant、TreatEvent、TreatAllocation | 同账本同活动；本人整单不重复；别人付款不产生本人Posting |
| 商户地点 | Merchant、SavedPlace、RecordMerchantSnapshot | 管理资料与原交易原文分开；手动修改优先 |
| 周期安排 | Recurrence、Occurrence、ExpectedIncome | 固定实例ID；确认关联已存事件；预留/实际互斥，不自动记账 |
| 金融规则 | FinancialRuleVersion、FeeTable、LimitPolicy、Deadline | 模式/生效期/时区/计息边界/舍入/验证；无机构名称预设 |
| 金融计划 | DebtContract、PaymentPlan、PlanPeriod、Bill、BillLine、RepaymentAllocation | 单卡/逐笔合同、预测/手动/已确认；本金费用分开；实际还款关联义务 |
| 核对资料 | StatementBatch、StatementRow、MatchLink、ReviewDecision | 独立保存；行与资金端一一占用；人工差异不能标完全匹配 |
| 附件小票 | FileBlob、AttachmentLink、Receipt、ReceiptImage、ExportBundle、ReceiptItem | 物理文件+引用；原图顺序/修订；商品不写入LedgerEvent |
| 生命周期/通知 | TrashEntry、ReminderOccurrence、RiskState | 30天回收、关联组、调度ID稳定、风险去重状态持久化 |

实体可按实际查询适当合并，不为了表格逐行创建空类。涉及账本内关联使用 `(bookId,id)` 等复合约束或事务检查，不能仅在界面筛选。DAO和Repository读取均要求明确BookId；当前账本切换不会改写其他账本偏好或数据。

### 3.2 资金与统计基础

- Money包含币种与最小单位；解析格式与精度在输入边界校验。无金额用显式未知状态，不以0代替。超过数值可表示范围时说明输入错误，不能溢出成其他金额。
- LedgerEvent保存用途与业务关联，Posting保存账户实际/预计资金端、币种金额、日期与确认状态。跨币种不要求将两个不同币种数值直接“配平”。
- 余额=期初+生效后的实际Posting；债务本金/费用义务分别汇总；必要缓存是可重算投影，不能成为与账目互相矛盾的第二份真相。
- 预计外币入账可以参与明确标注预计的欠款展示/预测；已确认与预计分列，不将预计值混入“确认实际”而失去状态。
- 月消费按发生日期、本位币历史统计值及退款原月冲减计算；实际账户变动按实际发生/到账日计算。历史补录已包含于期初时，仅补消费资料，不再产生资金变动。
- 转账/偿还本金不算消费；明确利息/手续费为ExpenseComponent，记录其是否已包含某资金端，防止余额重复扣。
- 一个保存事务同时更新事件、Posting、费用、关系和修订；成功后刷新相关查询与未来提醒。后台计划重算也版本化，不能部分结果被UI当作完整计划。
- 退款、消费编辑、账单确认、规则变更、计划办理、还款、删除恢复均有显式影响预览。历史预算可能改变，已确认历史义务不默默重写。
- 文件先写临时目录→校验/原子就位→数据库关联；DB失败清理未引用文件。进程中断的临时文件在后续维护清理，不修改已保存记录。

### 3.3 必须先成立的系统不变量

1. 一笔整单消费只计一次，活动/互请/商品只是关联维度。
2. 每个账户变动可回溯到事件；期初/预计/已确认区分明确。
3. 预留、待付义务、实际支付不能重复扣同一笔预算或未来资金。
4. 核对导入和商品回填没有自动创建账目的写入路径。
5. 账本之间不共享账户、预算、互请、金融规则或核对链接。
6. 所有实际金额取整按币种与适用规则处理，用户实际金额优先于参考汇率。
7. 已确认账单和还款事实不会仅因规则改动或消费删除而消失。
8. 删除/恢复保留原ID；所有主题处理同一UiState，不能产生不同业务结果。

## 9. 接手后可直接执行的工作方式

### 9.1 开始、实现、验收

每项任务按以下顺序执行，不额外建立重复计划：

1. 读取本任务引用的产品章节、落地规格、UI行与冻结源码最终实现，检查前置任务的实际结果。已有实现先核对，避免重复开发。

3. 做完一条真实闭环：用户入口→输入/选择→必要预览→保存→重新读取→关联页面更新。预计、确认、取消、编辑、删除等状态遵循本任务定义，不以按钮或静态数字代替业务。

### 9.4 UI一比一的操作标准

- **参考来源**：冻结第55版源码实际渲染，按最终脚本/CSS叠加顺序提取。保持原稿的页面或弹层形式、布局、图形、字体角色与交互层级；不能看到同名函数就用早期被覆盖的版本。
- **参考状态**：每项UI记录主题、语言、宽高、字体缩放、可信数据、滚动位置、展开项和加载完成状态。截图前等待字体加载、停止过渡动效。首页之外，详情/编辑、账户、分析、活动、金融、导入、设置及其菜单/确认同样纳入。
- **逐项比较**：先比构图、字体/字重/基线、金额格式与插画，再比间距、边线、圆角、纹理、阴影和装饰。标准状态主要锚点目标1dp内；出现肉眼可见的结构或字体偏差，继续修正。截图总像素得分不能替代这些检查。
- **三主题分别通过**：任一主题只换色、沿用另一主题字体、复用同一弹层皮肤，均判为未完成；语言切换、主题切换后表单与业务状态必须保留。
- **去演示检查**：按UI对照第5节移除评审导航、重置/加载样例入口、虚构数据说明、施工提示、假系统栏。真实金额状态、计算依据、导入不直接记账等产品说明保留；移除演示段落后自然收拢版式。
- **正式页面的阶段边界**：阶段APK的未完范围放在交付说明中，不把“阶段A”“暂未开发”“demo”等开发进度文字塞进正式页面。尚未实现的能力不得显示假结果或可点击后无效的按钮；阶段包暂不开放对应入口，后续任务实现时恢复HTML规定的位置与外观。此处理不删除最终需求，也不改变完整版本的页面结构。
- **微调边界**：系统权限/文件选择、真实系统栏、触控区域、窄屏换行、大字和键盘适配可以按实际情况处理。记录原因与影响，保持主题表达；主要构图/字体体系/流程变化需提供具体前后对照，不能以“安卓适配”统称重设计。
- **新增状态**：原HTML没有的管理状态先沿该主题补小范围设计和基准，再实现；原认可页面不顺带重做。系统弹窗以安卓真实系统UI为准，应用自行呈现的部分继续使用主题设计。

实现时按下表处理设计稿内容，避免以去除demo为由删掉产品说明或改变主构图：

| 原稿内容 | 实现动作 | 验收结果 |
| --- | --- | --- |
| 页面、菜单、弹层、图标、插画、主题内字体和装饰 | 按冻结HTML最终渲染迁移；每套主题独立核对 | 同主题从主页到二级弹层风格一致；切主题有原稿规定的布局和元素差异 |
| 虚构账本、金额、日期、商户、还款计划 | 替换为持久化真实数据；无数据进入该主题空状态 | 不用样例填空，不把缺少规则的金额显示成确定结果 |
| 演示提示、评审工具、模拟权限和样例加载入口 | 删除对应节点与正式路由，收拢相邻间距 | 正式页面和帮助页没有demo或开发进度提示，不留占位空白 |
| 预计金额、资料不足、实际确认、导入不直接记账等业务解释 | 保留并由实际状态驱动，中日文同步 | 用户能判断数字的依据和操作影响，文字不冒充演示说明 |
| 系统栏、权限、文件选择、键盘以及窄屏/大字适配 | 使用真实安卓能力；应用内部分保留主题表达 | 保存、关闭和返回可达；必要微调有具体原因及对应视觉记录 |

每项功能的交付同时包含真实数据闭环和其页面复刻。只做静态页面、只做业务逻辑，或仅首页符合原稿，均不满足任务完成门槛。

5. **记录实际结论**：在现有任务下简记验证及尚未完成内容，更新UI对照；满足门槛才勾选。批次交付只代表对应范围，后续任务保持在计划中。

以下契约用于实现Repository、计算和页面动作，补充第3节不变量。状态名称是业务含义，代码可采用等价命名；不要求为每个状态建立独立表或框架。

业务写入成功后由持久化查询更新UI，不先伪造成功数字。提醒重建和文件维护可在提交后执行，但必须可恢复、可重试，不因后台失败撤销已经真实发生的金融事实。

- **最终交付**：P01–P25和UI01–UI27逐项核对，正式包无演示入口/种子数据，签名升级和数据保留验证完成。任何尚未通过的必需项列为未完成，不以“可用版本”代替全部需求达成。

### 9.10 实施收敛与验收顺序

- 每次接续开发先从当前阶段的未完成项中选定一个可交付结果，例如“分类选择到编辑保存的整页闭环”，并明确剩余缺口。组件测量用于解决该结果的实际偏差，不无限扩展成另一份设计研究。
- 视觉检查先核对整页构图、字体体系、内容完整性及真实操作，再定位有明显差异的组件。修复后验证相关整页和受影响流程；已有有效的局部证据直接复用，不因接续会话重新测量全部控件。
- 同类行高、边框或间距问题在对应主题组件中统一解决，再检查代表页面，避免逐页贴补丁。三主题各自保留原稿表达，统一业务行为不意味着统一视觉皮肤。
- 一个任务只有具体阻碍时才保持未完成：在现有阶段状态文件列出缺失页面、状态、功能或验收结果，并按依赖逐项关闭。不得以泛泛的“仍需打磨”代替可执行的剩余工作，也不得用组件通过掩盖整页遗漏。
- 阶段验收通过后立即整理该阶段APK、校验值和使用路径，再进入下一阶段。后续发现回归时修复相关项；不在没有新问题的情况下循环执行同一组检查。所有阶段仍须达到第6.2节门槛，不以收敛为由降低UI复刻或功能要求。
