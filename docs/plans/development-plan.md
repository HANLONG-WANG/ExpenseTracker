## 2. 工程与依赖决策

### 2.1 工程结构

在仓库新增 `android/` 单一Gradle工程与 `app` 模块，保留原 `design/` 和 `docs/`。

建议初始命名空间 `com.yohaku.expensetracker`；正式稳定安装包使用该 applicationId，开发包增加 `.dev` 后缀，避免开发样例污染正式账本。核心包目录：

```text
android/
  settings.gradle.kts / build.gradle.kts / gradle/libs.versions.toml
  gradlew / gradle/wrapper/
  app/
    src/main/java/com/yohaku/expensetracker/
      app/                 依赖装配、应用生命周期、导航
      domain/model/        Money、账目、规则、状态
      domain/ledger/       资金/债务变动、退款、期初
      domain/budget/       月/分类/活动预算、预留
      domain/finance/      分期、リボ、贷款、账单与额度
      domain/forecast/     确定安排、情景、风险
      domain/reconcile/    1:1匹配与差异
      domain/receipt/      商品与小票状态
      data/db/             Room实体、DAO、迁移、事务
      data/repository/     读写接口、账本约束
      data/files/          附件存储、JSON与ZIP
      data/rates/          Frankfurter、缓存与来源
      platform/            定位、通知、分享、时间
      ui/theme/            magazine / journal / objects
      ui/components/       独立主题控件与无样式行为
      ui/features/         页面、ViewModel、UiState
    src/main/res/          字体、图标、语言、XML配置
    src/test/              必要计算、匹配、协议测试
    src/androidTest/       DB/迁移/核心交互验证
    src/debug/             专用可信样例与视觉入口
```

目录是实现边界，不要求每个目录一个Gradle模块。开始时使用小型应用级依赖容器与构造注入，避免为单机应用建设额外框架。页面通过ViewModel与StateFlow观察数据，不直接改数据库或在Composable内部算利息。

### 2.2 技术与工具落地

- Kotlin、Compose、Room、DataStore、Coroutines/Flow、kotlinx.serialization；金额中间值BigDecimal，持久货币最小单位Long。
- minSdk29，JDK/AGP/Gradle/Kotlin/Compose与compile/target SDK在P01核对当时稳定兼容组合后固定在版本目录；不用动态 `+`、未经核对的旧版本或长期预览版本。
- 时间API使用 `java.time`，注入Clock供预算/到期/30天清理使用；交易当地日期与金融时区分开。
- 网络仅参考汇率，采用简洁HTTP客户端；图像按尺寸解码，不把100MB文件读入Compose状态。音频可选Media3本地播放器，文件播放生命周期与页面一致。
- 前台定位优先Android位置服务，不把Google Play Services作为核心记账前提。仅与该账本用户保存的商户地点比较，不建设全球POI搜索或后台轨迹服务。
- AlarmManager调度适当窗口、WorkManager后台清理/重新检查；不建设服务器或常驻前台服务。
- 字体使用本地许可资源；三主题字体与图形迁移按UI对照第3节。
- 初始源码与工程内不硬编码签名密码、密钥、SDK用户路径或金融平台凭证。

P01之后提供 `android/README.md`，记录JDK/SDK要求、构建/安装命令、设备选择、开发与正式包区别。构建环境问题先解决，不能到交付时才发现无法安装。

## 3. 数据模型与写入规则

### 3.1 基础数据实体

| 数据组 | 建议实体与关系 | 关键约束 |
| --- | --- | --- |
| 账本与偏好 | Book、BookPreference、Draft | 账本ID、起始日、本位币；主题/语言/分析顺序独立；草稿不属于正式账目 |
| 账户/分类 | Account、OpeningPosition、Category | 账户固定币种/类型；期初资金/欠款不算收支；分类区分收支最多两级 |
| 正式账目 | LedgerEvent、Posting、ExpenseComponent、FxSnapshot、Revision | 稳定原ID、实际/预计状态、发生/到账日期；一次事件多资金端；一个消费分类 |
| 活动与互请 | Activity、ActivityBudget、Reserve、Friend、Participant、TreatEvent、TreatAllocation | 同账本同活动；本人整单不重复；别人付款不产生本人Posting |
| 商户地点 | Merchant、SavedPlace、RecordMerchantSnapshot | 管理资料与原交易原文分开；手动修改优先 |
| 周期安排 | Recurrence、Occurrence、ExpectedIncome | 固定实例ID；确认关联已存事件；预留/实际互斥，不自动记账 |
| 金融规则 | FinancialRuleVersion、FeeTable、LimitPolicy、Deadline | 模式/生效期/时区/计息边界/舍入/验证；无机构名称预设 |
| 金融计划 | DebtContract、PaymentPlan、PlanPeriod、Bill、BillLine、RepaymentAllocation | 单卡/逐笔合同、预测/手动/已确认；本金费用分开；实际还款关联义务 |
| 核对资料 | StatementBatch、StatementRow、MatchLink、ReviewDecision | 独立保存；行与资金端一一占用；人工差异不能标完全匹配 |
| 附件小票 | FileBlob、AttachmentLink、Receipt、ReceiptImage、ExportBundle、ReceiptItem | 物理文件+引用；原图顺序/修订；商品不写入LedgerEvent |
| 生命周期/通知 | TrashEntry、ReminderOccurrence、RiskState | 30天回收、关联组、调度ID稳定、风险去重状态持久化 |

实体可按实际查询适当合并，不为了表格逐行创建空类。涉及账本内关联使用 `(bookId,id)` 等复合约束或事务检查，不能仅在界面筛选。DAO和Repository读取均要求明确BookId；当前账本切换不会改写其他账本偏好或数据。

### 3.2 资金与统计基础

- Money包含币种与最小单位；解析格式与精度在输入边界校验。无金额用显式未知状态，不以0代替。超过数值可表示范围时说明输入错误，不能溢出成其他金额。
- LedgerEvent保存用途与业务关联，Posting保存账户实际/预计资金端、币种金额、日期与确认状态。跨币种不要求将两个不同币种数值直接“配平”。
- 余额=期初+生效后的实际Posting；债务本金/费用义务分别汇总；必要缓存是可重算投影，不能成为与账目互相矛盾的第二份真相。
- 预计外币入账可以参与明确标注预计的欠款展示/预测；已确认与预计分列，不将预计值混入“确认实际”而失去状态。
- 月消费按发生日期、本位币历史统计值及退款原月冲减计算；实际账户变动按实际发生/到账日计算。历史补录已包含于期初时，仅补消费资料，不再产生资金变动。
- 转账/偿还本金不算消费；明确利息/手续费为ExpenseComponent，记录其是否已包含某资金端，防止余额重复扣。
- 一个保存事务同时更新事件、Posting、费用、关系和修订；成功后刷新相关查询与未来提醒。后台计划重算也版本化，不能部分结果被UI当作完整计划。
- 退款、消费编辑、账单确认、规则变更、计划办理、还款、删除恢复均有显式影响预览。历史预算可能改变，已确认历史义务不默默重写。
- 文件先写临时目录→校验/原子就位→数据库关联；DB失败清理未引用文件。进程中断的临时文件在后续维护清理，不修改已保存记录。

### 3.3 必须先成立的系统不变量

1. 一笔整单消费只计一次，活动/互请/商品只是关联维度。
2. 每个账户变动可回溯到事件；期初/预计/已确认区分明确。
3. 预留、待付义务、实际支付不能重复扣同一笔预算或未来资金。
4. 核对导入和商品回填没有自动创建账目的写入路径。
5. 账本之间不共享账户、预算、互请、金融规则或核对链接。
6. 所有实际金额取整按币种与适用规则处理，用户实际金额优先于参考汇率。
7. 已确认账单和还款事实不会仅因规则改动或消费删除而消失。
8. 删除/恢复保留原ID；所有主题处理同一UiState，不能产生不同业务结果。

### 6.2 每项完成的统一门槛

- 已实现该任务描述的真实行为，入口可达、保存/取消/回退正确。
- 相应三主题和中日文同时完成；有真实加载/空/未知/失败状态。

- 每阶段产出可安装APK与一份简短已完成/尚未完成范围；下一阶段继续全范围，不将未实现功能静默删掉。

### 6.3 重要依赖与处理原则

- 字体真实回退/分发许可在P02解决，否则后续全页文字尺寸都会偏；不先做完再换字体。
- 账务Posting/实际状态/期初在P04成立，否则退款/贷款/换汇会重复扣；不各页面独自修改余额。

- 正式schema与样例在P19/P20先定再写读取，不能把HTML示例格式当永久协议。
- 无实机只影响实机验证，不阻塞计算/工程/模拟器/UI/文件工作；保留未验状态直至可验证。
- 必要系统适配按用户允许微调，涉及主要设计变化提供具体前后对照；不把平台差异作为重新设计理由。

## 7. 明确范围与新增合理默认

- 维持不提供报销/备份/同步/应用锁/OCR/金融机构连接；不追加登录、云服务、广告、社交或跨账本汇总。
