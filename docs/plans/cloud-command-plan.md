# 云端办理：开发计划

更新：2026-11-03。状态：用户已批准；阶段 0 已验收通过；阶段 1 已验收通过（见[阶段 1 记录](cloud-command-stage-1.md)）；阶段 2 已验收通过（见[阶段 2 记录](cloud-command-stage-2.md)）；阶段 3 已验收通过（见[阶段 3 记录](cloud-command-stage-3.md)）；阶段 4 已验收通过（见[阶段 4 记录](cloud-command-stage-4.md)）；阶段 5 已验收通过（见[阶段 5 记录](cloud-command-stage-5.md)）；阶段 6 已验收通过（见[阶段 6 记录](cloud-command-stage-6.md)）；阶段 7 已验收通过（见[阶段 7 记录](cloud-command-stage-7.md)）；**阶段 8 已验收通过，计划全部完成**（见[覆盖表](cloud-command-coverage.md)与[阶段 8 记录](cloud-command-stage-8.md)）。

目标：用户在手机上用自然语言（可附截图、文件）描述需求，提交给云端工作台；助手返回一份结构化方案；手机在本机试运行并展示预览，用户确认后原子执行。最终覆盖应用内**所有用户操作**（永久边界除外），并提供月度计划评语和整批撤销。

阶段只决定实施顺序。全部阶段完成才算完成；前面阶段的纵向链路不是终点。

## 1. 已确定的决策

| 项 | 决定 |
|---|---|
| 覆盖范围 | 以"用户在界面上能完成的意图"为单位，覆盖全部操作（约 80–120 个命令） |
| 永久边界（云端永远不能做） | 恢复备份；云端连接凭证与设备管理；所有永久删除（永久删除记录/账本、清空回收站、到期清理）。删除到回收站照常开放 |
| 上传范围 | 每个任务自动附带账本结构（专用导出模型，不直接序列化 Entity）；具体记录按任务里用户选择的范围上传；提交前显示将上传的内容 |
| 月度评语 | 每月提醒用户，由用户点一下提交；不做后台自动上传 |
| 预览方式 | 在主库外层事务里试运行，然后回滚；不复制数据库 |
| 一致性 | 不建统一修订号，不冻结 ID 生成。确认时在新事务中重跑，比较结构化确认模型，一致才提交 |
| 网站 | 不修改。使用现有 `general` 任务类型（结果 ≤2MB 任意 UTF-8，服务端不校验内容），由手机端识别和校验 |
| 本次讨论依据 | Claude 与 Codex 两轮架构评审（见对话记录）；以下规则均来自评审结论 |

## 2. 协议

### 2.1 任务约定

- 网站类型 `general`；`context` 写入 `{"book_id","yohaku_protocol":"yohaku.command-task","protocol_version":1,"purpose":"command"|"monthly-review"}`。
- `instructions`（≤20000 字符）：用户原话 + 固定引导语（"按附件 `yohaku-command-protocol-v1.md` 的约定，只返回一份 `yohaku.command-plan` v1 JSON"）。
- 附件：
  - `yohaku-command-protocol-v1.md`：给助手看的协议说明（格式、引用、选择器、确认、不可做的事、资料不足时如何处理）。
  - `yohaku-capabilities-v1.json`：本机当前支持的命令清单，含 `catalogDigest`。
  - `yohaku-ledger-context-v1.json`：账本结构（账本、账户、分类、商户/地点/朋友、模板、预算、周期、金融规则/计划/余额池/额度、活动、月计划等的用户可理解字段与 ID），含 `contextDigest`、生成时间、覆盖范围说明。
  - `yohaku-records-v1.json`（可选）：用户所选范围内的记录。
  - 用户选的截图和文件（原样）。
- 资料不足时：助手在网站上把任务标为待补充，或返回只有 `message`/`questions`、没有步骤的方案。

### 2.2 结果格式 `yohaku.command-plan` v1

```json
{
  "format": "yohaku.command-plan", "version": 1,
  "plan_id": "<助手生成的 UUID>", "book_id": "...",
  "catalog_digest": "...", "context_digest": "...",
  "message": "给用户看的 Markdown 说明",
  "questions": [],
  "steps": [
    {"id": "card", "command": "account.save", "command_version": 1, "input": {...}},
    {"id": "rule", "command": "financialRule.addVersion", "command_version": 1,
     "input": {"account": {"ref": "card", "output": "account"}, ...}},
    {"id": "recat", "command": "entry.update", "command_version": 1,
     "input": {"targets": {"select": {"merchant_contains": "星巴克", "category": "<id>"}}, "set": {"category": "<id>"}}}
  ]
}
```

- 引用必须是有类型的对象 `{"ref":"<stepId>","output":"<输出名>"}`，只能指向前面的步骤，类型必须匹配。不做字符串替换。
- 目标：既可以给明确的 ID 列表，也可以给受限选择器（日期范围、账户、分类、商户/备注包含、种类、金额范围）。选择器在**预览时**由本机解析成固定的 ID 集合，确认时不重新查询。
- 金额用最小单位整数加币种；汇率用十进制字符串。
- 用户事实声明（例如"已在金融平台办理"）不能由助手填写，只能由用户在预览里勾选。
- 未知命令、未知版本、`catalog_digest` 和本机不一致、引用了永久边界内的操作，都会让整份方案被拒绝，不会跳过后继续执行。
- 限制：步骤数 ≤500，选择器解析出的目标数 ≤5000（超出则拒绝并提示拆分）。

### 2.3 能力清单

每个命令：名称、语义版本、输入 schema（共享 `$defs`）、输出引用类型、默认值/未知值规则、前提、确认要求类型、执行方式（`transactional` 数据库原子 / `post-commit` 提交后执行 / `interactive` 需要用户在手机上操作）、示例、不适用时的处理。清单由本机注册表生成，结果只引用 `catalogDigest`，**手机永远按自己的注册表校验**，不接受结果附带的 schema。永久边界作为 `forbidden` 列在清单里，告诉助手不能做。

## 3. 本机架构

六个组件，代码放在新包 `data/command/`（业务）与 `ui/features/command/`（界面）。

1. **命令注册表与能力导出器**：注册所有命令适配器；导出清单、协议说明和账本结构上下文。
2. **命令适配器**（每个命令一个）：`normalize`（解析输入、默认值、解析选择器和引用、固定目标）→ 检查前提 → 调用现有的 preview/commit（或本计划下沉后的业务函数）→ 产出 `StepEffect`（业务对象前后状态、连带影响、确认要求、执行方式）→ 提供逆操作（第 2 阶段起要求）。`null`/`false` 一律转为明确的批次失败。
3. **批次执行器**：
   - 统一锁顺序：先 `mediaWrites`，后数据库事务。现有 `commitBookOperation`、`collectUnusedMedia` 等拆成"取锁包装"和"事务内核心"，执行器只调用核心。
   - 试运行：取锁 → 外层 `withTransaction` → 逐步执行 → 计算派生影响 → 抛内部回滚信号，在**最外层事务外**捕获（不与业务失败或协程取消混淆）。
   - 执行上下文 `ExecutionContext`：`asOfDate`、时区、预测区间、参考汇率快照（事务外先取好）。预览时固定并显示。
   - 正式执行：新事务里用同一份归一化方案和上下文重跑 → 比较确认模型 → 一致则提交，同时写入执行记录、云端结果去重记录、待发回执、提交后效果队列；不一致则回滚并要求重新预览。
   - 去重：`(站点, taskId, resultId, sha256)` 和 `plan_id` 都不能重复执行。
4. **确认模型与语义比较器**：
   - 结构化模型，预览页面从它生成；比较只比较规范化的结构化值，不比较文字。
   - 新生成的 ID 按"步骤 + 输出角色 + 业务键"映射成占位符，保留关联关系。
   - 比较内容包括：固定目标集合及其关键识别事实；每个对象的前后绝对值；余额/额度/预算的前后绝对值及风险状态；预测按逐期事实比较（日期、金额、付款账户、规则依据、确认/预测状态）；步骤级效果（改了又改回、重算、草稿清理等也要保留）。
   - revision 和时间戳按类型定义：有业务含义的（预测事实里的还款/退款 revision、影响默认值排序的保存时间）要比较其语义，没有业务含义的具体值忽略。
   - 和时间有关的有效性单独检查：确认时的日期/时区和预览不同、恢复期限或办理期限越界时，要求重新预览。
   - 事实声明绑定到具体步骤和所声明条件的摘要，条件变化后旧勾选作废。
5. **预览与历史界面**（三主题独立设计，中日文）：
   - 提交页：输入需求、选附件、选记录范围、显示将上传的内容。
   - 预览页：助手说明；逐步卡片（这一步做什么、目标对象、连带影响、确认要求，标明是方案中的中间状态）；最终净影响（对象差异、余额/额度/预算前后对比、还款与资金预测前后对比，注明口径、估算值、未知项、所用汇率）；执行边界（哪些一起成败、哪些提交后执行、哪些需要用户操作）；必须勾选的事实声明；确认/拒绝。
   - 方案历史：每份方案的状态（待预览、已执行、已拒绝、失败、已撤销）和详情。
6. **提交后效果与交互工作流执行器**：执行 `post-commit` 和 `interactive` 步骤（偏好写入、附件、需要系统选择器的操作等），可重试，进程中断后能恢复；状态在方案历史里可见。

本地数据：新增 Room 表 `command_plans`（方案 JSON、来源任务/结果、状态、确认模型、上下文、用户勾选、执行时间）和 `command_effects`（提交后效果队列）；`cloud_tasks` 增加 `purpose` 列。均通过正式迁移，保留现有数据。

## 4. 阶段

每个阶段的通用要求：中日文、三主题独立设计；新页面/弹层按 AGENTS.md 做视觉验证；更新受影响的文档；不过度测试，只覆盖本阶段真实风险。

### 阶段 0：技术验证与前置修复

实现与验收结果见[阶段 0 记录](cloud-command-stage-0.md)。

- 用仪器测试在 Room 2.8.4 上确认：外层事务内后续步骤（含 DAO Flow `.first()`）能读到前面步骤的写入；回滚后不触发 `ReminderCoordinator` 重建、UI 的 `snapshot` 看不到试运行状态；嵌套 `withTransaction` 随外层回滚。
- 修复锁顺序：拆分 `commitBookOperation`、`collectUnusedMedia` 以及其他"先媒体锁再事务"的函数（全仓搜索），统一顺序；现有行为不变。
- 测量：在 `LargeLedgerTest` 规模的账本上，模拟 50 步批量修改的试运行耗时，记录结果。
- **验收**：三项行为测试通过；锁顺序修改后相关现有测试通过；耗时数据写入阶段报告。如果任一行为与预期不同，暂停并回到架构讨论。

### 阶段 1：框架与纵向链路

- 协议文档与 schema：`docs/formats/` 增加 `command-plan.v1`、`capabilities.v1`、`ledger-context.v1`、`records.v1` 的 schema 和正常/错误样例；协议说明文件的源文本。
- 组件 1–5 的完整框架（组件 6 只建队列骨架）；数据库迁移。
- 下沉：记账默认值与确认策略（目前在 `AppViewModel.saveEntry` 一带）中本阶段命令用到的部分；金融规则表单到领域输入的转换（`FinancialRuleDraft`）、候选付款日期/计息区间生成（`FinancialPredictionEditor`）中本阶段用到的部分。下沉后界面改为调用同一业务函数，界面行为不变。
- 命令：`account.save`（含信用卡及其选项）、`financialRule.addVersion`、建立/重算预测（按现有预测流程对应的命令，含期初债务与日期；资料不足时显示缺项而不是伪造预测）、`entry.update`（本阶段只支持改分类，批量）。
- 界面：云端交接台增加"云端办理"入口与提交页；领取 `purpose=command` 的结果后进入预览页；方案历史；回执沿用现有 WorkManager 机制。
- **验收**：
  1. 用固定的样例方案（模拟云端结果）跑通"截图建信用卡 → 填还款规则 → 生成预测"和"批量改 20 笔记录的分类"，预览内容正确，确认后账本正确。
  2. 预览后修改账本中相关数据，确认时被拒绝并要求重新预览；修改无关数据时仍可确认。
  3. 中间一步失败、协程取消、进程在提交后中断：不留下部分修改，不重复执行，回执最终发出。
  4. 重复领取同一结果、换结果版本但 `plan_id` 相同：不会执行第二次。
  5. 未知命令、引用类型不符、`catalog_digest` 不符、永久边界操作：整份拒绝。
  6. 三主题提交页、预览页、历史页截图检查通过。
  7. 真实网站往返（需要用户的连接配置和 Work 订阅）列为用户实测项，不在本阶段宣称已验。

### 阶段 2：整批撤销与适配器规范定型

- 每个适配器必须提供逆操作，或明确标为"不可撤销"并写明原因（预览中显示）。补齐阶段 1 命令的逆操作。
- 撤销 = 由执行记录里的前后状态生成一份逆向方案，走同样的预览/确认/执行流程。前提：受影响对象的当前状态等于执行后的状态；有冲突的步骤显示原因并阻止整份撤销（不做部分撤销）。撤销后不删除原执行的去重记录。
- 写出"新增命令适配器检查表"（输入 schema、默认值、前提、确认类型、比较字段、逆操作、执行方式、说明与示例、测试要求），作为阶段 3–6 的验收标准。
- **验收**：信用卡→规则→预测（含额度）和20笔分类两条链路都恢复执行前业务状态；本方案新建对象及从属/修订行可受限移除，已有对象恢复原值。对象有修改或方案外引用时整批阻止并逐项说明；历史显示已撤销及时间。详见[阶段 2 记录](cloud-command-stage-2.md)。
- 阶段 3–6 的每个命令必须逐项满足[新增命令适配器检查表](cloud-command-adapter-checklist.md)。

### 阶段 3：基础账本全覆盖

- 账本：创建、编辑/完成设置、主题与语言、归档/移入回收站/恢复。切换当前账本（`post-commit`，写偏好）按本轮约定移至阶段6；新账本不能在同一方案中继续写入。
- 账户：保存（全部账户类型、期初信息）、启停；账户没有回收站语义，永久删除禁止。
- 分类：保存、收藏、归档/恢复、调整层级；MERGE_DELETE、DELETE_EMPTY 均属永久边界。
- 商户、地点、朋友：保存商户及地点、调整地点、启停商户、保存/启停朋友。
- 记录与资金流：支出/收入/转账/退款的创建与编辑（`entry.update` 扩展到全部字段）、确认实际金额、移入回收站/恢复。负余额确认归入"风险提示"类确认。
- 模板：保存/排序、用模板创建记录（编译成普通记录命令）；模板物理删除禁止。待补完草稿和附件按本轮约定留至阶段6。
- 下沉本阶段涉及的界面编排；界面直接写数据库的地方（全仓搜索 `dao.` 在 `ui/` 下的写入调用）改走业务函数。
- **验收**：每个命令满足检查表；每个领域至少一个组合方案（例如"建账户 + 建分类 + 记 3 笔"）预览正确、执行正确、撤销正确；新增确认/预览卡片三主题截图通过。

### 阶段 4：预算、活动与周期全覆盖

- 月/分类预算、账本预算组合；活动模式、当前活动、保存/结束/移入回收站活动；预留/释放；参与人；他人请客记录。
- 周期：保存/启停、取消/恢复实例、关联/解除、记录支付（含支付草稿协调）；预计收入：保存/取消/新增或关联到账。
- **验收**：同阶段 3 的标准。

### 阶段 5：金融与额度全覆盖

- 规则版本（全部模式）、规则核验、手工计划、预测/重算、余额池、借入、还款/清偿、合同关联、账单确认、已办理安排（事实声明）、安排重核、余额池付款变更、批量转循环及其撤销。
- 额度配置、共享额度组、恢复确认、作废恢复、可用额度观测。
- 资金预测前后对比覆盖全部金融对象。
- **验收**：同阶段 3 的标准；另外用一个"多张卡 + 分期 + 余额池"的复杂方案验证预测比较、事实声明绑定和撤销。

### 阶段 6：文件工作流、偏好与外部效果

- 补齐切换当前账本（post-commit）与待用户补完的记账草稿（interactive）；阶段3已明确移交。

- 流水：接受/解除差异关联、补记、实际金额确认。小票：商品回填与编辑（结果里直接给商品明细，与现有回填共用校验）。CSV：撤销导入批次（导入本身由记录命令替代，在协议说明里写明）。
- 附件：把**本任务上传的源文件**附到记录上（字节已在手机上，`post-commit`）。
- 偏好与分析设置：分析模块、提醒设置、自动汇率、定位开关（系统权限部分为 `interactive`）、照片保存方式。
- 需要系统选择器的操作（如导出备份到用户选的目录）：`interactive`，方案执行时引导用户操作。
- 组件 6 完整实现：重试、进程中断恢复、状态展示。
- **验收**：同阶段 3 的标准；提交后效果在失败重试、进程中断后能继续，且不会重复执行。

### 阶段 7：月度计划、评语与问答

- 每个账本的自然语言月度计划：在应用里编辑（预算页附近，三主题），也可以由命令 `book.monthlyPlan.save` 设置。
- 每月提醒：在通知设置里开关，默认开启；每月 1 日提醒提交上月评语，接入现有 `ReminderCoordinator`。点提醒打开预填的提交页，显示将上传的内容：月度汇总（收支、分类、预算执行、账户变化）、月计划和账本结构。
- 任务 `purpose=monthly-review`；结果使用同一 `command-plan` 格式：`message` 是评语；可以附带建议步骤（例如调整预算），用户可选择预览并执行。
- 评语按账本、按月保存，有历史页。
- 问答：普通云端办理中没有步骤、只有 `message` 的结果作为回答显示。
- **验收**：提醒在正确时间出现且同一月不重复；提交、领取、显示、历史正常；建议步骤走完整预览流程；三主题截图通过。

### 阶段 8：全覆盖审计与总验收

- 审计：列出全部写入路径（Repository 写入函数、ViewModel 动作、界面直接写数据库的地方），逐一对应到命令或永久边界，输出覆盖表；有遗漏就补上。

## 5. 执行与验收流程

- 每个阶段由 Claude 写任务规格交给 Codex 实现。Codex 汇报改了哪些文件、取舍、与规格不一致之处、未完成的部分。
- Claude 验收：看实际 diff，对照本阶段验收标准逐条核对；自己跑构建、单元测试、相关仪器测试，UI 改动跑 `looks=all visual=true` 并查看截图；检查文档。
- 不合格：把具体问题写清楚，让 Codex 返工；返工一次仍不合格，由 Claude 亲自修改。
- 当前阶段验收通过后，才派下一个阶段。
- 环境约束：Gradle 任务串行，`--max-workers=2`；模拟器运行时不串联重型 Gradle 任务；模拟器由 Claude 启动（带窗口，DISPLAY=:0）。Codex 沙箱如果无法运行 Gradle 或模拟器，由 Claude 运行并把输出反馈给它。
- 提交：每个阶段验收通过后提交一次（中文提交说明，不加 Co-Authored-By 行）。
- 每个阶段结束时向用户简要汇报：完成了什么、验收结果、遗留的实测项。

## 6. 风险与暂停条件

- 阶段 0 任一行为与预期不同（读不到前序写入、回滚泄露、锁问题无法统一）：暂停，回到架构讨论。
- 某类操作无法放进"预览后执行"的模型：标为 `interactive`，和用户确认处理方式，不悄悄缩减范围。
- 下沉界面编排时，发现会改变现有界面行为：先停下来说明。
