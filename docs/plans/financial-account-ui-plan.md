## 一、实施依据与边界

### 1.1 已核对的事实

本计划以 2026-11-04 的 UI 审查结论为问题依据（Codex 在模拟器真实 App 中三主题截图审查，Claude 逐条复核，14 项全部成立；审查报告与截图为本地临时产物，未入库），并核对了实际实现。

有三点需要明确：

1. **P2-06 的问题是编辑新版本时缺少差异展示。** 第 1 版规则没有上一版，不能要求它展示旧新差异；新增规则应显示“首次建立”和关键条件摘要。
2. **起草时按账单还款并没有完整预填金额。** 原 `FinancialLedgerEditor` 主要预选付款账户和分配目标。阶段 3 已在独立的 `FinancialRepaymentEditor` / `FinancialRepaymentState` 中实现有明确依据的预填和单目标联动，具体规则仍以 5.3 为准。
3. **云端办理当前没有通用的金融对象跳转。** `CommandFollowupViews.kt:85–113` 的本机续办主要是普通记账草稿、导出和权限操作。本计划中的金融对象续办入口属于新增的本机导航衔接，不能写成已有入口迁移。

### 1.2 冻结设计稿与本次修改的关系

[development-plan.md](development-plan.md) 规定冻结 HTML 第 55 版是复刻依据，同时明确“后续用户明确修改优先于本计划”。

本次以下内容属于**有意偏离冻结稿的设计变更**，需用户确认后才能成为新基准：

| 范围 | 原结构或现有约定 | 推荐变更 |
|---|---|---|

## 二、目标信息架构

以下为推荐方案；重大选择见第七节。

### 2.1 页面层级

```text
账户详情
└─ 账单、计划与金融规则
   ├─ 固定账户栏：返回、账户名称、当前任务
   ├─ 固定任务导航：总览 / 账单 / 计划 / 管理
   │
   ├─ 总览
   │  ├─ 主题封面、下次付款与状态
   │  ├─ 记录还款〔主操作〕
   │  ├─ 查看账单、可用额度〔快捷入口〕
   │  ├─ 付款账户、资金缺口与筹资入口
   │  ├─ 待确认付款、逾期、未安排债务
   │  └─ 未完成金融草稿〔紧凑入口〕
   │
   ├─ 账单
   │  ├─ 月份选择、前后月
   │  ├─ 月汇总
   │  ├─ 按付款日期分组的账单行
   │  │  ├─ 金额确认状态 + 付款状态
   │  │  ├─ 记录还款 / 查看付款
   │  │  └─ 核对金额、查看期次明细
   │  ├─ 信用卡：本付款日批量转为循环还款
   │  └─ 相关消费/借入、未安排提醒
   │
   ├─ 计划
   │  ├─ 添加还款安排〔主操作〕
   │  │  └─ 选择：录入已知账单 / 按规则预测 / 管理循环还款
   │  ├─ 有效计划摘要列表
   │  ├─ 已替换计划〔独立入口或折叠分区〕
   │  └─ 计划详情
   │     ├─ 进度、下次付款、已列剩余金额、状态
   │     ├─ 紧凑期次表 → 期次明细
   │     ├─ 适用于本计划的调整操作
   │     ├─ 计算依据与来源〔按需展开〕
   │     └─ 版本与办理历史 → 历史详情
   │
   └─ 管理
      ├─ 信用卡：还款记录
      ├─ 网贷：借入与合同、还款记录
      ├─ 计算规则 → 规则详情/编辑/版本历史
      ├─ 额度与恢复
      │  ├─ 本地预计额度、配置
      │  ├─ 跨账户共享额度及成员
      │  ├─ 平台可用值
      │  └─ 恢复确认、作废及历史
      ├─ 办理与版本历史〔按对象分类入口〕
      └─ 未完成金融草稿
```

管理首页是任务目录，**不将规则、合同、额度和历史全部展开成另一条长页面**。

### 2.2 信用卡与网贷的区别

| 区域 | 信用卡 | 网贷 |
|---|---|---|
| 总览 | 本期/下次付款、扣款资金、缺口、预计可用额度、付款方式变更截止 | 下次付款、扣款资金、缺口、固定合同与循环借入摘要 |
| 主操作 | 记录还款 | 记录还款；“记录借入”为次操作 |
| 账单 | 一次付、分期、循环还款；保留付款日批量转换 | 固定贷款和循环借入账单；保留合同来源 |
| 计划 | 一次付已知账单、分期计划、账户循环还款计划 | 固定合同分别管理；循环借入按现有共同计划管理 |
| 管理 | 还款记录、规则、额度与恢复、历史、草稿 | 借入与合同、还款记录、规则、额度与恢复、历史、草稿 |
| 额度摘要 | 显示真实配置下的关系与预计可用值 | 纯固定借款总览不突出无关额度；管理入口仍保留 |
| 新建引导 | 区分平台已知安排、规则预测、循环还款 | 同时说明“固定合同逐笔安排”和“循环借入共同还款” |

网贷总览不再默认铺开所有合同的完整期次表。保留近期付款摘要，完整表移到相应计划详情；未知本金、缺少计划和未安排借入仍在总览显式提示。

### 2.3 主操作与层级规则

- 总览：主操作为“记录还款”。
- 计划列表：主操作为“添加还款安排”，不再并列三个同权重实心按钮。
- 账单：未结清账单提供就地还款；待确认付款优先引导查看、核对已有付款，避免误导用户重复记录。
- 管理目录：使用导航行，不堆放多个主按钮。
- 编辑：主操作为“预览”。
- 预览：主操作为具体的保存动作，次操作为“返回修改”。
- 真实办理类操作：比较完成后进入“记录已办理结果”，仍需用户确认平台事实。
- 撤销：从具体办理记录进入，显示具体对象和恢复结果。

### 2.4 子页面、弹层与返回路径

| 场景 | 进入路径 | 返回规则 |
|---|---|---|
| 计划详情 | 计划列表 → 指定计划 | 返回原列表位置 |
| 期次明细 | 账单或计划详情 → 指定账期 | 返回实际来源，保留月份、滚动位置 |
| 还款 | 总览、账单、合同或还款记录 | 取消/保存后返回来源；原账单或记录刷新 |
| 规则 → 额度设置 | 规则草稿 → 额度与恢复 | 返回同一规则草稿，保留输入 |
| 比较方案 → 补齐账单 | 方案草稿 → 本期金额核对 | 返回原方案草稿，重新生成预览 |
| 批量转换 → 建立循环计划 | 批量转换 → 循环计划编辑 | 返回原付款日和选择状态；重新核对候选 |
| 重核 → 上一层安排 | 子安排 → 上一安排核对 | 逐层返回，保留各自草稿，不混用输入 |
| 合同无候选 → 建立计划 | 关联合同 → 新建计划 | 保存后返回该合同的候选选择，突出新计划 |
| 草稿恢复 | 总览或管理 → 草稿 | 本次打开来源作为返回位置；无来源时回对应管理页或计划页 |
| 云端续办 | 命令详情 → 金融对象/草稿 | 返回原命令详情及位置，不自动执行或结束后续任务 |

复杂编辑采用全屏流程；月份、账户、模式选择、日期控件及简单确认仍使用各主题现有菜单或短弹层。预览回退只返回填写步骤，不直接关闭整个流程。

## 四、三主题设计与组件安排

三主题共用业务事实、导航目标和输入状态，**分别实现视觉构图**。不能把同一套通用卡片换三种颜色作为完成。

### 4.1 视觉方案

| 元素 | magazine 杂志 | journal 手账 | objects 小物 |
|---|---|---|---|
| 固定导航 | 编辑目录式四栏，选中项使用墨色强调和短标记 | 四张纸页签，选中页与正文纸面衔接 | 钱包分隔签，选中项像抽出的标签 |

## 五、状态、导航和数据展示契约

### 5.1 导航状态

当前关键位置：

- `FinancialAccountScreen.kt:18`：`tab`、月份和大量编辑/返回状态。
- `NativeApp.kt:77`：`financialInitialMonth`、`financialInitialTab`。
- `NativeApp.kt:143、151、225、245`：账户、事项、金融页面及分析入口。
- `NativeApp.kt:190–225`：返回处理、公共滚动容器与金融页面宿主。

推荐做法：

1. 在金融模块内建立小型、可保存的导航状态，明确任务区、子页、对象 ID 和返回来源；不重构全应用路由。
2. 四个任务区固定为 `overview / statement / plans / manage`。
3. 旧目标映射：
   - `rules` → `manage/rules`
   - `movements` → `manage/records`；需要时直达合同或还款
   - `limits` → `manage/limits`
   - `plans`、`statement`、`overview` 保持业务目标。
4. 暂保留 NativeApp 外层 `"rules"` 路由标识，避免无关页面名称、通知和返回逻辑一起改名；内部页面名称按实际任务显示。
5. 将 `financialInitialTab` 的散落赋值收敛到同一目标转换入口。外部重复打开同一账户时应能消费新的月份/对象请求，不能仅依赖 `rememberSaveable(bookId, accountId)` 的首次初始值。
6. 外部请求只消费一次；普通数据刷新不得重新定位、切回初始标签或关闭编辑器。
7. 金融页拥有自己的滚动区域和固定导航，退出 `NativeApp.kt:212` 的整页公共滚动包装，避免“导航写在顶部但仍随整页滚走”。
8. 列表位置按账本、账户、任务区保存；计划详情按计划 ID 保存，不跨账户复用。

### 5.2 草稿与流程状态

继续使用 `FinancialDraftHost`、`financialField` 和现有持久草稿：

- `FinancialDrafts.kt:98、159、179`：宿主、列表、恢复分派。
- `NativeApp.kt:358–361`：切账本保留、放弃、继续编辑。
- `FinancialAccountScreen.kt:187–205`：循环计划、方案、账单及上层重核返回。

需要保留的状态包括月份、选择目标、输入、展开分区和来源返回位置。

**不得持久恢复旧预览或平台确认勾选。** 草稿恢复后重新预览，事实变化后沿用现有重审机制。

合同新建计划的上下文建议作为可选草稿信息保存，兼容旧草稿默认值；不改变现有 slot 身份，不把旧草稿当成新建流程的空白输入覆盖。返回页面信息尽量留在界面状态中，只有跨进程续办必须知道的合同/来源上下文才进入草稿。

### 5.3 还款简化的准确边界

普通还款首层显示：

- 还款目标；
- 付款账户；
- 实际付款金额；
- 实际付款日期；
- 平台确认状态；
- 一段可核对的组成/分配摘要。

展开区包括费用与组成、跨币种金额、关联已有付款/转账、多目标分配、还款类型与备注。

具体规则：

1. 从账单进入时，预选账期及付款账户；已知待付金额可以作为明确标注来源的建议值。
2. 默认仍为“实际已付款、平台清偿待确认”，不自动勾选平台确认。
3. 单目标时，同一组成只编辑一次，再生成该目标的分配明细；切换多目标才显示可编辑分配行。
4. **账单的“利息/费用合计”不能擅自拆成利息和平台费用。** 有非零合并费用而缺少拆分时，需用户补充；不能默认全部归入其中一项。
5. 未知不补零。同币种也不能仅凭金额相同推定付款端费用为零、平台已实收。
6. 修改金额形成部分还款时，不按比例猜测本金、利息和费用，展开必要组成。
7. 编辑既有记录时，原有费用、跨币种、关联和分配内容必须可见，不因简化模式丢失。
8. 保存继续调用 `previewRepayment` / `commitFinancialLedger`，不新增另一套清偿计算。

### 5.4 预览和比较的数据来源

**规则差异：**

- 使用 `FinancialRuleReview.before` 中同账户、同模式的上一版本与新规则比较。
- 包括基本字段、高级计费规则、费用表、阶梯、奖金月安排、截止时间、生效日和时区。
- 不能只比较当前 `FinancialRuleFacts` 输出的非空字段，否则删除值、空值变化和嵌套列表会漏掉。
- 新建第 1 版显示“首次建立”；旧新业务条件相同时如实显示，并单列版本/生效信息。
- 预览刷新后重新取得差异基线，不沿用最初打开编辑器时的过期比较。

**方案比较：**

- 按付款日期取并集、聚合同日已列金额，不能按期号或数组下标直接配对。
- 同日多付款账户保留账户变化信息；原/新总额相同但账户或组成变化也算变化行。
- 默认显示变化日期及总费用、当期付款、范围后本金变化。
- “查看全部日期”以及“原方案完整依据”“新方案完整依据”始终可达。
- 对没有列出的日期显示“该日无已列付款”；资料不完整时，不能把它解释为完整债务的零付款。
- 总费用、范围后本金等沿用现有比较结果及完整性标识，不在 UI 推导出确定值。

## 七、需要用户拍板的决策

以下事项有多种合理方案。表中的推荐是本计划的设计基线，尚未视为用户决定。

| 决策 | 选项 | 推荐与理由 |
|---|---|---|
| 一级信息架构 | A. 四标签“总览/账单/计划/管理”；B. 保留六类一级导航，使用横向滚动 | **A**。四项可固定显示，管理内容有明确归属；代价是规则多一次进入 |
| 计划展开方式 | A. 摘要列表 → 独立详情；B. 同页手风琴展开 | **A**。多计划、历史和深链更清晰，返回位置稳定；比大手风琴更容易控制复杂操作层级 |
| 非总览页封面 | A. 紧凑账户栏；B. 保留可折叠大封面 | **A**。任务页一进入就有内容，不让用户每次处理折叠状态 |
| 复杂编辑载体 | A. 全屏流程；B. 保留大弹层并固定操作栏 | **A**。更适合长表单、键盘、比较和多层返回；短选择器继续用弹层 |
| 新建计划入口 | A. 一个主入口后选方式；B. 三个入口保留但降权 | **A**。能解释适用场景，空状态更容易开始；代价是熟练用户多一次选择 |
| 单目标还款预填 | A. 根据已知事实建议金额并联动分配；B. 只折叠字段、金额仍全手填 | **A**。真正减少重复劳动；未知、费用拆分和平台确认仍需明确处理 |
| 合同创建后的关联 | A. 返回候选并确认；B. 创建和关联一次提交 | **A**。复用现有事务、结果透明，不扩大数据层；B 需额外设计联合预览与原子提交 |
| 比较表默认范围 | A. 变化日期优先，可看全部；B. 默认全部日期 | **A**。快速看到结果；所有日期、未知和完整范围仍可访问 |
| 中文术语 | A. 首次“循环还款（リボ）”，之后“循环还款”；B. 全程保留“リボ” | **A**。兼顾中文理解和日本金融业务识别 |
| 云端金融续办 | A. 添加具体对象/草稿跳转；B. 只同步文案、预览和术语，仍由用户自行找账户 | 起草推荐 **A**；复核推荐 **B**，见第九节第 1 条 |
