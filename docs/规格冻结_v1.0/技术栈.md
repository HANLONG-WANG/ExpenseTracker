# Android 记账软件技术栈定案 v1.0

本次选型以已经冻结的需求基线为唯一输入：Android-only、本地优先、隐藏式平衡记账、整库及附件加密、50 万笔当前交易、200 万条底层变动及历史版本、十万行表格导入、数十 GB 级备份、位置地图、桌面组件和专业分析。

下面只确定**语言、框架、库、平台 API、构建工具和基础设施组件**。暂不定义模块边界、数据库表、领域对象、调用方向或业务流程，那些属于下一阶段的系统架构设计。

# 二、平台与语言：原生 Kotlin Android

## 最终选择

- 只使用 Kotlin 编写应用业务代码。
    
- 使用原生 Android SDK。
    
- 不采用 Flutter、React Native、Kotlin Multiplatform或 Compose Multiplatform。
    
- 不主动编写 C/C++ 业务代码；SQLCipher 和 MapLibre 带来的原生库通过官方 AAR 使用。
    
- `minSdk = 28`。
    
- `targetSdk = compileSdk = 36`。
    

## 原因

本项目没有跨平台需求，而大量关键功能高度依赖 Android 平台能力：

- Android Keystore 与 BiometricPrompt；
    
- 前台服务和用户发起数据传输任务；
    
- WorkManager；
    
- Storage Access Framework；
    
- Glance 桌面组件；
    
- Android 生命周期和最近任务遮挡；
    
- Play App Signing；
    
- MapLibre 原生地图；
    
- 系统文件授权和外部文件打开。
    

引入跨平台框架只会额外增加平台桥接、原生依赖封装、后台限制适配和安全审计面积，没有业务收益。

`minSdk 28` 是有意的产品决策。它牺牲一部分旧设备覆盖率，换取更一致的加密、时间 API、存储权限、系统组件和测试矩阵。该软件定位为高质量长期项目，不需要为了覆盖 Android 8 及更早设备积累大量兼容代码。

# 三、UI 技术栈

## 1. Jetpack Compose＋Material 3

所有新页面使用 Jetpack Compose，不建设 XML View 页面体系。Compose 是 Android 当前推荐的现代原生 UI 工具包，Material 3、动态色、主题、字体缩放和无障碍语义均可以在同一体系中处理。([Android Developers](https://developer.android.com/compose?utm_source=chatgpt.com "Jetpack Compose UI App Development Toolkit"))

选定组件：

- Compose UI；
    
- Compose Foundation；
    
- Material 3；
    
- Lifecycle Compose；
    
- Compose Animation；
    
- Compose UI Test；
    
- Compose BOM 管理兼容版本。
    

允许使用 `AndroidView` 的场景严格限定为：

- MapLibre `MapView`；
    
- 极少数没有成熟 Compose API 的系统或第三方原生视图。
    

不使用混合 XML/Compose 双套 UI 体系。

## 2. Navigation 3

导航采用 **Navigation 3**，不再以 Navigation 2 作为新项目基础。

Navigation 3 是 Compose-first 导航体系，由应用显式控制 back stack，适合复杂录入流程、分类网格复用、深层筛选、恢复页面状态以及多个主导航入口。Navigation 2 已进入维护模式，而 Navigation 3 已有稳定版本。([Android Developers](https://developer.android.com/jetpack/androidx/releases/navigation3 "https://developer.android.com/jetpack/androidx/releases/navigation3"))

## 3. Jetpack Glance

桌面小组件使用 Glance。它适合快速记账入口、预算、余额、目标进度和大型财务概览组件，但必须遵守底层 RemoteViews 的布局及交互限制，不能把普通 Compose 页面直接搬到桌面。([Android Developers](https://developer.android.com/develop/ui/compose/glance/create-app-widget "https://developer.android.com/develop/ui/compose/glance/create-app-widget"))

## 4. 状态与异步数据

采用：

- `ViewModel`；
    
- `StateFlow` 表达可观察界面状态；
    
- `SharedFlow` 或 Channel 表达一次性事件；
    
- `collectAsStateWithLifecycle()`；
    
- Kotlin structured concurrency。
    

不引入 RxJava，也不同时维护 LiveData 和 Flow 两套响应式模型。Coroutines 和 Flow 是 Android 官方推荐的异步与数据流方案。([Android Developers](https://developer.android.com/kotlin/flow "https://developer.android.com/kotlin/flow"))

# 四、依赖注入和设置存储

## 1. Hilt＋KSP

依赖注入采用 Hilt：

- 与 Android 生命周期和组件集成成熟；
    
- 支持 ViewModel、Worker 和系统组件；
    
- 通过 KSP 生成代码；
    
- 不使用运行时反射式依赖注入；
    
- 不使用 kapt。
    

Hilt 是 Android 官方推荐的依赖注入方案，Dagger/Hilt 已支持 KSP。([Android Developers](https://developer.android.com/training/dependency-injection/hilt-android "https://developer.android.com/training/dependency-injection/hilt-android"))

## 2. Proto DataStore

Proto DataStore只保存**非账务型设置**，例如：

- 主题和语言；
    
- 一周起始日；
    
- 应用锁超时；
    
- 小组件显示设置；
    
- 回收站保留期限；
    
- 备份策略；
    
- 遥测开关；
    
- 用户界面偏好。
    

账务数据、预算、目标、周期模板等不能放进 DataStore，仍进入主数据库。

Proto DataStore提供强类型、异步和事务性更新，适合替代 SharedPreferences。([Android Developers](https://developer.android.com/topic/libraries/architecture/datastore "https://developer.android.com/topic/libraries/architecture/datastore"))

# 五、数据库：Room 2.8.4＋SQLCipher 4.17.0

这是本次技术选型中最关键的决定。

## 1. 最终组合

- Room 2.8.4；
    
- SQLCipher for Android 4.17.0；
    
- 使用新的 `net.zetetic:sqlcipher-android`，不使用已经停止演进的旧 `android-database-sqlcipher`；
    
- AndroidX SQLite 2.x 的 `SupportSQLiteOpenHelper` 接口；
    
- Paging 3；
    
- FTS5；
    
- R*Tree；
    
- 必要的复杂分析使用经过白名单构造的原生 SQL。
    

Room 提供 SQL 编译期检查、类型映射、事务、迁移验证和 Paging 集成；SQLCipher 提供 SQLite 数据库的整库加密。当前 SQLCipher通过 `SupportOpenHelperFactory` 与 Room 2.x 集成，4.17.0 已针对 Room 2.8 兼容性进行更新。([Android Developers](https://developer.android.com/jetpack/androidx/releases/room?utm_source=chatgpt.com "Room | Jetpack"))

## 2. 为什么不使用 Room 3

Room 3 已经发布稳定版本，但它使用新的 SQLite 驱动架构。截至当前，SQLCipher 尚未提供对应的 Room 3 驱动集成。因此当前不能同时获得：

- Room 3；
    
- 官方可维护的 SQLCipher 整库加密；
    
- 满足本项目要求的低风险组合。
    

所以项目明确冻结在：

> **Room 2.8.4＋SQLCipher 4.17.0**

只有在 SQLCipher 官方发布 Room 3 驱动、迁移测试和目标规模测试全部通过后，才重新评估 Room 3；不能仅因为 Room 3 更新就自动升级。([Android Developers](https://developer.android.com/jetpack/androidx/releases/room3?utm_source=chatgpt.com "Room 3.0 | Jetpack"))

## 3. Room 使用限制

由于 SQLCipher 与 Room 的组合层面仍存在少数公开兼容问题，技术规则固定为：

- Room 与 SQLCipher版本成对锁定；
    
- 所有 schema 导出到版本控制；
    
- 所有正式版本必须提供显式迁移；
    
- 不把 destructive migration 用于正式用户数据；
    
- 初期不使用 `@Upsert`；
    
- 使用显式 `INSERT`、条件检查和 `UPDATE` 事务代替；
    
- nullable 字段和原生查询必须有真机兼容测试；
    
- 每次升级 Room、AndroidX SQLite 或 SQLCipher 都执行完整兼容矩阵。
    

SQLCipher 的公开问题列表中仍有 Room `@Upsert` 和部分 null 处理相关问题，因此这些限制属于主动风险控制，而不是一般编码偏好。([GitHub](https://github.com/sqlcipher/sqlcipher-android/issues/90 "NullPointerException when the column value is NULL · Issue #90 · sqlcipher/sqlcipher-android · GitHub"))

## 4. 搜索和地理查询

全文搜索采用 SQLite FTS5：

- 分类；
    
- 商户；
    
- 项目；  
    -互请名称；
    
- 参与人；
    
- 备注；
    
- 附件显示名称。
    

中文、日文和英文需要独立验证分词效果；对于不依赖语言分词的“任意子串搜索”，优先评估 FTS5 trigram tokenizer。FTS5 是 SQLite 官方全文检索扩展。([SQLite](https://www.sqlite.org/fts5.html "https://www.sqlite.org/fts5.html"))

地点推荐与地图可视范围初筛使用 SQLite R_Tree。精确距离仍由 Kotlin 计算，R_Tree只负责快速缩小候选集。

应用启动测试和 CI 必须验证 SQLCipher 构建确实包含：

- FTS5；
    
- R*Tree；
    
- JSON1 或当前 SQLite 内建 JSON 功能；
    
- 所需窗口函数。
    

如果官方 AAR 缺少任一必需能力，则使用同版本 SQLCipher 源代码构建经过签名和复现验证的内部 AAR，而不是静默降级为全表扫描。

# 六、金额、汇率、贷款和时间

## 1. 金额

正式入账金额保存为：

> `Long`＋货币代码

`Long` 表示货币的最小单位：

- JPY：1 表示 1 日元；
    
- USD：1 表示 1 美分；
    
- 三位小数货币按相应最小单位处理。
    

禁止使用 `Float` 或 `Double` 存储、累计或比较金额。

## 2. 汇率与利率

以下计算使用 `java.math.BigDecimal`：

- 汇率；
    
- 有效汇率；
    
- 贷款利率；
    
- 分期费率；
    
- 等额本息；
    
- 等额本金；
    
- 提前还款；
    
- 百分比分摊；
    
- 币种换算；
    
- 金额表达式计算。
    

运算必须显式指定：

- `MathContext`；
    
- 舍入模式；
    
- 输出货币 scale；
    
- 中间计算精度。
    

必要时使用 `BigInteger` 防止长期贷款或复杂中间计算溢出。

`Double` 只允许用于已经精确汇总后的图表坐标、标准差、趋势线和其他非账务统计结果，不能反写为权威金额。

## 3. 金额表达式

`+ - × ÷ ( )` 使用自行实现的确定性 Kotlin 解析器：

- tokenizer；
    
- Pratt parser 或 shunting-yard；
    
- `BigDecimal` 求值；
    
- 明确的语法错误位置；
    
- 不调用 JavaScript 引擎；
    
- 不使用支持任意函数或脚本的第三方表达式语言。
    

这样可以保证表达式功能不会演变成脚本执行面。

## 4. 日期时间

使用 `java.time`：

- `Instant`：绝对创建和修改时间；
    
- `ZoneId`：交易时区和账单时区；
    
- `ZonedDateTime`：用户录入及显示；
    
- `LocalDate`：预算归属日期；
    
- `YearMonth`：月度预算和账单周期；
    
- `LocalTime`：周期模板时间。
    

由于应用仅面向 Android且最低 API 28，不需要引入跨平台日期时间库。

# 七、数据库外的加密技术

## 1. Android Keystore

Android Keystore用于保存或保护：

- SQLCipher 数据库密钥的包装密钥；
    
- 应用普通加密主密钥；
    
- 卡片保险库认证密钥；
    
- 自动备份本机密钥材料。
    

Keystore支持不可导出的密钥和用户认证约束。BiometricPrompt可以通过 `CryptoObject` 让一次认证直接授权一次加解密操作。([Android Developers](https://developer.android.com/privacy-and-security/keystore "https://developer.android.com/privacy-and-security/keystore"))

## 2. 卡片保险库

保险库单独采用：

- 随机生成的数据加密密钥；
    
- Android Keystore中的认证绑定密钥包装；
    
- BiometricPrompt＋CryptoObject；
    
- 每次查看或复制独立解密；
    
- 离开页面或超时后清除明文缓冲区。
    

普通账本解锁与保险库解锁使用不同密钥，不共享解锁状态。

## 3. 附件和大型备份

使用 Google Tink：

- 小型清单、元数据和密钥包：AEAD；
    
- 附件、大型备份和大型临时流：Streaming AEAD；
    
- 流式模板采用 Tink 推荐的 AES-GCM-HKDF 大分段方案；
    
- 不把整个文件加载到内存后再加密。
    

Tink Streaming AEAD专门用于大型数据流，并提供经过认证的分段加密；当前稳定版本线可使用 1.23。([Google for Developers](https://developers.google.com/tink/encrypt-large-files-or-data-streams "https://developers.google.com/tink/encrypt-large-files-or-data-streams"))

## 4. 恢复密码

恢复密码使用：

- Argon2id；
    
- Bouncy Castle `Argon2BytesGenerator`；
    
- 每份密钥包独立随机盐；
    
- 保存算法版本、内存、迭代次数和并行度；
    
- 参数在目标设备上校准，但不降低到不安全的快速配置；
    
- Bouncy Castle只作为类库调用，不注册为全局 Android Security Provider。
    

Argon2id是 RFC 9106 推荐的混合模式，Bouncy Castle提供了对应实现。([IETF Datatracker](https://datatracker.ietf.org/doc/rfc9106/ "https://datatracker.ietf.org/doc/rfc9106/"))

## 5. 明确不使用的安全库

不使用：

- `EncryptedSharedPreferences`；
    
- `EncryptedFile`；
    
- `MasterKey` 作为新设计核心。
    

`androidx.security:security-crypto` 1.1.0 中相关 API 已整体标记弃用，因此本项目直接使用 Keystore、Tink 和 SQLCipher，不建立在弃用抽象之上。([Android Developers](https://developer.android.com/privacy-and-security/cryptography "https://developer.android.com/privacy-and-security/cryptography"))

# 八、网络和外部服务

## 1. OkHttp 5＋Okio 3

网络统一使用：

- OkHttp 5 稳定版；
    
- Okio 3；
    
- kotlinx.serialization JSON；
    
- MockWebServer测试。
    

不使用 Retrofit。项目只有少量、但高度特殊的网络接口：

- 汇率；
    
- Google Drive 大文件分块传输；
    
- 遥测；
    
- 崩溃报告；
    
- 地图样式及瓦片由地图 SDK 处理。
    

Drive可恢复传输、范围下载、重试、校验、进度和断点持久化需要低层控制，Retrofit不会提供实质性收益。

## 2. 网络约束

所有自有请求必须：

- 设置连接、读取和调用超时；
    
- 支持取消；
    
- 对幂等请求实施有界重试；
    
- 不在日志中记录请求正文；
    
- 不发送金额、账户、商户、位置等业务字段；
    
- 通过 Network Security Config 禁止明文 HTTP；
    
- 汇率服务只收到币种对和日期；
    
- 遥测只允许白名单字段。

# 九、地图与定位

## 1. MapLibre Native Android 13.4.1

地图采用 MapLibre Native Android SDK，通过 `AndroidView` 嵌入 Compose。

不采用尚处于 0.x 阶段的 MapLibre Compose包装库。地图属于数据量大、交互复杂且性能敏感的功能，直接使用稳定原生 SDK比依赖未稳定的包装层更可控。MapLibre Native支持 Android，并提供聚类、数据源和热力图能力；13.4.1 是当前稳定版本线。([GitHub](https://github.com/maplibre/maplibre-native "https://github.com/maplibre/maplibre-native"))

初始采用成熟的 OpenGL 构建，不把 Vulkan作为首发必要条件。

## 2. 底图

默认使用 OpenFreeMap：

- 不需要用户 API Key；
    
- 与开源项目定位一致；
    
- 不需要应用建立地图账户；
    
- 地图样式 URL 不硬编码到业务代码；
    
- 必须显示地图数据和样式要求的 attribution。
    

OpenFreeMap公开服务声明不使用 API Key、Cookie 或用户数据库，并提供开放样式和瓦片服务。由于公共服务不等于商业 SLA，应用必须支持通过构建配置切换到 MapTiler或自托管 OpenFreeMap。([openfreemap.org](https://openfreemap.org/quick_start/ "https://openfreemap.org/quick_start/"))

## 3. 定位

采用：

1. `FusedLocationProviderClient` 为主；
    
2. Google Play services不可用时使用 `LocationManager` 后备；
    
3. 只请求前台位置；
    
4. 保存时最多等待 3 秒；
    
5. 超时即以无位置记录保存；
    
6. 不启动后台连续定位。
    

Fused Location Provider提供适合单次当前位置请求的 API。([Android Developers](https://developer.android.com/develop/sensors-and-location/location/retrieve-current "https://developer.android.com/develop/sensors-and-location/location/retrieve-current"))

Apache Commons CSV支持预定义格式，并可以按记录顺序处理数据。([Apache Commons](https://commons.apache.org/proper/commons-csv/apidocs/index.html "https://commons.apache.org/proper/commons-csv/apidocs/index.html"))

## 2. XLSX：dhatim FastExcel 0.20.2

选择：

- `org.dhatim:fastexcel:0.20.2`；
    
- `org.dhatim:fastexcel-reader:0.20.2`。
    

原因：

- 面向大型 XLSX 的流式读写；
    
- Java 8+；
    
- 不需要将完整工作簿载入内存；
    
- 比 Apache POI 更符合十万行 Android 导入导出场景；
    
- 本项目不需要执行 Excel宏、重算复杂公式或编辑任意现有工作簿。
    

FastExcel 0.20.2 是当前发布版本，并以快速读写大型 Excel文件为目标。([GitHub](https://github.com/dhatim/fastexcel?utm_source=chatgpt.com "dhatim/fastexcel: Generate and read big Excel files quickly"))

正式采用前设置一次强制兼容门槛：

- API 28、API 34、API 36 真机；
    
- 100,000 行；
    
- 多工作表；
    
- 日期、数字、共享字符串；
    
- 公式缓存值；
    
- 非 ASCII 文本；
    
- 取消及损坏文件；
    
- 低内存场景。
    

FastExcel仍是冻结选型；如果其 Android运行时出现不可修复的硬兼容问题，预定后备不是 Apache POI，而是基于 Android XML Pull Parser和 ZIP64 实现受控范围的 OOXML流式编解码器。

## 3. PDF：Android PdfDocument

PDF报表使用平台 `android.graphics.pdf.PdfDocument`：

- 逐页 Canvas绘制；
    
- 自行控制分页；
    
- 可以复用图表渲染结果；
    
- 输出到流；
    
- 不引入大型 PDF编辑库。
    

`PdfDocument` 提供页面 Canvas和 OutputStream输出，足以覆盖报表生成需求。([Android Developers](https://developer.android.com/reference/android/graphics/pdf/PdfDocument "https://developer.android.com/reference/android/graphics/pdf/PdfDocument"))

## 4. 归档

专用备份容器使用：

- Apache Commons Compress；

# 十四、后台任务与大型操作

采用混合方案，而不是把所有任务都塞进 WorkManager。

## WorkManager／CoroutineWorker

用于：

- 周期交易检查和漏项补齐；
    
- 汇率缓存更新；
    
- 自动本地备份；
    
- 回收站清理；
    
- 备份保留策略；
    
- 遥测队列发送；
    
- 短时、可延迟的维护任务。
    

WorkManager用于可靠且可延迟的后台工作，CoroutineWorker支持结构化取消。([Android Developers](https://developer.android.com/jetpack/androidx/releases/work "https://developer.android.com/jetpack/androidx/releases/work"))

## User-Initiated Data Transfer

Android 14/API 34 及以上，用于用户主动发起的：

- Google Drive大型上传；
    
- 大型下载；
    
- 导出到远端文件提供器。
    

这是 Android针对用户主动数据传输提供的系统机制。([Android Developers](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options "https://developer.android.com/develop/background-work/background-tasks/data-transfer-options"))

## 前台服务

API 28—33，或不适合 UIDT 的本地大型操作，使用带可见通知的 `dataSync` 前台服务：

- 大型导入；
    
- 大型导出；
    
- 完整恢复；
    
- 大型本地备份；
    
- 附件迁移。
    

Android新版本对前台数据同步和长时间 WorkManager都有配额限制，因此每个大型操作必须持续写入检查点，可以暂停、失败恢复或重新入队，不能假设后台进程可以无限运行。([Android Developers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running "https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running"))

不使用 exact alarm。周期交易允许系统延迟，并在应用下次启动时通过幂等算法补齐。

API 30以上通过 `ApplicationExitInfo` 在下次启动时读取：

- native crash；

## 4. 功能统计

功能统计使用自定义事件模型：

- 固定枚举事件名；
    
- 固定字段 schema；
    
- 编译期或单元测试白名单；
    
- 禁止任意 Map 和自由文本；
    
- 30 天轮换安装 ID；
    
- 可查看本地待发送事件；
    
- 关闭即删除队列和 ID。
    

遥测接收端属于服务器基础设施，不属于本次“仅 Android平台”的技术栈；Android客户端只依赖一个可替换的 HTTPS白名单接收接口。

## 5. 日志

不使用“自动打印整个对象”的日志方式。

采用自定义结构化日志封装：

- debug构建允许诊断元数据；
    
- release构建只允许错误代码和流程阶段；
    
- 所有业务实体默认不可序列化到日志；
    
- 禁止金额、备注、路径、商户和位置；
    
- 敏感类型的 `toString()` 不输出内部值。
    

开发构建启用 StrictMode 和 LeakCanary；正式构建不包含 LeakCanary。

# 十七、明确排除的技术

|不采用|原因|
|---|---|
|Flutter、React Native|无跨平台需求，增加 Android安全及后台能力桥接成本|
|Kotlin Multiplatform|没有第二平台需要共享代码|
|XML View作为主 UI|会形成两套 UI体系；Compose足够覆盖需求|
|Room 3|当前没有 SQLCipher官方驱动集成|
|直接使用裸 SQLCipher Cursor|丧失 Room 的编译期 SQL校验、映射和迁移能力|
|SQLDelight|技术上可行，但本项目没有跨平台价值，且 Room的 Android工具链集成更直接|
|Realm、ObjectBox|不适合以复杂 SQL分析、FTS、窗口函数和整库 SQLCipher为核心的要求|
|未加密系统 SQLite|直接违反整库静态加密要求|
|Google Maps SDK|增加闭源服务和计费绑定；MapLibre更符合开源定位|
|MapLibre Compose 0.x|当前成熟度不足，首发直接使用 Native SDK|
|MPAndroidChart|长期缺少正式发布，不作为长期项目基础|
|Apache POI|Android包体、依赖和内存成本不适合十万行流式处理|
|Retrofit|API数量少且 Drive传输需要低层控制|
|RxJava|Coroutines/Flow已覆盖需求，避免双异步体系|
|`androidx.security.crypto`|核心 API已弃用|
|AlarmManager exact alarm|周期交易不要求绝对准点，WorkManager＋启动补齐更合理|
|Firebase Analytics/Crashlytics|不满足严格白名单及本地可审计遥测边界|
|DuckDB|引入第二套原生分析数据库、额外加密和一致性问题；当前规模 SQLite足够|
|AppSearch|会产生独立搜索存储及额外加密边界，FTS5更可控|
|JavaScript表达式引擎|金额输入只需要有限算术语法，不应引入脚本执行面|

# 十八、版本冻结与升级规则

## 立即冻结的关键组合

```text
minSdk                  28
compileSdk / targetSdk  36
JDK                     17
AGP                     9.3.x
Gradle                  9.5.x
Kotlin                  2.4.x
Room                    2.8.4
SQLCipher Android       4.17.0
MapLibre Native         13.4.1
Coil                    3.5.x
Tink                    1.23.x
FastExcel               0.20.2
```

其余 Jetpack库由兼容的稳定 BOM 或 Version Catalog精确锁定。

## 升级政策

1. 生产代码只使用 stable版本，不使用 alpha、beta、RC或 snapshot。
    
2. 所有依赖精确锁版本，不使用动态版本。
    
3. Room、AndroidX SQLite、SQLCipher作为一个兼容单元升级。
    
4. 数据库相关升级必须跑完全部历史迁移和目标规模测试。
    
5. Tink、Bouncy Castle、OkHttp、SQLCipher安全更新优先处理。
    
6. MapLibre升级必须回归地图聚类、热力图、缓存和内存。
    
7. FastExcel升级必须回归十万行导入导出。
    
8. 每个发布版本生成依赖锁、SBOM和许可证报告。
    
9. Room 3和 MapLibre Compose在满足前述稳定条件前不迁移。
    
10. 依赖升级失败不能迫使用户执行破坏性数据库重建。
