本设计严格建立在三项已冻结输入之上：

- 产品需求：单用户、单总账、本地优先、隐藏式平衡记账、多币种、预算、信用卡、贷款、项目、目标资金、互请结算、完整修改历史、加密附件与专业分析。
- 技术基线：Kotlin、Room 2.8.4、SQLCipher、SQLite FTS5/R*Tree、`Long` 最小货币单位、`BigDecimal` 汇率和贷款计算。
- 总体架构：模块化单体、领域分层、轻量 CQRS、当前状态＋不可变修订＋不可变财务日志、统一财务写入协调器和可重建投影。

以下具体聚合、实体、表字段、约束和交易算法属于本轮设计推导。

# 一、先解决一个架构冲突

现有基线同时包含两个要求：

1. `JournalEntry` 和 `Posting` 在普通账务操作中永不修改、永不删除；
2. 交易从回收站永久清除时，要删除当前记录、全部历史版本和附件。

两者不能在所有情况下同时成立。最终规则调整为：

> **财务日志在正常业务操作中严格只追加。只有一条交易链已经被完整冲销、当前净账务影响为零、所有依赖已处理、回收站期限已到时，才允许执行受控隐私清除。**

受控清除必须：

- 在维护锁下执行；
- 验证原始分录与全部冲销分录对每个账户、币种和本位币的净额均为零；
- 删除该交易链的业务修订、分录、效果行和附件引用；
- 写入不含金额、备注、商户、位置等敏感内容的 `purge_tombstone`；
- 保留交易稳定 UUID、清除提交 ID 和清除时间，用于阻止旧备份在合并时将其复活。

因此新增架构决策：

> **ADR-007A：Journal/Posting 在普通操作中不可变；隐私清除是唯一物理删除例外，只能作用于已完全冲销的封闭交易链。**

全量“替换恢复”仍可能把旧备份中的已清除数据带回来，因为替换恢复的语义就是完全恢复旧快照；“合并恢复”则必须让清除墓碑优先于旧版本。

# 二、模型分层

系统中的数据分为四类，生命周期必须严格区分。

| 类型 | 含义 | 可否修改 | 可否重建 |
|---|---|---:|---:|
| 当前领域实体 | 账户、分类、商户、项目等当前状态 | 可以，通过 Command | 否 |
| 不可变业务修订 | 交易各次创建、编辑、删除、恢复的完整快照 | 不可以 | 否 |
| 不可变财务事实 | Journal、Posting、经济效果、预算效果等 | 不可以 | 否 |
| 查询投影 | 当前余额、预算执行、流水列表、报表汇总等 | 可以 | 可以 |

数据库表后续使用以下标记：

- **C**：Current，当前领域状态；
- **R**：Revision，不可变业务修订；
- **F**：Fact，不可变事实；
- **P**：Projection，可重建投影；
- **K**：Cache，可丢弃缓存；
- **O**：Operation，长任务和基础设施状态。

# 三、限界上下文和聚合根

## 3.1 领域上下文

| 上下文 | 主要聚合根 | 核心职责 |
|---|---|---|
| Book & Commit | `Book`、`BookCommit` | 单总账、提交图、幂等命令、合并和清除墓碑 |
| Ledger | `BusinessTransaction` | 交易修订、复式分录、经济语义、修改和冲销 |
| Account | `UserAccount`、`PaymentCard` | 现金、银行、信用、贷款账户和实体卡 |
| Classification | `Category`、`Merchant`、`Place` | 分类、商户、地点、位置推荐 |
| Budget | `BudgetMonth`、`BudgetTemplate` | 月度总预算、分类预算、结转和调整 |
| Project | `Project` | 项目预算、项目交易和项目报表 |
| Goal | `Goal` | 账户内预留资金和目标进度 |
| Refund | `RefundTransaction` | 原交易关联、部分退款、跨月预算恢复 |
| Credit | `CreditStatement`、`InstallmentPlan` | 信用卡账单、还款分配、分期计划 |
| Loan | `LoanContract` | 分批次贷款、还款计划、实际执行和提前还款 |
| Settlement | `SettlementActivity` | 多人互请、参与人贡献、净额结算 |
| Automation | `TransactionBlueprint`、`RecurrenceSeries` | 快捷模板、周期规则、候选记录 |
| Attachment | `Attachment`、`EncryptedBlob` | 加密附件、哈希去重、引用和垃圾回收 |
| Analytics | `ReportDefinition`、`Dashboard` | 固定报表、自定义报表、预测和异常规则 |
| Transfer | `BackgroundOperation` | 导入、导出、备份、恢复和合并 |

## 3.2 聚合边界原则

- `BusinessTransaction` 不包含完整的账户、分类、商户或项目对象，只保存稳定 ID 和必要快照。
- `BudgetMonth` 按月份分成独立聚合，不能把所有历史月份组成一个巨大预算聚合。
- `CreditStatement` 按信用账户和账单周期分成独立聚合。
- `LoanContract` 内部可以有多个 `LoanTranche`，用于组合贷款。
- `SettlementActivity` 管理参与人和净额子账，不直接拥有交易。
- `PaymentCard` 是独立聚合根，引用所属账户；卡片敏感字段使用独立安全边界。
- 跨聚合写入由 `FinancialMutationCoordinator` 统一协调，不能由聚合之间直接调用 DAO。

# 四、核心值对象

每个需要备份、导入或合并的实体拥有两类 ID：

```kotlin
@JvmInline value class InternalId(val value: Long)
```

# 五、Book、Commit 和版本模型

## 5.1 Book 聚合

```kotlin
data class Book(
```

- `REFERENCE_DATA_CHANGE`
- `PROJECTION_REBUILD`

普通提交一个父节点，合并提交允许两个父节点。


# 十二、修改、删除和恢复模型

## 12.1 创建

创建 `rev1`：

```text
Transaction.currentRevision = rev1
Journal APPLY(rev1)
Effects APPLY(rev1)
```

## 12.2 编辑

将 `rev1` 编辑为 `rev2`：

```text
TransactionRevision rev2
Journal REVERSE(applies rev1)
Journal APPLY(applies rev2)
旧效果的反向效果
新效果
currentRevision = rev2
```

反向分录的业务有效时间使用原分录时间，而不是编辑当天，使当前历史余额被正确重算。Commit 创建时间仍记录真实编辑时间。

## 12.3 放入回收站

```text
TransactionRevision rev3, resultingState = TRASHED
Journal REVERSE(applies rev2)
currentRevision = rev3
Transaction.state = TRASHED
```

`rev3` 仍复制完整业务内容，便于展示和恢复。

## 12.4 恢复

```text
TransactionRevision rev4, resultingState = ACTIVE
Journal APPLY(applies rev4)
currentRevision = rev4
Transaction.state = ACTIVE
```

恢复旧版本永远创建新修订，不修改旧修订。

## 12.5 依赖处理

删除或修改具有依赖的交易时，命令必须明确给出依赖策略：

- 同时冲销依赖交易；
- 将退款改为独立退款；
- 将分期计划取消或重新绑定；
- 重新计算互请净额；
- 重新打开已结算活动；
- 重新生成信用账单；
- 重新计算贷款计划。

不得留下悬空业务关系。

# 三十、数据库与领域约束分工

## 30.1 由 SQLite 直接保证

- 行级非空；
- 枚举范围；
- UUID 唯一；
- Command ID 唯一；
- Revision number 唯一；
- Recurrence occurrence 唯一；
- 一条 Entry 的 `reverses_entry_id` 唯一；
- 卡片属于一个账户；
- Blob 哈希和大小去重；
- 主外键完整性；
- 金额大于等于零；
- 局部状态合法。

## 30.2 由领域 Planner 保证

- Journal 本位币借贷平衡；
- Posting 币种与 LedgerAccount 一致；
- 一笔交易最多一个分类和一个项目；
- 普通支出/收入分类必填；
- 卡片与账户类型兼容；
- 二级分类父级不可变；
- 退款累计不超额；
- 预算层级上限；
- 互请 paid、owed 和净额守恒；
- 贷款本金守恒；
- 分期本金守恒；
- 自动信用卡还款不主动形成溢缴；
- Goal 与 Account 币种一致；
- 删除依赖闭包完整；
- 当前投影版本与 Book revision 一致。

## 30.3 由完整性审计重复验证

启动维护、备份和恢复后执行：

- `PRAGMA integrity_check`
- `PRAGMA foreign_key_check`
- 所有 Journal 借贷平衡；
- 每个 Posting 币种合法；
- 每个当前交易存在正确子类型详情；
- 每个 Active 交易拥有一个未被冲销的有效 APPLY 链；
- 每个 Trashed 交易净账务效果为零；
- 预算、账户、贷款、信用和互请投影可由事实表重建；
- 投影 Hash 与重建结果一致。

# 三十一、原子写入流程

## 31.1 新建普通支出

```text
1. 校验账户、分类、卡片和币种
2. 解析金额表达式
3. 固化汇率证据
4. 创建 BusinessTransaction
5. 创建 TransactionRevision rev1
6. 创建 RevisionAmount
7. 生成 Journal APPLY
8. 插入 Posting
9. 插入 EconomicEffect
10. 插入 BudgetEffect
11. 可选插入 ProjectEffect / GoalEffect / SettlementEffect
12. 更新账户、预算、项目、目标、互请、FTS、RTree、小组件投影
13. 更新 currentRevision
14. 创建 BookCommit 和 CommandReceipt
15. 增加 book.localRevision
```

全部位于一个 Room `withTransaction` 中。

## 31.2 编辑交易

```text
1. 检查 expectedRevisionId
2. 加载当前修订和全部依赖
3. 生成 rev2
4. 为旧 APPLY 生成 REVERSE Entry 和反向 Effects
5. 为 rev2 生成 APPLY Entry 和新 Effects
6. 重算受影响日期后的账户每日余额
7. 重算受影响月份后的预算结转链
8. 重算信用账单、贷款、项目、目标和互请
9. 更新 currentRevision
10. 创建 Commit
```

## 31.3 永久清除

只有满足以下条件才可执行：

- 当前状态为 `TRASHED`；
- 已超过 `purge_after`；
- 所有 Entry 和 Effect 的净额为零；
- 依赖已级联删除或解除；
- 没有未完成导入、恢复或合并任务引用；
- 当前备份操作没有读取这些附件。

清除事务：

```text
1. 获取维护锁
2. 重新验证净额为零
3. 插入 purge_tombstone
4. 删除投影和 FTS/RTree 记录
5. 删除 Revision 子表和附件引用
6. 删除 Effects、Postings、JournalEntries
7. 删除 TransactionRevisions 和 BusinessTransaction
8. 将无引用 Blob 加入 GC 队列
9. 创建 PURGE Commit
10. 释放维护锁
```

# 三十二、永久不变量

以下规则应作为领域测试、数据库审计和恢复验证的共同标准：

1. 每个 Journal Entry 的本位币借方等于贷方。
2. 每个 Posting 的账户币种与 LedgerAccount 一致。
3. 每个正式交易最多一个分类、一个项目和一个目标。
4. 普通支出和收入只有一个 Primary 金额，不允许拆分分类。
5. 每个当前交易必须引用一个完整、自洽的当前修订。
6. 旧修订、旧 Journal 和旧 Effects 在普通操作中不可修改。
7. 每条 APPLY Entry 最多被冲销一次。
8. Active 交易的净 APPLY 链恰好产生一份当前账务影响。
9. Trashed 交易的当前净账务影响为零。
10. 退款不得超出原交易可退余额，除非显式 override。
11. 退款现金流日期、费用归属日期和预算月份可以不同。
12. 信用卡还款不产生费用或收入。
13. 贷款本金还款不产生费用。
14. 贷款利息、手续费和罚息产生非消费费用。
15. 内部转账不改变净金融资产。
16. 当前汇率不能修改历史交易本位币金额。
17. 当前汇兑重估不进入收入和费用。
18. 一级分类预算总和不得超过总预算。
19. 二级分类预算总和不得超过父分类预算。
20. 结转链必须能从交易效果、预算调整和前月结转重建。
21. Goal 余额不改变真实账户余额。
22. 互请交易所有参与人的头寸增量合计为零。
23. 外部参与人付款不能修改本地用户账户。
24. 已完成互请结算后的交易修改不得篡改历史结算付款。
25. 贷款计划本金合计必须等于待偿本金。
26. 分期计划本金合计必须等于分期本金。
27. 周期 occurrence 唯一键必须防止重复生成。
28. 候选记录不能产生任何正式财务效果。
29. 分类、账户、卡片的墓碑或归档不能破坏历史引用。
30. Purge tombstone 在合并恢复中优先于旧实体版本。
31. 所有核心投影必须与同一 `localRevision` 对齐。
32. 保险库字段不得进入 FTS、审计快照、日志或遥测。
33. 任意导入、恢复或大型批次失败时，主账本必须保持原状态。
34. 所有金额累加必须检测 `Long` 溢出。
35. 任何依赖当前交易内容的缓存都必须带版本号。

# 三十三、Schema v1 迁移规范

## 33.1 首版原则

- 从 v1 开始导出 Room Schema JSON；
- 所有表、索引、视图和触发器定义进入版本控制；
- 正式版本禁止 destructive migration；
- 主数据库、导入 staging database 和备份 manifest 各自拥有独立 schema version；
- Journal 和 Effect 表保存 `rule_set_version`。

## 33.2 后续迁移策略

采用 Expand → Backfill → Switch → Contract：

1. 新增可空字段或新表；
2. 分批回填；
3. 新旧代码并行读取验证；
4. 切换查询；
5. 后续版本才收紧约束或删除旧结构。

## 33.3 不得重新解释历史财务事实

如果未来账务算法改变：

- 新交易使用新的 `rule_set_version`；
- 旧 Journal、Posting 和 Effect 不重新计算；
- 投影重建按每条事实的规则版本解释；
- 只有用户主动执行“重算历史交易”时，才创建新的修订、冲销和替换事实。

## 33.4 每次迁移后验证

- SQLCipher 解密；
- `integrity_check`；
- `foreign_key_check`；
- Journal 平衡；
- 交易子类型完整；
- 投影重建一致；
- FTS 和 R*Tree 可用；
- 目标规模查询基准；
- 旧备份恢复测试。

# 三十五、最终模型结论

数据库的权威写模型不是“流水表”，而是以下组合：

```text
BusinessTransaction
    └── immutable TransactionRevision
            ├── typed transaction detail
            ├── amount and FX evidence
            ├── attachment / location / settlement snapshot
            └── JournalEntry
                    ├── Posting
                    ├── EconomicEffect
                    ├── BudgetEffect
                    ├── ProjectEffect
                    ├── GoalEffect
                    ├── StatementEffect
                    ├── LoanEffect
                    └── SettlementEffect
```

当前界面和报表从可重建投影读取：

```text
Immutable facts
    └── synchronous projections
            ├── current transaction
            ├── account balance
            ├── budget usage
            ├── credit statement
            ├── loan progress
            ├── project / goal
            ├── settlement position
            ├── FTS / RTree
            ├── analytics rollups
            └── widget snapshots
```

该设计同时满足：

- 用户界面保持普通记账语义；
- 底层达到复式记账级准确性；
- 交易编辑、删除和恢复可完整审计；
- 多币种账户和历史汇率可追溯；
- 信用卡、贷款、退款和互请不会污染收入消费口径；
- 预算、项目、目标和报表可从不可变事实重建；
- 大规模查询不需要扫描或载入全部历史；
- 备份合并能够识别稳定实体和清除墓碑；
- 敏感卡片字段与普通账务数据分离。

下一层设计应直接将本逻辑模型转换为 **Room Entity、DAO、Database View、FTS/R*Tree DDL、领域 Command 和 FinancialMutationPlan 接口规格**，不再改变上述聚合边界和账务不变量。
